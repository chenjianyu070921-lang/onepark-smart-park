## 二、致命问题（P1，必须修复）

### P1-1 `golang.org/x/text` 版本错误，gateway 无法编译

**位置**：`gateway/go.mod:47`

**现状**（本次未提交改动引入）：

```
golang.org/x/text v1.34.0 // indirect
```

**问题描述**：`golang.org/x/text` 版本线只有 v0.x，**v1.34.0 不存在**；且 `gateway/go.sum:113-114` 只有 v0.34.0 的 hash，go.mod 与 go.sum 已失配。这是本次改动把 `v0.34.0` 手改成 `v1.34.0` 造成的。

**实证**（`go build ./gateway/...`）：

```
golang.org/x/text@v1.34.0: unrecognized import path "golang.org/x/text"
```

**影响**：gateway 无法编译，对外入口完全不可用；即使网络正常也拉不到该版本。

**修复**：

```diff
-	golang.org/x/text v1.34.0 // indirect
+	golang.org/x/text v0.34.0 // indirect
```

或直接执行 `go mod tidy` 收敛。

**验证**：`go build ./gateway/...` 退出码 0。

### P1-2 JWT 密钥明文写死为公开弱密钥

**位置**：`gateway/etc/apigateway-api.yaml:5`（本次未提交改动引入）

**现状**：

```yaml
JwtSecret: "change-me-in-prod"
```

**问题描述**：密钥是公开可读的占位弱密钥；JWT claims 里的 `user_id/role_ids/tenant_id` 都是自声明字段，网关只验签名不查库。任何人用这个公开密钥自签一个 `user_id:1` 的 token 即可冒充任意用户/管理员通过网关。同时违反 README 的「配置走环境变量占位 `${VAR}`」约定（`.env.example:65` 已定义 `JWT_ACCESS_SECRET` 但未被引用），且 `config.go` 中 `JwtSecret` 标记为 `optional`，漏配时空密钥也能跑。

**影响**：带着此配置部署 = 认证体系形同虚设，任意身份冒充。

**修复**：

`gateway/etc/apigateway-api.yaml`：

```yaml
JwtSecret: "${JWT_ACCESS_SECRET}"
```

`gateway/internal/config/config.go` 改为必填并在启动时校验：

```go
package config

import (
	"errors"

	"github.com/zeromicro/go-zero/rest"
)

type Config struct {
	rest.RestConf
	JwtSecret string `json:",optional"`
}

func (c Config) Validate() error {
	if c.JwtSecret == "" {
		return errors.New("JwtSecret is required, set via env JWT_ACCESS_SECRET")
	}
	return nil
}
```

`gateway/apigateway.go` 在 `conf.MustLoad` 后调用：

```go
conf.MustLoad(*configFile, &c)
if err := c.Validate(); err != nil {
	panic(err)
}
```

**验证**：不配环境变量启动 → 启动即报错；配 `JWT_ACCESS_SECRET` 后正常启动；用错误密钥访问受保护路由返回 401。

## 三、严重问题（P2，建议修复）

### P2-3 三个 M6 服务端口全是 8888

**位置**：`gateway/etc/apigateway-api.yaml:3`、`app/auth-service/etc/auth-api.yaml:3`、`app/user-manage/etc/usermanage-api.yaml:3`

**现状**：

```yaml
Port: 8888   # 三个文件均为 8888
```

**问题描述**：与 README 端口分配表（`README.md:89-91`）冲突——gateway=8080、auth=8018、user-manage=8019；Makefile:114 注释也写明「HTTP :8080」。三个服务同时启动必有一个以上 bind 失败。

**影响**：本地联调 `make run-auth` + `make run-apigateway` 立刻端口冲突；与其余 19 个服务的端口分配表也不一致。

**修复**：

| 文件 | 改为 |
|------|------|
| `gateway/etc/apigateway-api.yaml` | `Port: 8080` |
| `app/auth-service/etc/auth-api.yaml` | `Port: 8018` |
| `app/user-manage/etc/usermanage-api.yaml` | `Port: 8019` |

**验证**：三个服务同时启动，`netstat -ano | findstr` 确认各端口独立监听。

### P2-4 错误码 HTTP 状态码映射错误

**位置**：`common/errorx/http_status.go:11-21`

**现状**：

```go
func (e *CodeError) HttpStatus() int {
	if len(e.Code) < 4 {
		return http.StatusInternalServerError
	}
	// 形如 M1-E-1001, 第 3 位是级别
	level := string(e.Code[3])
	switch level {
	case LevelError:
		return http.StatusInternalServerError
	...
```

**问题描述**：按「错误级别」映射状态码，导致所有 E 级错误一律 500。`M6-E-0001`（参数错误）、`M6-E-0002`（未登录）、`M6-E-0004`（资源不存在）语义上应为 400/401/404。且 gateway 中间件对 token 失效硬编码 401（`gateway/internal/middleware/auth.go:98`），与统一映射行为矛盾——同一条链路两套状态码。

**影响**：前端拿不到正确的 HTTP 语义（未登录应触发跳转登录，却收到 500）；网关与公共库行为不一致。

**修复**：

```go
package errorx

import "net/http"

// HttpStatus 按具体错误码映射 HTTP 状态码.
func (e *CodeError) HttpStatus() int {
	switch e.Code {
	case ErrBadRequest:
		return http.StatusBadRequest
	case ErrUnauthorized:
		return http.StatusUnauthorized
	case ErrForbidden:
		return http.StatusForbidden
	case ErrNotFound:
		return http.StatusNotFound
	default:
		return http.StatusInternalServerError
	}
}
```

**验证**：补单测断言 `M6-E-0002 → 401`、`M6-E-0004 → 404`、`M6-E-0005 → 500`。

### P2-5 响应格式与项目约定不一致

**位置**：`gateway/internal/handler/apigatewayhandler.go:24-26`、`app/auth-service/internal/handler/authhandler.go:24-26`、`app/user-manage/internal/handler/usermanagehandler.go:24-26`

**现状**：

```go
resp, err := l.Auth(&req)
if err != nil {
	httpx.ErrorCtx(r.Context(), w, err)
} else {
	httpx.OkJsonCtx(r.Context(), w, resp)
}
```

**问题描述**：三个 handler 全用 goctl 默认 `httpx.OkJsonCtx` 输出裸对象；README 约定统一响应 `{code,msg,data}`（`common/response.Body`），gateway 中间件也输出 `{code,msg,data}`。同一项目两种格式并存，前端无法统一解析。另外当前 logic 未实现、`resp` 为 nil 时接口返回 `null`。

**修复**：handler 改用 `common/response`：

```go
// app/auth-service/internal/handler/authhandler.go
resp, err := l.Auth(&req)
if err != nil {
	response.FailWith(w, errorx.ErrInternal, err.Error())
	return
}
response.Ok(w, resp)
```

> 注：`httpx.ErrorCtx` 的 err 是 go-zero 错误，统一封装时建议在 logic 内转为 `*errorx.CodeError` 再走 `response.Fail`。

**验证**：`curl` 接口返回体为 `{"code":"0","msg":"ok","data":...}`。

### P2-6 JWT 身份链路空转

**位置**：`gateway/apigateway.go:24`、`gateway/internal/middleware/auth.go`、`common/ctxdata/ctxdata.go`

**现状**：

```go
// gateway/apigateway.go
authMw := middleware.NewAuthenticator(c.JwtSecret, "/from/", "/auth/")
```

**问题描述**：

1. skip 前缀 `/from/` 恰好覆盖当前唯一路由 `/from/:name`（`gateway/internal/handler/routes.go:17-20`），JWT 校验对现有全部请求不生效；
2. 中间件把身份写入 `x-user-id/x-role-ids/x-tenant-id` Header，但业务服务没有任何 middleware 把 Header 转进 context——`common/ctxdata` 只有 `SetRequestId/SetUserId`，且没有 role/tenant 的 Set/Get，下游 `ctxdata.GetUserId` 永远读不到值。

**影响**：目前无消费者不炸，但接入真实业务路由/服务时会出现「要么被 `/from/` 前缀误跳过、要么拿不到身份」。鉴权属于公共基础服务核心能力，必须接线。

**修复**：

1. skip 前缀只保留真正的免鉴权接口（如 `/auth/login`、`/auth/refresh`），移除 `/from/` 这类模板前缀：

```go
authMw := middleware.NewAuthenticator(c.JwtSecret, "/auth/login/", "/auth/refresh/")
```

2. 补 header→context 中间件（放 `common/middleware/identity.go`，业务服务统一挂载）：

```go
package middleware

import (
	"net/http"
	"strconv"

	"onepark/common/ctxdata"
)

// Identity 将网关注入的身份 Header 写入 context, 业务侧只信 context, 不信任前端直接传参.
func Identity(next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		ctx := r.Context()
		if uid := r.Header.Get(ctxdata.CtxUserId); uid != "" {
			if id, err := strconv.ParseInt(uid, 10, 64); err == nil {
				ctx = ctxdata.SetUserId(ctx, id)
			}
		}
		next(w, r.WithContext(ctx))
	}
}
```

3. 补齐 `common/ctxdata` 的 role/tenant 读写函数（`SetRoleIds/GetRoleIds/SetTenantId/GetTenantId`）。

**验证**：带合法 token 请求业务路由，logic 中 `ctxdata.GetUserId(ctx)` 能读到网关注入的 user_id；不带 token 返回 401。

## 四、警告问题（P3）

### P3-7 ES healthcheck 使用 curl，镜像无此命令

**位置**：`deploy/docker-compose.yml:182`

**现状**：

```yaml
test: ["CMD-SHELL", "curl -fs http://localhost:9200/_cluster/health || exit 1"]
```

**问题描述**：Elasticsearch 8.x 官方镜像（Ubuntu 基底）不包含 `curl`，healthcheck 会持续失败，容器永远 `unhealthy`。

**修复**：

```yaml
test: ["CMD-SHELL", "wget -q -O - http://localhost:9200/_cluster/health || exit 1"]
```

**验证**：`docker compose ps` 中 ES 状态为 healthy（本机需 Docker 环境实跑确认）。

### P3-8 TDengine 默认密码错误

**位置**：`deploy/.env.example:62`

**现状**：

```
TDENGINE_DSN=root:onepark123@tcp(tdengine:6030)/device
```

**问题描述**：TDengine 默认 root 密码为 `taosdata`，不是 `onepark123`；M1 服务按此 DSN 连接会认证失败。

**修复**：

```
TDENGINE_DSN=root:taosdata@tcp(tdengine:6030)/device
```

**验证**：`docker compose exec tdengine taos -s "SHOW DATABASES"` 后，用该 DSN 连接成功（本机需 Docker 环境实跑确认）。
