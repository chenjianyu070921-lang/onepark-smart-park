## 〇、模块总览

M2 承接园区"物业运营"域的四大业务线，另受组长划入交付**门禁权限管理**：

| 业务线 | 服务 | 端口 | 核心场景 |
| --- | --- | --- | --- |
| 工单闭环 | workorder-service | 8091 / gRPC 9091 | 报修创建 → 派单 → 处理 → 验收/驳回 → 关闭 |
| 访客通行 | visitor-service | 8092 | 邀请发码 → 扫码签入(联动开门) → 签出 |
| 停车计费 | parking-service | 8093 | 地磁上报 → 入场识别 → 离场计费 → 月卡管理 |
| 公告发布 | notice-service | 8094 | 公告创建(立即/定时) → 站内通知 → 在线推送 → 已读回填 |
| 门禁权限 | access-control | 8010 | 批量授权/撤权 → 远程开门(审计) → 刷卡记录查询 |

统一约定：经网关 8080 携带 `x-tenant-id / x-user-id / x-role-ids / x-request-id`；响应体 `{code, msg, data}`（成功 `code="0"`）；跨服务事件走 Kafka（尽力而为，不阻断主流程）。

## 一、工单闭环管理

### 1.1 场景目标
业主报修/投诉等问题从**发起 → 分派 → 处理 → 验收**全程线上留痕，支持驳回返工与任意环节关闭，处理时效供大屏统计（gRPC 9091 聚合）。

### 1.2 角色
- 业主/企业租户（角色5）：报修发起，仅见自己报的单。
- 物业客服（3）/园区管理员（2）/系统管理员（1）：派单、状态流转。
- 物业维修人员（4）：接单处理、提交完成，仅见派给自己的单。

### 1.3 主流程（五态状态机）
```
业主创建工单 → 待派单(0)
管理员派单(assign) → 处理中(1)          [写入处理人+部门]
维修提交(submit)   → 待验收(2)
管理员验收(approve) → 已完成(3)          [记录 finished_at]
管理员关闭(close)   → 已关闭(4, 终态)
```
分支：**驳回(reject)** 待验收(2) → 处理中(1)，维修返工后重新提交；**取消** 待派单(0) 可直接 close。

### 1.4 关键业务规则
- 建单即待派单，处理人/部门默认 0，乐观锁 `version` 初始 0。
- 派单与状态流转均为 **version 条件更新**：并发操作 `RowsAffected==0` 即报"冲突，请刷新后重试"（错误码 `M2-E-1003`）。
- 每次动作写 `work_order_flow` 流水（from/to/action/operator），与主表**同事务**，杜绝"有状态变化无审计流水"。
- FSM 校验失败返回 `M2-E-1002`；工单不存在返回 `M2-E-1001`（强制租户隔离）。
- 涉及接口：`POST /api/workorder`（创建）、`POST /api/workorder/:id/assign`（派单）、`POST /api/workorder/:id/status`（submit/approve/reject/close）、`GET /api/workorders`（分页，RBAC 角色叠加个人维度）、`GET /api/workorder/:id`（详情）、`POST /api/workorder/:id/attachments`（附件，MinIO）。
- 事件联动：建单/派单/状态流转均发 `workorder-event`；M2 消费 `alarm-event`（停车异常车）自动创建报修工单（幂等）。

## 二、访客通行联动

### 2.1 场景目标
业主/物业邀请访客后生成**防伪造二维码**，访客到场扫码签入自动触发门岗开门（联动 M1 设备），离开签出，全程轨迹可查。

### 2.2 主流程
```
业主邀请(invite) → 生成加密二维码+base64图片, 状态=待使用(1)
访客到场扫码(checkin) → 验签+有效期校验 → 状态=已签入(2) → 调 M1 开门(800ms 短超时)
访客离开(checkout, 按ID或二维码) → 状态=已签出(3)
```

### 2.3 关键业务规则
- **二维码防伪**：内容为 `base64(JSON载荷+md5签名)`，签入前 constant-time 验签，不通过统一报"二维码无效"（不透出细节，防探测）；邀请响应可带 `qr_image`（base64 PNG，渲染失败降级不阻断邀请）。
- **有效期**：超过过期时间签入 → 记录置"已过期(4)"并拒绝，错误码 `M2-E-2002`。
- **防重复核销**：签入更新带 `status=待使用` 原子条件，并发第二次请求 `RowsAffected==0` 直接拒绝（防止重复开门）。
- **开门降级三态**：M1 成功→"开门成功"；未配置→"门禁未配置，签入已记录，请联系前台人工开门"；不可达/超时→"门禁未响应，签入已记录，请联系前台人工开门"。**签入一律不阻断**。
- 涉及接口：`POST /api/visitor/invite`、`POST /api/visitor/checkin`、`POST /api/visitor/checkout`、`GET /api/visitor/:id`（详情+轨迹 invite→checkin_open_door→checkout→expired）、`GET /api/visitor/records`（分页，邀请人维度过滤）。
- 事件联动：invite/checkin/checkout 均发 `visitor-event`（key=访客记录ID，供大屏实时感知访客动态）。

## 三、停车自动计费与月卡

### 3.1 场景目标
地磁设备上报车辆出入，系统自动建停车记录并计费；月卡车辆免计费并支持办理/续费/停用/到期提醒。

### 3.2 主流程
```
M1 event-dispatcher 上报 device-telemetry(标准信封 request_id + payload 业务字段)
parking-service 消费:
  entry → 建停车记录(状态=停车中, 月卡识别定 vehicle_type) → 发 parking-entry
  exit  → 按 entry/exit 事件时间差计费 → 状态=已完成 → 发 parking-exit
异常车(异常类型)离场 → 另发 alarm-event → M2 自动建报修工单
```

### 3.3 计费规则（代码内固定规则，费率表已备待配置化）
- 月卡/VIP：0 元。
- 临时车：15 分钟内免费；超出按 **5 元/小时向上取整**。
- 按遥测事件时间（`occurred_at`）计费，不按消费时刻，容忍消息延迟。

### 3.4 关键业务规则
- **入场幂等**：Kafka 至少一次投递下，同一 `request_id` 的重复入场消息由 `parking_record.uk_request` 唯一键去重，静默跳过且不重复发 `parking-entry`。
- **月卡识别**：入场时 `vehicle_type=0`（未知）则查 `(tenant, plate)` 生效月卡（status=生效且时间窗覆盖入场时刻）；DB 未初始化降级按临时车，不阻断入场。
- **月卡管理**：创建校验车牌非空、生效止晚于生效起、同车牌已有生效卡拒绝（提示直接续费）；表不建 (tenant,plate) 唯一键——停用/过期后可再次办卡。`expiring_days` 参数支持到期提醒筛选。
- 消息兼容：标准信封为主，旧扁平格式（字段顶层）自动回退。
- 涉及接口：`GET /api/parking/records`（分页+状态/车牌/时间筛选）、`GET /api/parking/active`（在场车辆）、`POST /api/monthly-card`（办卡）、`POST /api/monthly-card/:id/renew`（续费）、`POST /api/monthly-card/:id/disable`（停用）、`GET /api/monthly-cards`（列表+到期提醒）。

## 四、公告统一发布与触达

### 4.1 场景目标
物业统一发布通知/公告（支持**定时发布**），已发布内容推送站内通知与在线用户实时推送，用户未读数可查、已读可回填。

### 4.2 主流程
```
创建公告:
  publish_at=0  → 立即发布(状态=2) → 发 notice-event → 站内通知 + 在线推送
  publish_at>0  → 存草稿(状态=1) → 定时调度每分钟扫描 → 到期自动发布 → 补发 notice-event
用户侧:
  GET /api/notices/unread-count  查未读数
  POST /api/notices/read         已读回填(body 版)
  POST /api/notice/:id/read      已读回填(路径版别名, 幂等)
```

### 4.3 关键业务规则
- 公告类型 1通知/2公告/3活动/4停水/5停电；置顶公告列表优先（`top DESC, id DESC`）。
- **定时发布**：调度到期后按 `status=草稿` 条件更新，仅更新成功的实例投递事件——多实例部署不会重复推送；服务启动时先做一次补偿扫描（防停机跨期）。
- **站内通知**：消费 `workorder-event` 自动生成工单动态通知（建单/派单/状态变化）。
- **在线实时推送**：notice-event → Redis PubSub `notice-push:{tenant}`，网关侧订阅推送在线用户。
- **已读回填幂等**：仅回填当前用户本人 `notice_read` 记录，`read_at IS NULL` 才更新；重复调用/广播型公告返回 `updated=0` 不报错。
- 涉及接口：`POST /api/notice`、`GET /api/notices`（分页+type/status 筛选）、`GET /api/notices/unread-count`、`POST /api/notices/read`、`POST /api/notice/:id/read`。

## 五、门禁权限管理（access-control）

### 5.1 场景目标
管理人员对"人员×门禁设备"批量授权/撤权（含时间段与星期几生效窗）；支持远程开门（全部留审计）；刷卡通行记录可查。

### 5.2 关键业务规则
- **批量授权**：人员×设备笛卡尔积（单次上限 500），校验时间窗 HH:mm 与 days 1-7；重复授权幂等覆盖（ON DUPLICATE KEY UPDATE）。
- **撤权**：绑定租户物理删除，0 匹配报 `M3-E-2002`（不静默）。
- **远程开门**：调 M1 SendCommand 800ms 短超时；**设备白名单 fail-closed**（未配置白名单时全拒）；成功/失败/超时/被拒**均落 `access_operate_log` 审计**（含操作人与结果）。
- **刷卡记录**：`/api/access/records` 分页查询（人员/设备/结果/开门方式/时间范围筛选，强制租户隔离）；注：远程开门审计不在该表，用 SQL 查 `access_operate_log`。
- 刷卡通行时的授权有效性判定按架构由 M1/M6 侧消费 `access_permission`（status/expire_at/time_window 字段已备）。
- 涉及接口：`POST /api/access/grant`、`DELETE /api/access/revoke`、`POST /api/access/remote-open`、`GET /api/access/records`。

## 六、场景间联动关系（事件驱动）

| 事件 | 生产方 | 触发的联动 |
| --- | --- | --- |
| `parking-entry` / `parking-exit` | parking | 大屏车流展示（M5 消费） |
| `alarm-event` | parking（异常车） | M2 自动建报修工单（工单线） |
| `workorder-event` | workorder | notice 站内通知；M5 大屏统计（gRPC 直采） |
| `notice-event` | notice | 站内通知 + Redis PubSub 在线推送 |
| `visitor-event` | visitor | 大屏访客动态（预留消费方） |

联动均为**尽力而为**：Kafka 不可用仅记日志，HTTP 主流程不回滚；对账类场景以 DB 为准。
