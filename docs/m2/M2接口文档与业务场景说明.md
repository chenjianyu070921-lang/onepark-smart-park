# M2 物业管理模块 · 接口文档与业务场景说明

> 适用范围：物业管理模块（M2）四大服务 —— 工单 workorder-service、访客 visitor-service、停车 parking-service、公告 notice-service。
> 本文档基于各服务 .api / .proto 契约与代码实现整理，作为 M2 对外接口与业务联动的权威说明。
> 统一约定：所有接口经 API 网关注入 x-tenant-id（租户隔离）与 x-role-ids / x-user-id（RBAC）；响应体统一由 response.Ok/Fail 包装。

## 1. 模块概览

| 服务 | 技术形态 | 核心职责 |
| --- | --- | --- |
| workorder-service | gRPC（WorkorderService）+ 工单生命周期管理 | 工单建单/派单/流转、M5 大屏聚合统计 |
| visitor-service | REST（visitor-api） | 访客邀请二维码、多方式签入核销、门禁开门、签出、黑名单 |
| parking-service | REST（parking-api）+ Kafka 消费 | 车辆出入场计费、月卡管理、计费规则配置 |
| notice-service | REST（notice-api） | 公告发布/列表/撤回、已读回填、未读计数 |

## 2. 工单服务 workorder-service

### 2.1 接口

gRPC（供 M5 运营调度大屏聚合）：

| RPC | 入参 | 出参要点 |
| --- | --- | --- |
| Ping | Empty | Empty（探活） |
| ListWorkOrders | tenant_id(园区,0=不限)、status(状态过滤, <0=不限、0=待派单)、page、page_size | total / list(摘要) / pending_count / today_count / completed_today / avg_process_minutes / completion_rate |

status 语义：<0 不限；>=0 按该状态筛选（其中 0=待派单）。HTTP 列表与该约定对齐（修复审查问题1）。

工单生命周期管理（建单 / 派单 / 状态流转）：

| 动作 | 触发 | 前置约束 |
| --- | --- | --- |
| create 建单 | 业主/物业报修 | 建单即 待派单(0)；维修仅能报自己单、业主仅能报自己单 |
| assign 派单 | 管理员/客服 | 仅 待派单(0) 可派；RBAC 仅系统管理员/园区管理员/物业客服可派单 |
| submit 提交完成 | 维修 | 处理中(1) → 待验收(2) |
| approve 验收通过 | 业主/主管 | 待验收(2) → 已完成(3)，写 finished_at |
| reject 驳回 | 业主/主管 | 待验收(2) → 处理中(1) |
| close 关闭/取消 | 任意 | 任意活跃态 → 已关闭(4)，写 finished_at |

### 2.2 工单状态机（FSM）

| 状态码 | 含义 | 允许出边 |
| --- | --- | --- |
| 0 待派单 | 建单初始态 | assign→1、close→4 |
| 1 处理中 | 已派单处理 | submit→2、close→4 |
| 2 待验收 | 提交待验收 | approve→3、reject→1、close→4 |
| 3 已完成 | 正常终态 | close→4 |
| 4 已关闭 | 终态（不可再流转） | 无 |

乐观锁：状态流转带 version 条件，并发冲突返回"状态流转冲突，请刷新后重试"并与审计流水同事务回滚。

### 2.3 大屏聚合口径（与 HTTP 看板一致）

- 待处理 pending_count = status IN (0,1)（待派单+处理中）；待验收(2) 属验收环节，不计入运营"待处理"看板（物业联调确认口径）。
- 今日新建 today_count = created_at >= 今日0点（本地时区，DSN loc=Local 保证无偏移）。
- 今日完成 completed_today = status IN (3,4) AND finished_at >= 今日0点（含"已关闭"终态，避免完成率随 close 回退）。
- 平均处理时长 avg_process_minutes = 已完成工单 TIMESTAMPDIFF(分, created_at, finished_at) 均值。
- 完成率 completion_rate = (已完成3 + 已关闭4) / 总数 × 100，空园区返回 0（不除零）。

## 3. 访客服务 visitor-service（REST）

### 3.1 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /api/visitor/invite | 发起邀请，生成带签名的加密二维码 + base64 图片 |
| POST | /api/visitor/checkin | 多方式签入（二维码/手机号/身份证/人脸/工牌），核销 + 调 M1 开门 |
| POST | /api/visitor/checkout | 按 Id 或二维码签出 |
| GET | /api/visitors | 访客记录分页（按 status 过滤） |
| GET | /api/visitor/:id | 访客详情 + 门禁进出轨迹 |
| POST | /api/visitor/blocklist | 黑名单新增/更新（手机号或身份证去重） |
| POST | /api/visitor/blocklist/:id/unblock | 黑名单解除 |

### 3.2 关键枚举

- 访客状态：1 待使用 / 2 已签入 / 3 已签出 / 4 已过期。
- 核验方式 verify_channel：1 二维码(默认) / 2 手机号 / 3 身份证 / 4 人脸 / 5 工牌。
- 签入响应 open_msg：开门指令已下发（M1 异步 MQTT 下发，仅代表指令已受理，不代表物理门已开）；降级提示"门禁未响应，签入已记录，请联系前台人工开门"，不阻断签入。

### 3.3 签入核销与开门链路（全链路）

前台邀请 → visitor-service 生成 md5 签名二维码
  → 访客扫码/凭证签入
      1) 黑名单实时拦截(fail-closed: 查询异常即拒)
      2) 过期校验
      3) Redis SETNX 防重放闸(visitor:redeem:{recID}, TTL 至二维码过期)  ← 与 DB CAS 双保险
      4) DB CAS 核销(status=待使用→已签入, 并发抢先者释放锁, 绝不重复开门)
      5) gRPC 调 M1 device-service SendCommand → MQTT 下行 onepark/cmd/{deviceId}/down 开门
      6) 发布 checkin 事件到 Kafka visitor-event
  → 离开时签出

多方式签入仅绑定最近一条待使用记录（status=待使用 AND Order(id DESC)），避免同凭证多邀请时误绑最早/已消费记录（修复"First 绑定歧义"）。

## 4. 停车服务 parking-service（REST + Kafka）

### 4.1 出入场与计费接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /api/parking/entry | 车辆入场（实际由 M1 Kafka 地磁事件驱动，亦提供 HTTP 入口便于联调） |
| POST | /api/parking/exit | 车辆离场，触发计费（优先走费用规则，无规则降级内置默认） |
| GET | /api/parking/records | 停车记录分页 |
| GET | /api/parking/active | 在场车辆列表 |
| GET | /api/parking/fee-rule | 查询当前生效计费规则 |
| POST | /api/parking/fee-rule | 新增/更新计费规则 |

### 4.2 月卡管理接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /api/parking/monthly-card | 创建月卡（同园区同车牌已生效则提示"请续费"） |
| POST | /api/parking/monthly-card/renew | 续费（延长有效期，须晚于当前到期时间；已停用卡续费自动恢复生效） |
| POST | /api/parking/monthly-card/disable | 停用（幂等：已停用重复停用直接成功） |
| GET | /api/parking/monthly-cards | 月卡分页（支持 status 过滤、车牌模糊、expiring_days 到期提醒） |

月卡并发防线：生成列 active_plate_key（仅 status=1 取车牌，否则 NULL）+ 唯一索引 uk_monthly_active_plate，保证同租户同车牌仅一条生效月卡；停用/过期卡不占唯一槽，允许重新办卡。冲突时逻辑层转"请续费"友好提示。

### 4.3 计费规则与口径

- 计费规则字段：free_minutes(免费时长) / hourly_fee(元/小时,>0) / daily_cap(每日封顶,0=不封顶) / effective_from / effective_to。
- 计费函数：月卡/VIP 免费；临时车首 free_minutes 免费，之后 hourly_fee 元/小时向上取整；跨天按天数放大 daily_cap。
- 自动离场（Kafka onTelemetryExit）与人工离场（ParkingExit）**统一走 GetActiveParkingFeeRule + CalcFeeByRule**，口径一致（修复此前自动路径只用内置默认的不一致）。
- 时长/计费按设备事件时间（occurred_at）口径，非处理时间。

## 5. 公告服务 notice-service（REST）

### 5.1 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /api/notice | 发布公告（type: 1通知 2公告 3活动 4停水 5停电；支持 top 置顶、publish_at 定时发布） |
| GET | /api/notices | 公告分页（type/status 过滤） |
| GET | /api/notices/unread-count | 当前用户未读计数（notice_read 中 read_at IS NULL 条数） |
| POST | /api/notices/read | 公告已读回填（body 版） |
| POST | /api/notice/:id/read | 公告已读回填（路径版，同语义） |
| POST | /api/notice/:id/recall | 公告撤回（仅已发布可撤回，置 已撤回 + 补偿事件） |

### 5.2 公告状态与送达

- 公告状态：1 草稿 / 2 已发布 / 3 已撤回。
- 未读计数基于 notice_read 表 read_at IS NULL 实时统计；已读回填与计数配套，支撑站内信红点。
- 定时发布由 cron 防重触发，避免重复发布。

## 6. 业务场景说明（端到端）

### 场景 A：业主报修工单闭环

业主在小程序报修 → create 建单（待派单）→ 物业客服 assign 派单给维修（处理中）→ 维修 submit 提交（待验收）→ 业主 approve 验收通过（已完成，写 finished_at）→ 大屏"完成率"上升、"待处理"下降。任意环节可 close 关闭（取消）。M5 大屏经 gRPC ListWorkOrders 单次聚合实时刷新待处理/完成率/平均时长。

### 场景 B：访客邀请通行

业主/物业在前台填来访信息发起邀请 → invite 生成签名二维码 → 访客到门岗扫码（或凭手机号/身份证）→ checkin 黑名单拦截 + 核销（Redis 闸 + DB CAS 双保险）+ gRPC 调 M1 开门 → 访客进园 → 离开时 checkout 签出。全程 Kafka visitor-event 供大屏/安防感知；黑名单命中实时拒绝。

### 场景 C：月卡车进出场计费

月卡车辆入场（M1 地磁事件）→ parking-service 入场建记录，事件未带车型时按月卡表自动识别（命中生效月卡按月卡计费）→ 离场（M1 事件）→ onTelemetryExit 按费用规则计费（与人工离场口径一致）→ 发布 parking-exit。管理端可对月卡 create/renew/disable，唯一索引防重复生效月卡。

### 场景 D：物业公告送达

物业发布公告（支持定时/置顶）→ notice-service 落库并经 Redis PubSub 推送 → 业主客户端拉取 /api/notices 并展示 → 点击后 /api/notices/read 回填已读 → 未读计数红点随 notice_read 实时下降。已发布可 recall 撤回。

## 7. 通用设计约束

- 租户隔离：所有查询带 tenant_id 条件；x-tenant-id=0 表示不限（仅内部聚合用）。遗漏 tenant_id 的设备遥测直接丢弃，防越权。
- RBAC：派单/状态流转按角色与归属人约束（维修仅自己单、业主仅自己报单、派单仅管理角色）。
- 失败降级：门禁/设备不可达不阻断主流程（签入照常记录并提示人工兜底）；DB 未初始化显式报错而非静默 0。
- 幂等与防重放：访客核销 Redis SETNX + DB CAS；停车入场 L1 Redis + L3 唯一索引双层幂等；Kafka at-least-once 由幂等键兜底。
- 事件驱动：访客/停车/工单状态变更发布 Kafka 事件（visitor-event / parking-exit / parking-entry / workorder-event），供大屏与安防联动。
