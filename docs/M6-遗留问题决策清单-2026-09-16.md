## F2 · billing 无租户隔离（P0，致命）

- **现状**：`Bill` / `BillingRule` 无 `tenant_id` 字段，全部查询不带租户过滤。
- **影响范围**：多园区账单数据互相可见，跨租户财务信息泄露；与已修复的 leasing F4（统一 `ctxdata.GetTenantId`）形成能力落差。
- **需谁确认**：
  - M2 负责人（物业管理 / 租户主数据定义方）—— 确定 tenant 取值来源；
  - 网关路由负责人 —— 账单接口租户透传与路由；
  - 前端（账单页）—— 租户维度展示与切换。
- **待定决策点**：
  1. `tenant_id` 取值来源：沿用网关 `x-tenant-id`（与 leasing 一致）还是 M2 租户主数据？
  2. 存量数据迁移：历史账单归属哪个租户？是否需要 `default tenant` 兜底？
  3. 迁移方式：停机迁移 vs 在线双写灰度？
  4. 唯一约束：现有 `uk_zone_period(zone_id, period_start, period_end)` 是否升级为含 `tenant_id` 的复合唯一键（防同租户重复出账）？
- **建议方案**：schema 迁移脚本（加 `tenant_id` 列 + 索引，唯一键升级为复合键）+ 接口统一改用 `ctxdata.GetTenantId`（复用 F4 已落地模式）。**本项涉及表结构与网关/前端，需开会定稿后再执行，本轮未改码。**

## P1-9 · billing 缴费流转缺失（P1）

- **现状**：`BillStatusPaid` / 作废常量已定义，但路由仅 `bills` / `generate` / `rule` / `rules`，无任何缴费 / 作废入口。
- **影响范围**：账单永远停留「待缴」，租赁 → 缴费 → 对账闭环断裂。
- **需谁确认**：前端（缴费页 / 作废确认交互）、网关（路由注册）、支付 / 财务对接方。
- **待定决策点**：
  1. 缴费入口：内部记账核销，还是接第三方支付回调？回调幂等如何保证（账单号 / 订单号唯一）？
  2. 作废场景：全额退 / 部分退？作废后是否允许重出账？
  3. 对账口径：缴费成功以哪一方状态为准（支付网关回调 vs 内部）？
- **建议方案**：补 `POST /bills/{id}/pay` 与 `POST /bills/{id}/void` 两个接口；复用 billing 乐观锁（`version`）与已存在的唯一约束做幂等。需与前端 + 网关对齐后再实现。

## P1-11 · billing 零用量不出账（P1，业务决策）

- **现状**：`usage <= 0` 直接拒绝出账（`ErrNoUsage`）。
- **影响范围**：零用量园区无账单，财务台账缺口，口径未定。
- **需谁确认**：财务（计费口径负责人）。
- **待定决策点**：
  1. 零用量是否出 **0 元账单**（保留台账）还是 **跳过**（不出账）？
  2. 固定费用 / 基础管理费是否与用量解耦、仍正常出账？
- **建议方案**：与财务确认后二选一；保留「零用量但含固定费」仍出账的分支，避免一刀切。属纯业务决策，无需代码改动方向争议。

## P1-5 · workorder 处理人校验（P1，依赖 M6 用户表）

- **现状**：`AssigneeID` 已强制非空，但处理人「是否存在 / 在线 / 负荷」无校验（受「独立库禁跨库 JOIN」约束无法查 M6 用户表）。
- **影响范围**：可能派给不存在的处理人，产生僵尸工单。
- **需谁确认**：M6 用户表负责人（用户主数据服务 gRPC 就绪时间）。
- **待定决策点**：
  1. 用户服务 gRPC 契约：入参（`user_id` / `tenant_id`）与返回（存在 / 在线 / 负荷）字段？
  2. 校验失败 UX：直接拒绝派单，还是允许派单但告警？
- **建议方案**：用户表就绪后通过 gRPC 校验；MVP 阶段已防空值（当前可接受）。与 P2-3 / P2-5 合并对接。

## P2-3 · dispatch 候选池维度缺失（P2，依赖 M6 用户表）

- **现状**：指派算法仅按「拓扑距离 + 在手工单数」，缺技能组 / 在线 / 排班维度（MVP 权衡已披露）。
- **影响范围**：可能派给无对应技能或离线的处理人，派单质量受限。
- **需谁确认**：M6 用户表负责人 + 调度业务方。
- **待定决策点**：
  1. 技能组 / 在线状态 / 排班的数据源与 gRPC 契约（与 P1-5 共用用户服务）？
  2. 指派权重：距离 / 负荷 / 技能 / 在线如何加权打分？
- **建议方案**：复用 P1-5 的用户服务 gRPC；候选池打分函数扩展维度，不改动现有 FSM / 乐观锁骨架。

## P2-5 · LoadCandidates zone_code 用 MAX 不准（P2，依赖主数据）

- **现状**：`MAX(assignee_name)` 仅用于取历史名字，非最新语义（注释已披露）。
- **影响范围**：区域名展示可能非最新，属数据准确性问题。
- **需谁确认**：区域 / 处理人主数据负责人。
- **待定决策点**：
  1. `zone_code` / 区域名的权威数据源与查询方式（gRPC vs 直接表）？
  2. 是否随 P1-5 / P2-3 用户服务一并解决？
- **建议方案**：随用户服务就绪替换为真实区域主数据查询，避免继续用聚合函数取语义字段。
