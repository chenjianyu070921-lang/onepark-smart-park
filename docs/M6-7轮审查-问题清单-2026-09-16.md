## 一、致命线上故障（P0，7 项，已修复 6 项）

### F1 ✅ 已修复 | billing 重复出账

**【致命线上故障】** `BillGenerate` 先 `FindBillByPeriod` 检查、后 `InsertBill`，`check-then-insert` 非原子；`bill` 表无任何唯一索引兜底

→ **影响范围**：并发触发同区域同账期重复出账、重复扣费，账务数据污染

→ **整改方案**：新建 `deploy/sql/billing_tables.sql`，bill 表增加 `uk_zone_period(zone_id, period_start, period_end)` 唯一索引，第二次写入被数据库拒绝

### F2 ⏳ 遗留（架构决策）| billing 无租户隔离

**【致命线上故障】** `Bill`/`BillingRule` 无 tenant\_id 字段，全部查询不带租户过滤

→ **影响范围**：多园区账单数据互相可见，跨租户财务信息泄露

→ **整改方案**：schema 迁移（加 tenant\_id 列 + 索引）+ 接口透传改造，**需与 M2 负责人对齐后执行**（涉及表结构、网关路由、前端）

### F3 ✅ 已修复 | alarm 告警丢失窗口

**【致命线上故障】** L1 Redis `SetNX` 置位**先于** DB 落库；DB 写失败后 Kafka 重投，被 L1 幂等拦截（seen=true）→ 告警永久丢失

→ **影响范围**：门禁入侵 / 火灾 / 烟雾等关键告警漏报，告警→派单链路断裂

→ **整改方案**：`Deduper` 增加 `Delete`；`HandleDeviceEvent` 在 DB 落库失败时**回滚 Redis 幂等键**，重投可重新处理

### F4 ✅ 已修复 | leasing 跨租户越权

**【致命线上故障】** ContractCreate 信任请求体 tenant\_id（可伪造）；Detail/Update/Expiring 无任何租户条件（凭 id 即可读写任意租户合同）；List/Occupancy 用客户端自报的 form 参数 tenant\_id（可传任意值穿透）

→ **影响范围**：租户 A 可读 / 改 / 续租 / 终止租户 B 的合同，严重越权

→ **整改方案**：6 个 logic 文件统一改用 `ctxdata.GetTenantId`（网关注入的 x-tenant-id）；Create 拒绝 tenant=0；Detail/Update/Expiring 查询强制加 tenant 条件；List/Occupancy 不信任 req.TenantId

### F5 ✅ 已修复 | dashboard WS 无鉴权

**【致命线上故障】** `CheckOrigin: true` + `TODO(M6) 校验 token` 未关闭；快照固定 `TenantId: 0`

→ **影响范围**：任何人可连 WebSocket 获取大屏聚合数据（数据裸奔）；多租户大屏串数据

→ **整改方案**：config 增加 `JwtSecret`（环境变量 \${AUTH\_SECRET}，禁止硬编码）；ws.go 校验 `?token=`（签名 + 过期 + 必须 access 类型）；secret 未配置时拒绝服务

### F6 ✅ 已修复 | leasing 出账失败静默吞掉

**【致命线上故障】** `billauto` 建单失败时，非重复错误（连接断开 / 字段超长等）也计入 `Skipped` 并 continue，无任何上报

→ **影响范围**：批量出账部分丢失无感知，财务对账缺数

→ **整改方案**：`BillAutoResp` 增加 `Failed` 字段；真失败计数，末尾 `Failed>0` 时返回 error 提示人工复核

### F7 ✅ 已修复 | billing 表 DDL 完全缺失

**【致命线上故障】** `billing_rule`/`bill` 表在 deploy/sql 下**无任何建表脚本**

→ **影响范围**：部署即缺表，服务启动后所有查询必然失败

→ **整改方案**：新建 `deploy/sql/billing_tables.sql`（含建库、两表、唯一索引、索引）

## 二、潜在隐患（P1，11 项，已修复 4 项）

### P1-1 ⏳ 遗留（排期）| 消费端无死信 / 重试退避上限

**【潜在隐患】** dispatch/alarm 消费端 handler 返回 error 即不提交位移（at-least-once），但无重试上限、无死信 topic、无 lag 告警；坏消息或 DB 长期故障时分区永久阻塞

→ **影响范围**：告警 / 工单消息积压，事件处理停滞，故障难发现

→ **整改方案**：死信 topic + 重试退避 + 分区 lag 监控告警

### P1-2 ⏳ 遗留（排期）| 消息结构未下沉 common

**【潜在隐患】** dispatch 的 `AlarmEvent` 与 event-dispatcher 的 `Message` 由 M1 单方定义、两处复制，注释自曝 "后续应下沉 common 包"

→ **影响范围**：字段漂移即消息解析失败，跨模块契约脆弱

→ **整改方案**：抽取 `common/message` 共享结构体，双端引用同一定义

### P1-3 ✅ 已修复 | event-dispatcher 告警投递失败静默

**【潜在隐患】** 主投递 telemetry 成功后，额外投递 alarm topic 失败**仅记日志**返回 nil

→ **影响范围**：告警消息静默丢失，派单源头断链

→ **整改方案**：alarm topic 投递失败返回 error 提升可见性（正式方案 = P2 本地消息表 / 死信）

### P1-4 ✅ 已修复 | workorder 单号碰撞崩溃

**【潜在隐患】** `genOrderNo` 4 位随机数，同秒并发碰撞命中 `uk_order_no` 唯一索引 → 整事务失败

→ **影响范围**：高并发建单偶发失败

→ **整改方案**：建单循环 5 次，捕获 1062 唯一冲突后换号重试

### P1-5 ⏳ 部分缓解 | workorder assign 不校验处理人存在 / 负荷

**【潜在隐患】** AssigneeID 已强制非空，但处理人 "是否存在 / 在线 / 负荷" 无校验（受 "独立库禁跨库" 约束无法查 M6 用户表）

→ **影响范围**：可能派给不存在的处理人（僵尸工单）

→ **整改方案**：M6 用户表就绪后通过 gRPC 校验；MVP 阶段已防空值

### P1-6 ✅ 已修复 | leasing 审计流水分离事务

**【潜在隐患】** 乐观锁更新与审计流水分离提交，流水失败仅记日志 → 状态流转无审计

→ **影响范围**：合同状态变更审计断档，追溯困难

→ **整改方案**：更新 + 流水同一 `Transaction`，冲突用哨兵错误判定

### P1-7 ⏳ 遗留（技术债）| dashboard 缓存无 singleflight / WS 多实例不广播

**【潜在隐患】** 30s 缓存无 singleflight（击穿）；wshub 内存广播不跨实例（多实例部署大屏漏推，已登记）

→ **影响范围**：高并发缓存击穿；多节点部署推送不完整

→ **整改方案**：singleflight + Redis Pub/Sub 扇出

### P1-8 ⏳ 遗留（排期）| 深翻页 + 缺复合索引

**【潜在隐患】** workorder/billing 列表用 offset 深翻页；缺 (tenant\_id,status,assignee\_id)、(status,period) 等复合索引

→ **影响范围**：大数据量分页查询退化

→ **整改方案**：游标分页（id < lastId）+ 复合索引

### P1-9 ⏳ 遗留（排期）| billing 缴费流转缺失

**【潜在隐患】** `BillStatusPaid/作废` 有常量定义，但路由仅 4 个（bills/generate/rule/rules），**无任何缴费 / 作废入口**

→ **影响范围**：账单永远停留 "待缴"，租赁 - 缴费 - 对账闭环断裂

→ **整改方案**：补缴费回调 / 作废接口（需与前端 + 网关对齐）

### P1-10 ✅ 已修复 | 大屏告警卡片恒降级

**【潜在隐患】** dashboard 的 Alarm/Device/Energy provider 均为占位（notready.go 返回 ErrSourceNotReady），但 M3 `GetActiveAlarms` gRPC 契约早已存在且支持租户过滤

→ **影响范围**：大屏 4 路数据仅工单 1 路真实，告警卡片恒 null+degraded，验收不达标

→ **整改方案**：接入 alarm gRPC 真实实现（config/yaml/provider/svc/overview/ 测试共 8 处），并补租户透传

### P1-11 ⏳ 遗留（业务决策）| billing 零用量不出账

**【潜在隐患】** `usage <= 0` 直接拒绝出账

→ **影响范围**：零用量园区无账单，口径未定

→ **整改方案**：与财务确认：0 元账单 vs 跳过（业务决策）

## 三、代码优化建议（P2，5 项，已修复 1 项）

`MAX(assignee_name)` 仅用于取历史名字，非最新语义（注释已披露）→ 后续按真实数据源替换
