### 大模型链路（用假 OpenAI 服务验证）

在 127.0.0.1:9099 起了个假的 `/v1/chat/completions`，把 yaml 的 BaseURL 指过去，验证"接上真模型"这条路：

- 请求格式正确：路径 `/chat/completions`、`Authorization: Bearer xxx`、model 字段、system+user 两条消息、temperature=0
- 返回正常时，`llmEnabled=true`、`llmModel=fake-model`，建议的 reason 变成模型返回的文本
- 假模型收到的提示词数字正确（如"当天用量: 220.00 度 / 历史基线: 100.00 度 / 偏离幅度: 120%"）
- 关掉大模型后，reason 自动回退成规则原文，结论一个不少

## 三、智能体重点检查

三层设计是成立的，实测下来最关键的一点得到验证：**大模型挂掉或没配 key，系统照常出报告，只是少了润色**。

- 层1 规则引擎：纯函数，17 个单测，确定性
- 层2 大模型：只翻译不判定（开关前后 findings 完全一致，已实测）
- 层3 兜底：mock 用规则算出的数字拼人话，不是"服务不可用"这种废话

数据口径与 M4 其他接口一致：
- 日用量 = 先按"每台设备每天"算 MAX-MIN 再求和（不是全表 MAX-MIN，会把表计基数差算进去）
- 分时用量用差分法（每个小时桶取最后读数，本桶 - 上一桶），避免跨小时增量丢失——这个坑之前在峰谷计费踩过，症状是账单少算钱

## 四、本次修掉的缺陷

| # | 问题 | 原因 | 修法 |
| --- | --- | --- | --- |
| 1 | `agent_run.zone_count` 永远 0，`find_count` 记的是区域数 | `finishRun` 把 `len(zones)` 传给了 findCount 参数，且 zone_count 没进 UPDATE 字段 | 两个数各归各位，zone_count 一并写库 |
| 2 | `llm_enabled` 永远 0、`llm_model` 永远空 | 用 `defer` 改内存里的 `run` 副本，Create 之后改副本不会落库 | 改为在 finishRun 时由调用方传入写库 |
| 3 | `llm_explain` 的工具调用 run_id 写死 0 | 调用时直接传了字面量 0 | 传 run.ID，轨迹归到本次巡检 |
| 4 | 夜间空转发给大模型的"当天用量"是 0 度 | 证据里键名叫 `total` 不是 `actual`，取值取空了；读数回退/数据缺失还硬塞 "0.00 度 / 偏离 0%" | `toExplainRequest` 做键名兜底；`BuildPrompt` 没数字就不输出数字行 |
| 5 | `EncodeEvidence` 序列化失败返回空串 | 空串会被 MySQL JSON 列拒绝，整条建议存不进去 | 改成返回 `{}` |

另外补了 `internal/llm/openai_test.go`（用 httptest 起假服务），把之前从没被执行过的 OpenAIClient 代码路径覆盖上：请求格式、401、body 里的 error 字段、choices 为空。

## 五、已知问题（本次未改，需要组内一起定）

1. **业务错误统一返回 HTTP 500。** `common/response.Fail` 用 `CodeError.HttpStatus()`，而 M4 的错误码都是 `M4-E-xxxx`，级别 E 映射到 500，所以"参数填错""区域没数据"这类也返回 500（响应体里的 code 是对的）。这是全项目约定，改 `common/` 会波及别的小组，建议组内统一决定是改成 400 还是统一 200+code。
2. **billing_rule 表里 B栋 有两条一模一样的启用规则**（id 3 和 4）。自动出账时匹配哪条不明确，属于数据问题，建议删掉一条或加"同区域只允许一条启用规则"的校验。
3. **接口 55 未做真实 Kafka 联调**（本次 Docker 没起）。消费者启动和消息解析都有单测保障，但真收发需要起 Kafka 后再验一遍。
4. **智能体路由还没挂到 gateway**，现在是直连 8064；审批转工单仍是占位（M6 的 workorder-service 还是空壳）。
