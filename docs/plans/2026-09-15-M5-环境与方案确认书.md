> **处置结果**：不使用本地 Kafka 容器，改用组长提供的共享 broker。实测结果见 §1.5。

已验证可用的替代（镜像加速器 `https://docker.m.daocloud.io/` 下 HEAD 请求均返回正常 manifest）：

| 替代方案 | 可用性 | 改动量 | 说明 |
|---|---|---|---|
| `bitnamilegacy/kafka:3.7` | ✅ AVAILABLE | **仅改 1 行镜像名** | 环境变量、卷路径、启动脚本与现配置完全一致；缺点：归档仓库，不再更新 |
| `apache/kafka:3.7.2` | ✅ AVAILABLE | 改镜像名 + 环境变量命名 + 卷路径 | Apache 官方维护，长期更稳；KRaft 配置项名字不同 |

**建议**：先用 `bitnamilegacy/kafka:3.7` 打通联调（零配置改动），同时把切换 `apache/kafka` 记为技术债。**此项改动影响全部 6 个模块的 compose 文件，需组长拍板后统一改。**

#### 阻塞项 2：Docker Desktop 需手动确认启动

本机 Docker Desktop 冷启动后需在图形界面完成初始化（可能涉及登录/接受条款），脚本无法完全代劳。**开发者每次开工前需确认鲸鱼图标变绿**，否则 `docker compose` 全部失败。

#### 非阻塞说明

镜像加速器已配置为 `https://docker.m.daocloud.io/`。经实测，**无法直连 Docker Hub**（`registry-1.docker.io` 连接超时），因此所有镜像都必须走加速器或本地缓存。这解释了为什么 MySQL / Redis 能秒起（本地已有镜像），而 Kafka 需要拉取。

### 1.5 共享 Kafka（组长提供）—— 已实测连通，但发现重大情况

组长指示改用其提供的 broker，不再启动本地 Kafka 容器。**已做 TCP + 协议级双重验证：**

| 检查项 | 实测结果 |
|---|---|
| TCP 可达性 | ✅ `115.191.16.159:9092` 连接成功 |
| 协议 / 认证 | ⚠️ **PLAINTEXT，无任何认证**（无需账号密码即可连接） |
| Controller | `115.191.16.159:9092` |
| 可见 topic 数 | **24 个** |

**⚠️ 重大发现：该 broker 上的 topic 与 OnePark 完全无关。**

```
__consumer_offsets (partitions=50)
order.created / order.paid / order.refunded / order.canceled / order.status.changed
orderclient.created / order-event
dispatch.new / dispatch.new.dlq / dispatch.result / dispatch.result.dlq
location-report / location-report.dlq
video_audit / video_ud / dynamics_ud / note_audit_pending / doc-embedding
test1111
```

**24 个 topic 中没有任何一个属于 OnePark —— `onepark.device.event` 与 `onepark.alarm.event` 都不存在。**

这批 topic（`order.*`、`location-report`、`dispatch.new`、`video_audit`）看起来属于**另一套业务系统**（订单/网约车类），加上还有 `test1111` 这种临时 topic，说明这是**多项目共用的共享 broker**。

**由此推出 3 个必须处理的问题：**

| # | 问题 | 处置建议 |
|---|---|---|
| 1 | OnePark 的 2 个 topic **不存在** | 需明确：谁创建？组长预建，还是 M5 / M1 / M3 各自建？→ 见决策点 10 |
| 2 | **PLAINTEXT + 公网 IP + 零认证** | 任何能访问该 IP 的人都能读走全部消息、写入任意数据，而里面已有 `order.*` 这类疑似业务数据。→ **建议向组长反馈**：至少加防火墙白名单，最好启用 SASL |
| 3 | **多项目共用同一 broker** | topic 必须带项目前缀（`onepark.` 是对的）；**消费组必须带项目 + 人 + 环境**，否则会和其它项目/队友互相提交 offset，把别人的消息"吃掉" |

**M5 使用纪律（必须遵守）：**

```
☐ 消费组命名：m5-{service}-{env}-{owner}，如 m5-dispatch-dev-hjy
☐ 只读写 onepark.* 前缀的 topic，禁止碰其它项目的 topic
☐ Kafka 消费者做成可开关且默认关闭 —— 避免在共享 broker 上意外消费并自动建单
☐ 禁止在该共享 broker 上做破坏性操作（删 topic / 改分区数 / 重置 offset）
☐ 如需自建 topic，先与组长确认并统一命名：onepark.<domain>.<event>
```

**附带发现**：`goproxy.cn` 与公网 Go module 代理**可达**（本次编译 `kafka-go` 及其依赖时实测成功）。此前"网络不通"的结论**仅针对 Docker Hub / 容器镜像仓库**，Go 依赖走代理是正常的。

## 3. 技术方案确认

### 3.1 方案一：`sync.WaitGroup` 4 路并发 gRPC 聚合（接口 #69 / #70 / #71 / #72）

#### 3.1.1 业务语义澄清（重要）

这里有一个必须先说清楚的点：**4 个方法的命名是 `List*`，但业务上要的是"统计量"，不是"列表"。**

| 方法 | 字面含义 | 实际业务需求（按清单） | 结论 |
|---|---|---|---|
| `ListDevices` | 设备列表 | #69「设备统计」、#72「在线/离线统计」 | 要**计数** |
| `ListWorkOrders` | 工单列表 | #23「查询**待处理工单数**（大屏聚合）」 | 要**计数** |
| `GetActiveAlarms` | 活跃告警 | #43「查询活跃告警**数**」、#70「按 severity 分组统计」 | 要**分组计数** |
| `GetDailyReport` | 日报 | #54「今日总能耗」 | 要**聚合值** |

→ **风险**：如果按字面实现成"返回列表"，4 路聚合会把 M1 的全部设备、M2 的全部工单**拉到 M5 内存里再算 count**，数据量大时必然拖垮大屏。

→ **建议**：RPC 名称沿用清单（避免与组长已批准的契约冲突），但**message 结构定义为统计响应体**，并在文档中显式标注"命名与语义不符，消费方按统计语义实现"。若组长同意，更准的名字是 `GetDeviceStat` / `CountWorkOrders`。

```proto
  double total_water_ton = 2;
  double total_gas_m3    = 3;
  repeated ZoneEnergy zones = 4;
}

service EnergyService {
  rpc GetDailyReport(DailyReportRequest) returns (DailyReportResponse);
}
```

> 时间戳统一用 `int64`（Unix 毫秒），与 `proto/common/common.proto` 的既有风格保持一致。

#### 3.1.3 并发聚合实现方案

**架构：端口 / 适配器（依赖倒置）**

上游未就绪是既定事实，因此**不能**在业务逻辑里直接写死 `zrpc` 客户端。在 `dashboard-service` 内定义 4 个 Provider 端口：

```go
// internal/provider/provider.go
type DeviceProvider interface {
    Stat(ctx context.Context) (DeviceStat, error)
}
type WorkorderProvider interface {
    Stat(ctx context.Context) (WorkorderStat, error)
}
type AlarmProvider interface {
    Stat(ctx context.Context) (AlarmStat, error)
}
type EnergyProvider interface {
    Daily(ctx context.Context, date string) (EnergyReport, error)
}
```

每个端口两份实现：

| 实现 | 文件 | 何时使用 | 行为 |
|---|---|---|---|
| `real` | `real_device.go` 等 | `Dependency.Mock = false` | 走 `zrpc` 客户端 |
| `mock` | `mock_device.go` 等 | `Dependency.Mock = true` | 返回**会波动**的假数据 + 可控延迟 |

**mock 必须"会动"**，否则 `#69` 的并发、超时、降级三个技术点全部无法验证：

- 数值随机波动 → 能看出大屏在刷新
- 支持配置 `mock.delay_ms`（如 300）→ 能压出超时路径
- 支持配置 `mock.fail`（按 provider 名指定）→ 能验证降级路径

`svc.ServiceContext` 依据配置注入对应实现，业务 `logic` 只依赖接口，**上游上线后改配置即可，代码零改动**。

**并发骨架（关键：等齐，不等同于"一失败全失败"）**

```go
const (
    overviewTimeout = 800 * time.Millisecond  // 总预算
    providerTimeout = 600 * time.Millisecond  // 单路预算（给聚合与序列化留 200ms）
)

// 结果槽：每路 goroutine 只写自己的槽位，天然无竞态
type overviewResult struct {
    device    DeviceStat
    workorder WorkorderStat
    alarm     AlarmStat
    energy    EnergyReport
    failed    []string          // 降级维度清单
    costMs    map[string]int64  // 各路耗时，用于定位瓶颈
}
```

执行步骤：

1. 外层 `ctx, cancel := context.WithTimeout(r.Context(), overviewTimeout)`，`defer cancel()`
2. 用 `errgroup.Group`（**注意：不是直接拿 `errgroup.WithContext` 的 ctx 去取消兄弟任务**）派发 4 个任务
3. **每个 goroutine 内部必须吞掉错误**：失败时走降级、写 `failed`、记录耗时，**`return nil`**
4. `g.Wait()` 后聚合结果 + 写缓存 + 返回

> **最容易踩的坑**：如果 goroutine 里 `return err`，`errgroup.WithContext` 会 cancel 派生的 ctx，**另外 3 路会一起失败**，"部分降级"就地变成了"整体失败"。清单要求"errgroup + context 超时 + 服务降级"，三者能同时满足，但前提是**错误必须在 goroutine 内部被吸收**，`errgroup` 只负责"等齐"和收集致命错误。

**单路超时用双层预算**：总预算 800ms 保证大屏体验；单路 600ms 保证慢的那个（通常是 TDengine 聚合）不拖垮整体。

**耗时埋点**：`costMs` 随响应返回，既能给前端展示，也是最直接的排障依据。

### 3.2 方案二：`errgroup` + `context` 超时 + 服务降级（返回缓存）

#### 3.2.1 三级降级策略

| 级别 | 触发条件 | 处理 | 前端表现 |
|---|---|---|---|
| **L1 单维度降级** | 某一路失败/超时，且该维度有兜底缓存 | 用兜底缓存值填充，`failed` 中记录该维度 | 该卡片数字正常，角标"数据延迟" |
| **L2 无兜底缓存** | 某一路失败且从未成功过（首次启动/缓存被清） | 该维度 `available=false`，**不填 0** | 该卡片显示 `—` + 灰色 |
| **L3 整体降级** | 4 路全部失败 | 返回整体兜底缓存，带 `stale_at` | 整屏显示，顶部横幅"数据更新于 xx:xx" |

> **关键设计约束：降级绝不能用 `0` 冒充真实值。** 大屏上"今日能耗 0 kWh"和"能耗数据不可用"是**完全不同的业务信号**——前者会被误读成"园区停电了"。所有降级维度必须带显式标记。

#### 3.2.2 响应结构（带数据新鲜度元信息）

```json
{
  "device":    { "available": true,  "total": 1263, "online": 1240, "offline": 23 },
  "workorder": { "available": true,  "pending": 7, "processing": 12, "pending_accept": 3 },
  "alarm":     { "available": true,  "total": 3, "critical": 1, "major": 2, "minor": 0 },
  "energy":    { "available": false, "total_kwh": 0 },
  "degraded":  ["energy"],
  "stale_at":  null,
  "cost_ms":   { "device": 42, "workorder": 88, "alarm": 55, "energy": 600 },
  "elapsed_ms": 612
}
```

`degraded` 为空数组 = 全绿；非空 = 前端展示降级角标。**这个字段是大屏"性能"与"可信度"的分界线**，必须实现。

#### 3.2.3 超时预算与错误分类

| 错误类型 | 判定 | 处置 |
|---|---|---|
| `context.DeadlineExceeded` | 单路超时 | 降级（L1/L2） |
| gRPC `Unavailable` / `DeadlineExceeded` | 下游不可用 | 降级 |
| gRPC `InvalidArgument` | M5 传参错误 | **不降级**，记录 ERROR 日志（这类错误降级会掩盖真实 bug） |
| gRPC `PermissionDenied` | 鉴权失败 | **不降级**，向上抛（说明是系统性问题） |

> 区分"可降级"与"不可降级"错误，是避免"用降级掩盖 bug"的关键。全部错误一律降级，会导致契约错误被长期隐藏。

### 3.3 方案三：Redis 聚合缓存（5s TTL）+ gorilla/websocket 大屏推送（接口 #73）

#### 3.3.1 缓存设计：改"物理过期"为"逻辑过期"

**朴素做法的问题**：清单要求 5s TTL。若直接 `SET key val EX 5`，5 秒后键就**被删了**。此时若正好上游故障，降级要"返回缓存"——**缓存已经没了**。这会导致"降级策略在最需要它的时候失效"。

**推荐方案：逻辑过期（logical expiration）**

```
KEY:   m5:ov:seg:{device|workorder|alarm|energy}
VALUE: {"data":{...}, "saved_at":1789000000000, "expire_at":1789000005000}

读取流程：
  1. GET key
  2. 命中 且 now < expire_at  → 直接返回（新鲜，等价于 5s TTL）
  3. 命中 但 now >= expire_at → 返回旧值，同时异步触发单飞刷新（stale-while-revalidate）
  4. 未命中                  → 同步刷新，singleflight 合并并发请求
  5. 刷新失败                → 返回旧值 + 该维度标记 degraded
```

**这个设计一举解决三个问题**：

| 问题 | 逻辑过期如何解决 |
|---|---|
| 降级无数据可用 | 值不会因 TTL 到期被删除，永远有"上一版"可退回 |
| 缓存击穿 | 5s 到期的瞬间高并发请求，由 `singleflight` 合并为 1 次真实刷新 |
| 雪崩 | 各维度独立键、独立刷新，不会同时失效 |

键设计（分维度而非整体）：

```
m5:ov:seg:device       ← 分维度缓存（5s 逻辑过期，1h 物理 TTL 兜底清理）
m5:ov:seg:workorder
m5:ov:seg:alarm
m5:ov:seg:energy
m5:ov:overview         ← 整体缓存（降级 L3 用）
```

> **为什么必须分维度？** 如果只缓存整体 JSON，energy 单维度降级时会连带污染其他三个正常维度的数据新鲜度，也会让"只重算 energy"变成"重算全部"。

并发控制：`go-zero` 已内置 `core/syncx` 的单飞（`singleflight.go`）与 `timeoutlimit.go`，**无需引入新依赖**。

`stale_at` 语义：整体缓存复用时填**该缓存的实际生成时间**，前端据此显示"数据更新于 10:00:03"。

#### 3.3.2 WebSocket 推送方案

**注册方式**：必须用 go-zero 的**原生路由**注册，不能用 `httpx` 包装的 handler（`httpx` 会自行写 JSON 响应，与 `Upgrade` 握手冲突）：

```go
server.AddRoute(rest.Route{
    Method:  http.MethodGet,
    Path:    "/ws/dashboard",
    Handler: dashboardWsHandler(svcCtx),
})
```

**连接管理**：

| 关注点 | 方案 |
|---|---|
| 连接池 | `sync.RWMutex` + `map[*wsClient]struct{}`（或 `go-zero/core/collection` 的安全容器） |
| 写并发 | **gorilla/websocket 不允许并发写**，每个连接一个 buffered `send chan []byte`，**只由一个 writer goroutine 写** |
| 慢客户端 | `send` 缓冲（建议 64）写满 → 丢弃该连接并关闭，防止一个慢客户端拖死广播协程 |
| 心跳 | 服务端 30s 发 `PingMessage`，客户端回 `Pong`；`SetReadDeadline(60s)`、`SetWriteDeadline(10s)` |
| 关闭 | 用 `done chan struct{}` 通知读写协程退出，`defer` 双向清理（连接池 + 关闭底层 conn） |

**推送策略（清单要求"定时全量 + 事件增量"）**：

| 来源 | 频率 | 数据 |
|---|---|---|
| 定时全量 | 每 5s（与缓存逻辑过期对齐） | `#69 overview` 聚合结果 |
| 事件增量 | 实时（Kafka 触发） | 设备上下线、告警新增 |

> **5s 全量推送 + 缓存 5s 逻辑过期**是同一个节奏，二者共用同一份聚合结果，不会产生额外查询压力。这是这套设计能扛住大屏的关键。

**必须提前处理的三个坑**：

1. **鉴权**：浏览器 WebSocket API **不允许自定义 `Authorization` 头**。必须改用 `?token=xxx` 查询参数或 `Sec-WebSocket-Protocol` 子协议。→ **token 出现在 URL 里会被 access log 记录，必须做日志脱敏。**
2. **多实例扇出**：若 `dashboard-service` 部署多实例，WS 连接分散在不同实例；Kafka 消费组同一分区只会被一个实例消费 → **其他实例上的大屏收不到增量**。
   - 开发期：单实例，无影响
   - 联调/演示期：需 Redis Pub/Sub 扇出，或让每个实例用独立 consumer group
   - → **需拍板：先单实例交付，还是直接做扇出**
3. **goroutine 泄漏**：连接关闭必须确保读写协程、ticker 全部退出。建议 `#73` 上线前用 `runtime.NumGoroutine()` 做一次压测前后的对比验证。

### 3.4 方案四：合同状态机 + 定时任务自动生成租金账单（接口 #63 ~ #68）

#### 3.4.1 状态机设计

组长给出的链路是 `待生效 → 生效中 → 已到期 → 已终止`。这里有一处**必须在动手前澄清的语义问题**：

> 「已到期」是**自然到期**（租期到了），「已终止」是**提前解约**（租期没到就退租）。把「已到期 → 已终止」串成必经路径，意味着**任何自然到期的合同，都要再经过一次人工操作才变成"已终止"**。

**推荐状态机（4 态 + 6 条合法转移）**：

| # | from | to | 触发 | 说明 |
|---|---|---|---|---|
| 1 | `PENDING` 待生效 | `ACTIVE` 生效中 | 到起租日（cron 自动）或手动生效 | |
| 2 | `PENDING` | `TERMINATED` 已终止 | 签约后取消 | 未生效即取消 |
| 3 | `ACTIVE` | `EXPIRED` 已到期 | 到终止日（cron 自动） | 自然到期 |
| 4 | `ACTIVE` | `TERMINATED` | 提前退租 | 收违约金/清退 |
| 5 | `EXPIRED` | `TERMINATED` | 到期后清退归档 | 组长要求的这条，**保留** |
| 6 | `EXPIRED` | `ACTIVE` | — | ❌ **禁止**，续签应生成新合同 |
| 7 | `TERMINATED` | 任意 | — | ❌ **禁止**，终态不可逆 |

**为什么不允许多状态直接"复活"**：终态可逆会让历史租金账单失去可追溯性——已终止合同的账单已经生成、可能已收款，改状态会让账实不符。

**续签的语义（决策点）**：

- 推荐 **续签 = 新合同 + 原合同置 `renewed_by_contract_id`**。理由：续签通常伴随**租金调整**，一份合同应绑定一个条款快照；且历史账单要能追溯到当时的租金。
- 若组长要求"延长原合同"，则必须新增 `contract_rate_history` 表记录租金变更，复杂度反而更高。

**实现方式**：用 `map[Status][]Status` 显式声明合法转移表，所有状态变更统一走一个 `transition(from, to)` 门禁函数。禁止在业务代码里散写 `if status == xxx`。

**审计**：`contract_status_log(id, contract_id, from_status, to_status, reason, operator_id, created_at)`。状态机是"防止乱改"，审计表是"改过之后能查"——两者缺一不可。

**自动流转**：cron 每日 `00:10` 执行两条批量更新（生效 / 到期）。批量更新必须幂等（`WHERE status = 旧状态`），天然幂等。

#### 3.4.2 定时任务自动生成租金账单（#68）

**执行流程**：

```
每月 1 日 02:00 触发
  → 抢分布式锁（Redis SET NX）
  → 查询所有 status=ACTIVE 的合同（分批，每批 200）
  → 逐条：按账期口径算金额 → 写账单（唯一索引兜底幂等）
  → 失败的落 bill_generate_failure 表，可重跑
  → 释放锁（Lua 比对持有者）
```

**幂等的根基是唯一索引，不是锁**：

```sql
UNIQUE KEY uk_contract_period (contract_id, billing_period)
```

分布式锁只解决"多实例重复跑"的**性能与日志噪音**问题；即使锁失效（锁过期、误删），唯一索引也能保证**不会生成重复账单**。把幂等寄托在锁上是很常见的错误——锁会丢。

**分布式锁的正确实现（两个经典坑）**：

```bash
# 加锁：NX + PX + 唯一值（值必须唯一，不能写死）
SET m5:lease:bill:{period}:lock {uuid} NX PX 600000

# 释放：必须用 Lua 比对 uuid 再删，不能直接 DEL
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

| 坑 | 后果 | 规避 |
|---|---|---|
| 释放时不校验持有者 | A 的任务超时后锁自动过期，B 拿到锁；A 执行完 `DEL` 把 **B 的锁删了**，C 又能拿到锁 → 并发执行 | Lua 比对 uuid |
| 锁 TTL 短于任务耗时 | 任务还没跑完锁就过期 → 重复执行 | TTL 需大于预估最长耗时（建议 600s）+ 分批处理缩短单次耗时 |

**金额精度**：一律 `shopspring/decimal`（本地缓存已有 v1.4.0），数据库用 `DECIMAL(12,2)`。**禁止用 `float64`** —— 浮点累加会产生 `0.1 + 0.2 = 0.30000000000000004` 这类误差，在财务场景是不可接受的。

**账期口径（决策点，需财务/组长确认）**：

| 口径 | 说明 | 优劣 |
|---|---|---|
| 自然月（推荐） | 每月 1 日出上月/本月账单，`billing_period = '2026-09'` | 财务对账简单、与物业账期一致 |
| 合同周年 | 按起租日的"月对日"生成 | 与合同严格对应，但同月会有多批账单，对账复杂 |

**不足整月如何计价（决策点）**：首月/末月不满整月时，按天折算 `月租金 ÷ 当月自然天数 × 实际天数`，还是首月全额？→ 必须确认，否则会出脏数据。

### 3.5 方案五：人员指派算法（接口 #74 / #77）

#### 3.5.1 前置发现：契约缺字段，会直接卡死算法

`proto/common/common.proto` 现有定义：

```proto
message AlarmEvent {
  string alarm_id  = 1;
  string device_id = 2;
  int32  severity  = 3;
  string content   = 4;
  int64  timestamp = 5;
}
```

**缺少 `zone_code`（区域编码）。** 而"就近分配"必须先知道工单在哪个区域。`device_id` 无法直接推出位置（需要反查设备表，但 M5 不允许跨库查询 M1 的设备库）。

→ **必须补齐**：建议 `AlarmEvent` 增加 `string zone_code = 6;` 与 `string alarm_type = 7;`（用于技能匹配）。

→ 这是**跨模块契约变更**（`common.proto` 被 M1/M3/M5 共用），需组长协调后统一改。

#### 3.5.2 指派算法：三档过滤 + 加权打分

**第一步：硬过滤（不满足直接排除）**

| 过滤条件 | 说明 |
|---|---|
| 在岗 | `status = 在职` |
| 值班 | 当前时间落在该员工的排班时段内（`duty_roster`） |
| 技能匹配 | 具备该工单类型要求的技能（如"火警"需消防资质） |

**第二步：加权打分排序**

```
score = w1 × 距离分 + w2 × 负荷分 + w3 × 级别适配分

距离分      = 1 - min(区域距离 / 最大区域距离, 1)          → 同层 = 1
负荷分      = 1 - min(进行中工单数 / 最大并发数, 1)         → 空闲 = 1
级别适配分  = 1 - |员工职级 - 告警级别要求| / 最大级别差    → 完全匹配 = 1

默认权重：距离 0.5 / 负荷 0.3 / 级别 0.2（配置化，便于调参）
```

**第三步：兜底**

无任何候选人（所有人都被硬过滤掉）→ 指派给**值班组长** + 工单标记 `manual_required = true`，并在大屏红点提示。**绝不能因为"没人可派"就静默不建单** —— 那等于把火警吞掉了。

#### 3.5.3 "就近"距离怎么算（无 GIS 坐标时的降级方案）

M5 库里没有经纬度。推荐**用区域编码的拓扑关系代替物理距离**：

| 关系 | 距离值 | 判定规则 |
|---|---|---|
| 同楼层 | 0 | `zone_code` 完全相同（如 `A-3F-01` vs `A-3F-08`） |
| 同楼栋不同层 | 1 | `zone_code` 前两段相同（`A-3F` vs `A-5F`） |
| 同园区不同楼栋 | 2 | 仅第一段相同（`A-3F` vs `B-2F`） |
| 跨园区 | 3 | 第一段不同 |

实现为 `zoneDistance(a, b string) int`，纯字符串前缀比较，零依赖、可单测。**这比硬编经纬度更贴合园区场景**，也避免了维护坐标数据的成本。

#### 3.5.4 幂等与并发（#74 自动建单）

Kafka **至少一次**投递语义意味着同一条告警可能被消费多次。防重复建单：

1. **建单前查重**，用 `alarm_id` 作为幂等键
2. 数据库唯一索引兜底：`UNIQUE KEY uk_alarm_id (alarm_id)`

> **顺序很重要**：幂等必须在**建单前**生效。如果先建单再查重，重复消息会先产生脏数据。

#### 3.5.5 超时未接单的升级（建议纳入，非清单要求）

`dispatch` 表加 `assign_expire_at`；cron 每分钟扫描超时未接单的工单 → 重新指派（升级到上级/值班组长）。

> 清单未明确要求，但对"指挥调度"这个业务场景是**必要的闭环**（否则工单派出去没人接就永远挂着）。**建议纳入，请组长确认。**

#### 3.6.1 服务发现：go-zero 原生不支持 Nacos

`README.md` 技术栈写的是「注册配置：Nacos 2」。但实测 `go-zero v1.10.3` 的 `zrpc.RpcClientConf` 字段如下：

```go

    Etcd          discov.EtcdConf `json:",optional,inherit"`  // etcd 服务发现
    Endpoints     []string        `json:",optional"`           // 直连地址
```

- `github.com/zeromicro/zero-contrib`（含 nacos resolver）

#### 4.5.4 环境坑 1：宿主机 6379 被原生 Redis 顶掉（**全队都会踩**）

**现象**：服务连 Redis 报 `ERR Client sent AUTH, but no password is set`，但 `docker exec onepark-redis redis-cli CONFIG GET requirepass` 显示的却是 `onepark123` —— 两边矛盾，极易误判。

**根因**：宿主机上存在一个**原生 Windows `redis-server` 进程占用 6379**，把 Docker 容器 `onepark-redis` 发布的 `0.0.0.0:6379` **顶掉了**。服务连上的是那个**无密码的原生 Redis**，而非团队 compose 起的容器。

**处置**：`deploy/.env` 中 `REDIS_PORT` 改为 **6380**（不动用户其他项目的 Redis），重建容器后映射为 `0.0.0.0:6380->6379`，M5 三个 yaml 的 `Redis.Addr` 指向 `127.0.0.1:6380`。

> ⚠️ **建议同步全队**：其他同学的机器若也装有本地 Redis，同样会连到错误的实例上。排查手法：`docker exec <容器> redis-cli -a <密码> ping` 与"服务直连端口"结果不一致，即端口被顶。

#### 4.5.5 环境坑 2：go-zero 的 `${VAR}` 占位符在本地启动路径下拿不到环境变量（**M2 也已踩**）

**根因**：`go-zero v1.10.3` 的 `core/conf/config.go:63` 是 `loader([]byte(os.ExpandEnv(string(content))), v)` —— 它在解析前对整份配置做 `os.ExpandEnv`，**变量未设置时会被替换成空字符串**（而非保留占位符）。实测在本机启动路径下 `${DASHBOARD_MYSQL_DSN}` 展开为空，导致 `invalid DSN: missing the slash separating the database name`。

**两个具体表现**（都会误导排查）：

| 现象 | 真相 |
|---|---|
| `invalid DSN: missing the slash separating the database name` | DSN 被展开成**空串**，不是 DSN 写错 |
| `type mismatch for field "Redis.db"` | `DB: ${REDIS_DB}` 被展开成**字符串**，而字段是 `int` |

**处置**：M5 三个 yaml 的 MySQL DSN / Redis Addr / Pass **直接写本地开发字面量**（`onepark123` 等开发凭据仓库 `.env.example` 中本已存在），并在注释中写明"部署环境请改回 `${}` 由环境变量注入"；`DB` 必须写数字字面量 `0`。

> ⚠️ **建议同步 M2**：`app/workorder-service/etc/workorder-api.yaml` 使用的是 `${WORKORDER_MYSQL_DSN}` 与 `DB: ${REDIS_DB}`，**存在同样问题**。

#### 4.5.6 新发现的契约缺口（需向 M2 反馈）

`WorkOrderSummary` 只有 `created_at`，**没有 `finished_at`**。因此组长要求的 4 个指标中：

| 指标 | 可行性 |
|---|---|
| 今日工单数 | ✅ 可用 `created_at` + `total` 计算 |
| 未完成 | ✅ `pending_count` 直接返回 |
| 完成率 | ⚠️ 需按 `status` 多次查询估算 |

### 4.7 【P1 收尾】清单 #74：告警事件自动建单（已实现并验证）

#### 4.7.1 数据源与消息结构

数据源为 M1 `event-dispatcher` 投递到 **`alarm-event`** 的消息（`common/kafka/topics.go` 的 `TopicAlarm`）。消息体（与 `app/event-dispatcher/internal/dispatch.Message` 对齐）：

#### 4.7.2 实现要点

| 要点 | 做法 | 理由 |
|---|---|---|
| **幂等** | 以 `request_id` 作为 `alarm_id`，靠 `dispatch_task.uk_alarm_id` **唯一索引**兜底 | 唯一索引在数据库层保证，重投/多实例并发都只落一张单；应用层"先查后插"有竞态 |
| **优先级映射** | `fire`/`smoke` → 紧急(1)；`intrusion`/`door_force` → 高(2)；`fault`/`offline_alert` → 普通(3) | 与 `dispatch_task.priority` 取值一致 |
| **未知告警类型** | **不丢弃**，按普通优先级建单 | 丢弃会漏掉真实告警，宁可多派一次 |
| **`zone_code` 缺失** | 依次尝试 `payload.zone_code` → `payload.location` → **留空** | **不臆造区域**——就近指派依赖真实区域编码，编造会把人员派到错的地方；留空则落到「待指派」交人工 |
| **坏消息** | 记录日志后**返回 nil** | 若返回 error，位移不提交，**整条分区会被一条毒消息卡死** |
| **复用** | 复用 `common/kafka` 的 `Consumer`（handler 成功才 commit） | 该封装语义正合需求，不自建 Reader |

**新增文件**：`internal/consumer/{alarm,handler,runner}.go` + `alarm_test.go`；`model.NewTaskNo()` 下沉到 model 层供两条建单路径复用。

#### 4.8.1 合同到期（补上"合同永远不会自动到期"的数据正确性缺口）

### 4.10 【P2】工单智能派单：技能标签 + 就近 + 负载均衡（2026-09-16）

#### 4.10.1 前置结论：技能数据源不存在，必须 M5 自持

`proto/user` 与 `proto/auth` 仍是 `rpc Ping` 骨架，全仓库搜不到任何 staff/employee/skill 定义。
而「基于人员负载与技能标签」是组长 P2 的明确要求 → **M5 在 `dispatch_db` 内自建人员池**（每服务独立库，无跨模块依赖）。

> 待 M6 提供人员主数据后，改为「同步 + 本地缓存」，**指派算法无需改动**。

#### 4.10.2 数据层

| 变更 | 说明 |
|---|---|
| 新表 `dispatch_staff` | `staff_id`(唯一) / `name` / `phone` / `zone_code` / `skills` / `on_duty` / `status` |
| 新列 `dispatch_task.required_skill` | 工单所需技能，空表示不限 |

- `skills` 用**逗号分隔**而非拆子表：园区处理人几十人量级，指派时全量载入内存比较，拆表换不来收益（若将来上千人再规范化，已在 DDL 注释中写明）
- 写入前 **`NormalizeSkills` 归一化**（去空白、去空项、去重、小写），否则 `"Fire"` 与 `"fire"` 匹配不上

#### 4.10.3 打分模型（本方案的核心）

```
score = 10000 × 技能匹配 + 100 × (3 - 拓扑距离) + (99 - min(负载, 99))
```

**权重为什么这么取**：`10000 >> 100 >> 99` 的量级差保证三层优先级呈**严格字典序**：

- 技能是"能不能干"的硬条件，必须压倒性优先 —— 派错人等于没派
- 负载项被截断在 99 以内，**再大的负载差也翻不过距离一档**（100），距离差也翻不过技能一档（10000）

**两个关键兜底**（否则功能会制造事故）：

1. **无人在技能上匹配时，自动退化为「就近 + 负载」**，而不是返回空把工单卡死
2. **未指定技能的工单**，技能项对所有人相同 → 自动退化为「就近 + 负载」，与改造前行为一致

**候选池双轨**：优先 `dispatch_staff`（带技能）；人员池为空时回退到历史指派记录（不带技能），保证旧行为不退化。

### 4.11 【P2】合同到期自动续签 + 续签提醒（2026-09-16）

#### 4.11.1 一个业务判断：不能无脑自动续签

P2 原文是「合同到期自动续签」。但**现实里房东不会替租客决定续租** —— 租金、租期都要谈。
若无条件延长所有到期合同，系统会凭空造出"承租方并未同意的租约"，属业务事故。

因此本方案把自动续签做成**合同条款级别的可选开关**：

| `auto_renew` | 到期时的行为 |
|---|---|
| `0`（默认） | 转「已到期」，由业务人员去谈续签 → 走已有的人工 `renew` |
| `1`（签约时显式约定） | 按**原租期长度**顺延，状态保持「生效中」 |

#### 4.11.2 数据层

| 变更 | 说明 |
|---|---|
| `lease_contract.auto_renew` | 1 约定自动续约 / 0 到期即止，**默认 0** |
| `lease_contract.renew_notice_days` | 到期前多少天进入续签提醒窗口，默认 30 |

#### 4.11.3 每日维护：**先续约，再到期**（顺序不能反）

```
每日 00:05（+ 启动补偿）
  ├─ 1) autoRenew : status=生效中 AND auto_renew=1 AND end_date < 今天 → 顺延租期
  └─ 2) expireDue : status=生效中 AND auto_renew=0 AND end_date < 今天 → 转「已到期」
```

**顺序是硬约束**：只有先把该续约的顺延掉，剩下的才是真正该到期的合同。反过来做，
续约合同会先被改成「已到期」，而 FSM 里「已到期」续签虽可行，但语义已经错了。

**续约后的新终止日按「原租期长度」顺延，不是写死一年**：

```
原 1 年期 → 顺延 1 年      原 3 年期 → 顺延 3 年
兜底: 原租期不足 1 年 / 超过 30 年(脏数据) → 退化为顺延 1 年
```
写死一年会把长期租约悄悄改成短期，这是不能接受的。

**三层防重复**（与前一轮同源设计，锁会丢所以不能只靠锁）：
Redis `SET NX` 锁（Lua 比对释放） → 更新带 `status AND version` 条件 → 审计仅在 `RowsAffected>0` 时写。

#### 4.11.4 续签提醒：按每份合同自己的谈判周期判定

`GET /api/lease/contracts/expiring` 的每条记录新增：

- `auto_renew` —— 前端据此区分"将自动续约"与"待谈续签"
- `need_notice` —— `days_left <= 该合同的 renew_notice_days`，**而不是请求参数 `days`**

理由：大周期租约（如 3 年）可能提前 90 天就要谈，小面积短租提前 15 天即可。
用请求级的 `days` 无法表达这种差异。

#### 4.11.5 验证证据

### 4.12 【跟进上游】启用 JWT 鉴权 + 简化 Kafka 依赖（2026-09-16）

#### 4.12.1 起因

合并 `origin/develop`（M1 `b341f95 打通指令下行链路并落地网关设备接入`）后，`common/` 带来两处与 M5 相关的变化：

| 上游变化 | M5 跟进动作 |
|---|---|
| `common/kafka` 新增 `type Message = kafka.Message` | **去掉 dispatch 对 segmentio 的直接依赖**（见 4.12.2） |
| **新增 `common/middleware/jwt.go`** | **M5 三服务挂上 JWT 中间件**（见 4.12.3） |

#### 4.12.2 去掉 Kafka 客户端的直接依赖

原先 dispatch 的 `consumer/runner.go` 为了拿到 `kafka.Message` 类型，必须 import segmentio 包并起别名 `segkafka`
（因为 `onepark/common/kafka` 与 `github.com/segmentio/kafka-go` **包名都叫 `kafka`**）。

上游增加了类型别名后：

```go
// 现在
err := r.consumer.Consume(ctx, func(ctx context.Context, msg kafka.Message) error {
	return r.handler.Handle(ctx, msg.Value)
})
```

`go mod tidy` 后 **`github.com/segmentio/kafka-go` 已不再是 dispatch 的直接依赖** —— 少一个版本漂移面。

#### 4.12.3 挂 JWT 中间件（含一个容易踩的顺序坑）

```
server.Use(middleware.RequestIdMiddleware)
server.Use(middleware.Cors)              // ← 必须在 JWT 外层
server.Use(middleware.JWT(c.JwtSecret))
```

**为什么 Cors 必须在 JWT 外层**：浏览器的 `OPTIONS` 预检请求**不带 token**，
若 JWT 在外层会把预检直接判成 401，**前端所有跨域请求都会失败**。
`middleware.Cors` 对 OPTIONS 是直接返回 204 并中断，因此不会走到 JWT。

**密钥留空的策略**：`JwtSecret` 在三个 yaml 中默认写成 `""` —— 中间件在 secret 为空时**降级为透传并打告警日志**，
因此这一改动**不改变任何现有调用方式**（本地联调不受影响），等 M6 认证服务就绪后只需填密钥。

**顺带修好一处缺陷**：JWT 中间件会把 token 里的 `userId / tenantId / roleIds` 写入 ctx。
M5 的审计流水一直用 `ctxdata.GetUserId(l.ctx)` 取操作人，此前无 JWT 时**恒为 0**；
挂上后**填了密钥即有值**。

#### 4.12.4 验证证据

**（1）配了密钥时，HTTP 与 WebSocket 都被真正拦住**（用临时配置 + 手签 HS256 token 实测）

```
1) HTTP 不带 token -> 401  {"code":"M6-E-0002","msg":"缺少 Authorization Bearer Token"}
2) HTTP 带 token   -> 200
3) WS   不带 token -> 握手被拒, HTTP 401
4) WS   带 token   -> 握手成功, HTTP 101
5) WS   收到快照   -> {"type":"snapshot","data":{...},"cached":true,...}
```

> 这**闭环了 §4.8.3 中公开披露的缺口** —— 原文档写「WS 鉴权 `?token=` 当前不校验（M6 JWT 就绪后补）」，
> 现已真正生效。`extractToken` 支持从 `?token=` 取值，正是为浏览器无法给 WS 握手设 Authorization 头而设计。

**（2）密钥为空时保持透传（不破坏本地联调）**

```
真实配置(JwtSecret: "") 不带 token 请求 -> HTTP 200 ✅
```

**（3）合并后回归**：`go build` / `go vet` / `go test` 三服务 EXIT=0（62 个用例全过）

#### 4.12.5 一个需要团队统一的口径

截至本次，**全队只有 M1 `device-service` 挂了 JWT**。M5 现在是第二个。
**M2/M3/M4 尚未挂** —— 若前端先接 M5，会出现"求 M5 要 token、求别家不要"的不一致。

因此 M5 采取的是**"代码就位、密钥留空"**：机制已通、行为不变，待组长统一后同步填密钥即可。

### 4.14 【功能补齐】指派超时重派（2026-09-17）

#### 4.14.1 缺口：`assign_expire_at` 写了没人读

`dispatch_task.assign_expire_at` 在指派时被写入（5 分钟窗口），DDL 注释也写着「超时由 cron 重派」——
但**全仓库没有任何地方读它，`dispatch-service` 连 cron 目录都没有**。

**后果**：派单后处理人一直不接单，工单会**永久卡在「已指派」** ——
既不出现在任何待办列表里，也不会被统计口径捞到。这属于数据正确性缺口，不只是"少个功能"。

#### 4.14.2 改动

| 层次 | 改动 |
|---|---|
| 状态机 | 新增 `ActionRelease`：`已指派 → 待指派`（FSM 原本没有 2→1 的出边） |
| 数据层 | `dispatch_task.reassign_count`（重派次数），纳入 `model.MaxReassignDefault=3` 上限 |
| 领域常量 | `assignExpireWindow` 从 logic 层上移到 `model.AssignExpireWindow` —— 指派与重派必须用同一个值，分开定义会错位 |
| 候选池 | `assign.Pool()` / `assign.Without()` 抽出，**指派与重派共用一份实现**，避免两处逻辑漂移 |
| 定时任务 | `internal/cron/{cron,reassign}.go`（周期扫描 + 启动补偿 + Redis 锁） |
| 接口 | `DispatchTask` 暴露 `reassign_count` 与 `assign_expire_at`（否则运维不知道系统替他改派过） |

#### 4.14.3 三层兜底：保证工单最终一定有人管

```
1. 未达重派上限且有人可派 → 改派给「排除原处理人」后的最优人选（沿用「技能 > 就近 > 负载」打分）
2. 没有人可派             → 释放回「待指派」，交人工
3. 重派次数已达上限       → 释放回「待指派」，交人工
```

**为什么不设"重派次数无上限"**：园区可能全员不在岗或技能池为空，无上限会每轮重试同几张单，
既刷爆日志，又掩盖「真的没人可派」这个事实。

**为什么只处理 `status=已指派(2)`**：`处理中(3)` 说明人已经接单，重派等于把人正在干的活抢走。

#### 4.14.4 四个不显眼但会出事的细节

| 细节 | 不这么做的后果 |
|---|---|
| **重派必须排除原处理人** | 会原样再派给刚超时的那位 → **每轮重派同一个人的死循环** |
| **本轮已派出去的负载要累加回内存** | 一批积压工单会拿着同一份陈旧负载**反复选中同一个人**，负载均衡当场失效 |
| **重派后重置超时窗口** | 新处理人同样需要一个接单时限 |
| **人工指派时把 `reassign_count` 归零** | 否则「被自动重派 3 次 → 释放 → 人工再指派 → 又超时」会**立刻被再次释放**，人刚指派的对象连一个接单窗口都拿不到（**此问题是在端到端验证中发现并修复的**） |

**并发防护三层**（与 leasing 到期任务同源设计，锁会丢所以不能只靠锁）：
Redis `SET NX` 锁（Lua 比对释放）→ 更新带 `status AND version` 条件 → 审计仅在 `RowsAffected>0` 时写。

**审计刻意不与状态更新放同一事务**：状态变更是主流程，审计失败只记日志不回滚 ——
「改了但没留痕」比「留了痕但没改」危害小得多，也不会让定时任务整体失败。

#### 4.15.2 大屏 Kafka 事件增量推送（周四 P0）

原状态：只做了 5s 周期快照；事件驱动当时因共享 broker 未授权而搁置。

**关键设计：事件必须能"穿透"聚合缓存。** 只推事件、不管缓存的话，下一次快照（5s 后）仍会读到旧聚合值，事件效果被 30s 缓存盖住 —— 那事件驱动就白做了。

```
事件到达 ──► Dirty.Mark()                    // 纯内存写一个 bool, 极轻量
                │
每 5s 快照循环 ─┴─► if Dirty.Take() { SCAN+DEL 概览缓存; 重新聚合 }
```

**为什么失效动作放在快照循环里，而不是事件回调里**：

1. **天然节流** —— 告警风暴时每 5s 最多失效一次，不会每个事件都去 `SCAN` Redis；
2. **不丢效果** —— 若在回调里做「节流失效」（如 1s 内只一次），节流窗口内的事件可能被随后的聚合写成旧值；而脏标记在被取走前一直保留，**最后一条事件的影响必然体现在下一次聚合里**。

**其他要点**：

| 点 | 做法 | 理由 |
|---|---|---|
| 缓存失效 | `SCAN` + `DEL` 匹配 `m5:dashboard:overview:tenant:*` | **`KEYS` 会阻塞 Redis 单线程**，key 一多就是事故 |
| 事件体 | **原样透传 Kafka 消息**，不解析 | 事件 schema 归生产方(M2/M3)；在这里再定义一份 = 把同一契约写两遍，上游改字段会静默失配 |
| 消费组 | `m5-dashboard-dev-{topic}` | 必须与生产方 M2/M3 的消费组区分，否则会**吃掉它们该消费的消息** |
| Topics | 必须显式配置，代码**不猜默认值** | 共享 broker 上"猜错 topic"就是去读别人的消息 |
| 无大屏在线时 | **照样置脏** | HTTP 的 `/overview` 同样吃这份缓存；「没人看就不失效」会让接口一直返回旧值 |
| 坏消息 | 返回 nil 跳过 | 返回 error 则位移不提交，**一条毒消息卡死整个分区** |

新增文件：`wsserver/event.go`、`logic/dashboard/cache.go`（+ 两个测试文件）；`config.KafkaConf`（默认关闭）。

#### 4.15.3 leasing gRPC 补 `GetContract` / `GetOccupancy`（周六）

| 项 | 内容 |
|---|---|
| 契约 | `proto/leasing/leasing.proto` 补 2 个 rpc + 消息定义，`protoc` 重新生成 pb |
| 端口 | **9051**（`etc/leasing-grpc.yaml`），与 HTTP 8051 是两个独立进程 |
| 入口 | `app/leasing-service/grpcserver/main.go`（沿用 alarm/workorder 的 `grpcserver/` 约定） |
| 实现 | `internal/rpcserver/server.go` |

**架构决策：gRPC 层是薄适配层，复用 HTTP 的 logic**

`GetContract` → 直接调 `ContractDetailLogic`；`GetOccupancy` → 直接调 `OccupancyLogic`。**不在本层重写查询** —— 同一个「查合同」若实现两遍，HTTP 与 gRPC 的返回迟早会不一致，而调用方无从判断该信哪个。

**三个细节**：

| 点 | 处理 | 理由 |
|---|---|---|
| 金额字段 | proto 用 **string** 承载 decimal（如 `"10000.50"`） | protobuf 无 decimal 类型；用 double 会重现项目内已明令禁止的金额精度问题 |
| 租户隔离 | 请求带 `tenant_id` 时**显式校验归属**，跨租户返回 `NotFound` | HTTP 侧靠网关注入的租户上下文约束，**gRPC 调用不经过网关中间件** —— 不校验就会出现"拿 A 园区身份查到 B 园区合同" |
| 错误语义 | 跨租户返回 `NotFound` 而非 `Forbidden` | 避免泄露「该合同存在」这一事实 |
| Redis | gRPC 入口**不装配 Redis** | 用到的两个 logic 都不碰缓存；而 `svc.NewServiceContext` 在 Redis 探活失败时 `log.Fatalf` —— gRPC 服务不该因缓存不可用就起不来 |

#### 4.15.4 月度租金账单定时任务（周三 P1 缺口）

计划书要求「每月 1 号凌晨扫描生效中合同生成当月账单」，但核查发现 leasing 的 cron **只有自动续约和自动到期，没有出账任务** —— 只能手工调 `POST /api/lease/bill/auto`。

补：`monthlySpec = "10 0 1 * *"`（每月 1 号 00:10），**与每日任务错开 5 分钟** —— 出账依赖「该到期的合同已转过状态」这一结果，同时刻启动会争抢连接与锁，日志也难以归因。

#### 4.16.1 ⭐ 补测过程中抓到一个真 Bug：人工续签不留审计

写「合同流转 + 核对审计流水」用例时，断言「创建/生效/续签/终止 各一条」→ **实际只有 3 条，`renew` 没有**。

根因 `ContractUpdate`：

```go
if nextStatus != contract.Status {   // 只认"状态变化"
    写审计
}
```

**续签是「生效中 → 生效中」**（改了租期与租金，但不改状态）→ 人工续签**完全不留下痕迹**。

而**同一件事由定时任务自动续约时是写审计的**（`cron/daily.go` 显式写 `from=2 to=2`）
→ **两条路径两套标准**，违反架构一致性铁律。

**已修**：审计条件改为「状态变化 **或** 合同条款实质变更（`renew` / `update`）」，
并消掉了 `case "update":` 的魔法字符串（提为 `actionUpdate` 常量）。

> 这类 Bug 的特点：**不报错、不崩溃、数据"看起来也对"** —— 只是想查「这合同什么时候续过、租金从多少调到多少」时查不到。
> 只有写了**断言审计条数**的测试才会发现它。

#### 4.16.2 顺带记录一个已知设计缺口（**未修，待确认**）

**「待生效」合同的租期无法修改**：

- `renew` 在「待生效」下非法（FSM 无该出边）
- `update` 只处理 `monthly_rent` / `auto_renew` / `renew_notice_days`，**不含起止日期**

即：合同录入后若发现日期写错，**在它生效之前没有任何接口能改**（只能先 activate 再 renew，而 renew 要求新终止日晚于原终止日 —— 改「起租日」根本无从下手）。

已在 `leasing/internal/state/fsm_test.go` 的 `TestPendingContractCannotChangeDates` 里**钉住当前行为**：
将来补上该能力时必须同步改该用例，而不是让它悄悄变化。**修不修请组长/业务确认。**

#### 4.17 A8：M5 容器化片段（2026-09-20）

计划书验收标准要求「**Docker Compose 一键启动全平台**」。核实后的事实是：

- `deploy/docker-compose.yml` **只有中间件**（mysql/redis/tdengine/kafka/emqx/nacos/minio/es），**一个应用服务都没有**；
- 全仓**只有 `deploy/m5` 一个 Dockerfile** —— M1~M4、M6 的服务都还是宿主机 `go run`。

**结论**：「一键启动全平台」是**平台级任务**，不是 M5 能单独完成的。M5 的职责是**交出自己的片段**，
由平台负责人合并。本目录即是该片段。

##### 交付物（`deploy/m5/`）

| 文件 | 内容 |
|---|---|
| `Dockerfile` | 4 个入口共用的多阶段构建，`--build-arg SERVICE=<main 包所在目录>` |
| `docker-compose.m5.yml` | override 片段，4 个服务（leasing HTTP/gRPC、dashboard、dispatch） |
| `etc/*.yaml` | 容器内配置（连接目标用**服务名**，与本地开发版写 `127.0.0.1` 不同） |
| `README.md` | 用法、端口表、**三个已踩过的坑**、当前限制 |

**为什么是 override 片段而非直接改主 compose**：`deploy/` 是全平台共用目录，直接加服务会与队友改同一文件，
冲突概率高。片段可独立评审、独立合入。

##### 验证证据（真实运行，非仅 `config` 通过）


##### ⭐ 顺手修掉一个「注释承诺了但做不到」的陷阱

三个 HTTP 入口（`leasing.go` / `dashboard.go` / `dispatch.go`）都**没有**开启 `conf.UseEnv()`：

```go
// etc/dispatch-api.yaml 的注释: "部署环境请改回 ${DISPATCH_MYSQL_DSN} 形式由环境变量注入"
conf.MustLoad(*configFile, &c)                 // ← HTTP 入口: ${} 不会展开, 保留字面量
conf.MustLoad(*configFile, &c, conf.UseEnv())  // ← 只有 leasing 的 gRPC 入口启用了
```

**后果**：部署时照注释改成 `${VAR}`，DSN 会带着未展开的 `${...}` 去连库，只报一句难懂的 `invalid DSN`。

而且这不是孤例 —— 全平台 **12 处启用了、8+ 处没启用**（`device`/`auth`/`gateway`/`shadow`/`energy-data`/... 都没启用），
其中启用的几个服务还专门写了「**必填**」注释。**属于平台级约定未统一**，建议平台负责人统一收口（M5 已改自己的 3 处）。

容器化过程中还实测出**两个片段自身的坑**（已写进 `deploy/m5/README.md`，避免后人重踩）：

1. **override 里的相对路径以「基础文件所在目录」为基准**，不是以片段自己所在目录为基准 ——
   `context: ../..` 会被解析到仓库**上一级**。已用 `docker compose config` 实测确认。
2. **不能复用 `.env` 的 `REDIS_ADDR`**（值是 `127.0.0.1:6380`，那是**给宿主机直跑的服务用的**）。
   `${VAR:-默认}` 的默认值只在变量未设置时生效，而 `.env` 里它是设了的 → 容器去连自己的 `127.0.0.1` 并启动失败。
   改用 M5 专属变量名，默认值即容器需要的 `redis:6379`。
3. **`SERVICE` 必须是 main 包所在目录**：leasing 的 gRPC main 在 `app/leasing-service/grpcserver/`，
   传成 `leasing-service` 会编出 HTTP 二进制，读 gRPC 配置时报 `field "Port" is not set` 并无限重启。

##### 当前限制

- 健康检查是 **TCP 探测而非业务探测** —— 服务尚无 `/healthz`（A7，待 M6 的 `common/checks`）。
- **M1~M4 未容器化**，容器内通过 `host.docker.internal` 访问它们；进同一网络后应改为服务名。
- Kafka 消费者在容器配置里**保持关闭**；`JWT_SECRET` 默认空（鉴权放行），与本地开发一致。
