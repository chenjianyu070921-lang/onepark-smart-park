# Day 1｜本地 Kafka 端到端闭环（部署 + 测试）

## 主线：把 M5 唯一的未验证项自己关掉

M5 目前**唯一的实质性未验证项**是 Kafka 端到端。之前的判断是「等组长授权 topic」——
但那只挡住「连**组长那个** broker」，**挡不住自己起一个本地 broker**。

1. **拉起本地 Kafka**（本机不可直连 Docker Hub，走镜像源）：

   ```powershell
   docker pull docker.m.daocloud.io/apache/kafka:3.7.0   # KRaft 单节点，无需 ZooKeeper
   docker run -d --name onepark-kafka-local -p 19092:9092 `
     -e KAFKA_NODE_ID=1 -e KAFKA_PROCESS_ROLES=broker,controller `
     -e KAFKA_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093 `
     -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://127.0.0.1:19092 `
     -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@127.0.0.1:9093 `
     -e KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER `
     -e KAFKA_LISTENER_SECURITY_PROTOCOL_MAP=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT `
     -e KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1 `
     docker.m.daocloud.io/apache/kafka:3.7.0
   ```

   端口用 **19092**（不用 9092），避免与配置里残留的远端地址混淆。

2. **建 topic**（本地随便建，不涉及授权）
3. **临时把 M5 消费者指向本地**：`Brokers: 127.0.0.1:19092`、`Enabled: true`
   —— ⚠️ **只在本机临时改，不要提交**（提交前改回 `Enabled: false`）
4. 验证两条消费链路

# Day 2｜招商账单闭环（研发）

## 主线：🔴 账单查询接口


补 `GET /api/lease/bills?contract_id=&period=&status=&page=&page_size=`，按账期倒序。

## 加练 A｜🔴 账单**缴费**接口（比查询更要紧）

`lease_bill.status` 有两个取值（1 未缴 / 2 已缴），但**没有任何接口能改它** ——
账单一旦生成就是**死数据**，收不到款的状态。

补 `PUT /api/lease/bill/:id/status`（`action=pay|unpay`）：

- 用**乐观锁** `WHERE id=? AND version=?` 防并发重复操作
- 幂等：已是「已缴」再缴一次不报错也不重复写（或明确返回提示）
- 写审计（谁在什么时候标记的）

> Hmm — `lease_bill` 有没有 `version` 列？DDL 里没有。**要么加列，要么用「条件更新」实现幂等**：
> `UPDATE lease_bill SET status=2 WHERE id=? AND status=1` → `RowsAffected=0` 说明已缴，返回提示。
> **不加列更简单，优先这个方案**。

## 加练 B｜账单汇总统计

`GET /api/lease/bills/summary?period=&tenant_id=` → 应收 / 已收 / 欠费金额 + 笔数。

- 金额一律 decimal，**SQL 层 `SUM` 后按定长 2 位渲染**（复用 `moneyString`）
- 招商页要的就是这几个数

# Day 4｜性能基线 + 缓存击穿防护（优化）

## 主线：大屏聚合性能基线

`/api/dashboard/overview` 是 M5 的**门面接口**，答辩/演示必被问「四路并发聚合性能怎么样」。现在**只有功能证据，没有性能数据**。

1. **基准测试**（测试桩替代真实 gRPC，先测聚合层自身开销）
2. **并发压测**：真实起服务，逐步加压 100 / 500 / 1000 并发
3. **出这些数**：

   | 指标 | 说明 |
   |---|---|
   | p50 / p95 / p99 | 缓存命中 vs 穿透**分别测** |
   | QPS | 30s 缓存下的稳态吞吐 |
   | 缓存命中率 | 实测值 |
   | **800ms 预算守不守得住** | 整体超时是硬承诺，要看到最坏值 |
   | 降级开销 | 某路挂掉时的延迟变化 |

## 加练 A｜🔴 缓存击穿防护（现在有真实风险）

**已核实：`dashboard` 没有用 `singleflight`。**

后果很具体：30s 缓存**过期的那一瞬间**，若正好有 500 个并发请求到达 ——
**500 个请求会同时穿透到四路 gRPC**（2000 次上游调用）。

这恰恰抵消了缓存的意义（计划书周四 P1 的原话是「**减轻 gRPC 压力**」）。

**方案**：复用 go-zero 内置的 `core/syncx/singleflight`（项目里已有可复用件）：

```
缓存未命中 → singleflight.Do(key, 实际聚合)  → 同一 key 的并发只放一个进去
```

⚠️ 注意：`singleflight` 返回的 `resp` 会被多个调用方共享，**必须只读**（不能在返回前再改字段）。
如果需要写 `cached` / `elapsed_ms` 这类字段，要先拷贝一份再改 —— 否则会数据竞争。

**产出**：加练前后各压一轮，**用数据说明穿透次数下降**。

## 加练 B｜WebSocket 推送压测

5s 快照 × N 个客户端：CPU、内存、推送延迟、单客户端断开的清理是否及时（连接泄漏）。

## 加练 C｜列表接口的索引验证

对 `dispatch` / `leasing` 的列表接口跑 `EXPLAIN`：

- 工单列表按 `status + priority`、`zone_code + status` 是否走索引
- 合同列表按 `status + end_date` 是否走索引
- **造一批数据（几千条）再看执行计划** —— 空表上 EXPLAIN 看不出问题
