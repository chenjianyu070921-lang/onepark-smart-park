# 事项一：topic 不存在 + 建 topic 的权责未定

## 1. 现状

M5 的两个消费者要用的 topic：

| 服务 | 消费 topic | 用途 |
|---|---|---|
| `dispatch-service` | `alarm-event` | 告警自动建调度工单（接口清单 #74） |
| `dashboard-service` | `alarm-event`、`workorder-event` | 大屏事件增量推送（计划书 周四 P0） |

**2026-09-16 实测该 broker 上 24 个 topic，没有一个属于 onepark 体系**（`alarm-event` 不在）。

## 2. 为什么 M5 不敢自己开

消费一个**不存在的** topic 时，若 broker 开启了 `auto.create.topics.enable`，Kafka 会**隐式把它创建出来** —— 这等于**往组长的共享基础设施上写东西**。

按团队约定，这必须先经同意。因此 M5 的两个消费者都设成 `Enabled: false` 默认关闭，并在 yaml 注释里写明「开启前四项检查」。

## 3. 需要拍板

**请明确两点：**

1. `alarm-event` / `workorder-event` 是**组长建**，还是**授权 M5 建**（或授权 M2/M3 各建自己的）？
2. 该 broker 是否开启了 `auto.create.topics.enable`？若开启，M5 开启消费者时需不需要额外的保护（如先显式建 topic 再开消费）？

> M5 侧不需要改动任何代码 —— `Enabled` 改成 `true` 即可（前提是事项二、四一并确认）。

# 事项二：topic 命名有三套口径

## 1. 三个来源，三种名字

| 来源 | topic 名 | 说明 |
|---|---|---|
| `common/kafka/topics.go`（共用常量） | **`alarm-event`** | M1 的 `event-dispatcher` 按它投递（`deviceeventlogic.go` 调 `Publish(kafka.TopicAlarm)`） |
| `app/alarm-service/etc/alarm-api.yaml` | **`onepark.alarm.event`** | M3 安防自己的命名 |
| `app/energy-data-service/etc/energydata-api.yaml` | **`onepark.device.telemetry`** | M4 自己的命名 |

后两者的 yaml 里还都留着 `TODO: topic 名待与 M1 同学确认后定稿` 之类的注释。

## 2. 后果（以 M1 → M3 为例）

```
M1 event-dispatcher  ──投递──►  alarm-event            （共用常量）
M3 alarm-service     ──消费──►  onepark.alarm.event    （自己的命名）
```

**两条不同的 topic，消息落不到 M3 手里。** M3 的 yaml 注释里也自己写明了这一点：

> `# topic 归属需与 M5 / 组长确认后再联调: 它与 M1 生产的 alarm-event 是两条不同 topic`

## 3. 建议

**统一采用 `common/kafka/topics.go` 的常量**，理由：

- 它已经是**共用包里的唯一权威来源**，各服务直接 `kafka.TopicAlarm` 引用即可，不再手写字符串（手写字符串正是当前分歧的成因）；
- M1（投递方）已经在用它；
- 命名风格统一（中划线短名），与 `TopicParkingEntry` / `TopicNotice` / `TopicWorkorder` 一致。

若最终决定改用点号长名（`onepark.*`），**请一并改 `common/kafka/topics.go`**，并通知所有生产/消费方 —— 不要各改各的。

# 事项三：⚠️ 一条告警可能派两次活（职责重叠）

## 1. 现状

**两个服务都在消费同一个 `alarm-event` 做「自动建单」：**

| 服务 | 消费组 | 建的单 | 开关状态 |
|---|---|---|---|
| **M2** `workorder-service` | `m2-workorder-dev-liu` | **报修工单** `work_order` | `Enabled: true` |
| **M5** `dispatch-service` | `m5-dispatch-dev-hjy` | **调度工单** `dispatch_task` | `Enabled: false` |

M2 的消费者代码注释写着：

> `// 幂等: 复用 dispatch-service 的 uk_alarm_id 唯一索引模式 —— work_order.alarm_id 可空唯一, 同一告警重复投递/多实例并发消费只会落一张工单`

即 **M2 是照着 M5 的模式实现的**，消息体解析也一致（都用 `request_id` 当幂等键）。

## 2. 技术上不冲突，但业务上会重复

**消费组不同 → Kafka 是广播语义，两边都能收到全部消息**（没有互相抢消息的问题）。

**但同一条告警会产生两张单**：M2 的报修单派给物业维修，M5 的调度单按「技能 + 就近 + 负载」派给安保/维修 —— **可能两个人跑到同一个地方干同一件事**。

## 3. ✅ 结论：组长定「双层」（2026-09-18）

**保持两层并存**：M2 建报修工单（受理/记录层），M5 建调度工单（派活/处置层）。

### 3.1 这一决策的落地要求（M5 侧）

**① 关联键已经天然具备：`alarm_id`**

两张单都用同一条告警的 `request_id` 作为幂等键，因此**「同一条告警的两张单」可以通过 `alarm_id` 互相找到**：

| 表 | 列 | 值 |
|---|---|---|
| M2 `work_order` | `alarm_id`（可空唯一） | 告警的 `request_id` |
| M5 `dispatch_task` | `alarm_id`（可空唯一） | **同一个** `request_id` |

M5 的 `alarm_id` 已经在 HTTP 响应里暴露（`DispatchTask.alarm_id`），M2 侧同理 → **无需任何代码改动即可关联**。

**② 两层的职责边界（写清楚，避免演示被问「为什么两张单」）**

| 层 | 归属 | 回答的问题 | 处理人来源 |
|---|---|---|---|
| 报修工单 | M2 `workorder-service` | 「这件事**被受理了吗**」——记录、跟踪、验收闭环 | 物业派单流程 |
| 调度工单 | M5 `dispatch-service` | 「**现在谁去现场**」——按技能 + 就近 + 负载 + 超时重派 | 智能派单算法 |

**③ 遗留的语义问题（M5 无法单方面决定，需与 M2 对齐）**

两层各有自己的状态机，**目前互不影响**，由此产生两个待确认点：

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | **状态是否联动** | 可能出现「报修单已验收关闭，调度单还在派人」或反之 | 建议**单向联动**：调度单 `finish` 后回写报修单状态；反向不回写（避免循环）。M5 侧可提供 gRPC 供 M2 查询调度单状态 |
| 2 | **会不会重复派人** | 两层若各自自动派单，可能派两个人到同一现场 | 建议明确：**处置只由调度单负责**，报修单不自动派人（或派单前先看同 `alarm_id` 是否已有调度单） |

> 这两条 M5 不自行改动跨模块行为。**若组长认为需要联动，M5 侧愿意承担**：
> 在 `dispatch` 增加「按 `alarm_id` 查调度单」的 gRPC 接口，或由 M5 在调度单完成时主动调 M2 的接口回写。
> 请明确由哪一侧发起。

### 3.2 M5 侧当前状态

`Enabled: false`，**未在真实 broker 上产生过任何数据** —— 双层决策落地时不存在脏数据需要清理。

# 事项四：`common/kafka` 的 `StartOffset` 硬编码

`common/kafka/kafka.go`：

```go
func NewConsumer(brokers, topic, group string) *Consumer {
	return &Consumer{reader: kafka.NewReader(kafka.ReaderConfig{
		Brokers:        strings.Split(brokers, ","),
		Topic:          topic,
		GroupID:        group,
		StartOffset:    kafka.FirstOffset, // ← 硬编码: 首次从最早位移开始
		CommitInterval: 0,
	})}
}
```

**`FirstOffset` 的含义是：新消费组从该 topic 的**最早**位移开始消费。**

**后果**：M5 一旦开启消费者，若 topic 上已有积压消息，会**一次性全部处理**：

- `dispatch-service` → 为每条积压告警**建一张真实工单**
- `dashboard-service` → 把每条积压告警**推给所有在线大屏**

**建议**：给 `NewConsumer` 增加 `StartOffset` 参数（或 `FromLatest bool`），让消费方按场景选择：

| 场景 | 应选 |
|---|---|
| 首次接入、确认无积压 | `FirstOffset` |
| 生产环境新增消费方（不希望补历史） | `LastOffset` |

`common/` 是跨模块共用目录，**M5 未自行改动**，仅提出建议。

# 建议 1：`common/kafka` 的失败重试没有退避

同一个文件：

```go
if hErr := handler(ctx, m); hErr != nil {
	// 处理失败不提交, 等待后续重试(至多一次语义的简单兜底).
	continue
}
```

**不提交位移 → 下一次 `FetchMessage` 会立刻拿到同一条消息 → 不带任何退避地死循环重试。**

后果很具体：**一条永远处理不了的消息会把该分区的消费线程 CPU 打满**，且日志被刷爆。

这正是 M5 的 `dispatch` 消费者**对坏消息必须 `return nil`** 的原因（记日志后跳过）—— 否则一条毒消息就卡死整个分区。但这个防护应该做在**公共层**，而不是指望每个业务 handler 都记得。

**建议**：`common/kafka` 增加 ①失败退避（指数退避或 `time.Sleep` 下限）②最大重试次数后转**死信队列**（`topic-dlq`）。

> 参考：M3 已经自建了 `alarm_dlq`（死信表）与 `internal/dedup/cooldown.go` 去重，说明这类保护是各服务真实需要的，适合下沉到公共层。

# 建议 2：`dispatch-api.yaml` 里写入了 broker 公网地址
