# 事项一：`device-service` 增加设备统计接口

## 1. 一句话诉求

请 `device-service` 增加一个 **返回设备数量统计（而非设备列表）** 的 gRPC 方法，供 M5 大屏计算设备在线率。

## 2. 现状：M5 拿不到设备数

`proto/device/device.proto` 当前只有三个方法：

```proto
service DeviceService {
  rpc Ping(onepark.common.Empty) returns (onepark.common.Empty);
  rpc SendCommand(onepark.common.DeviceCommand) returns (onepark.common.CommandResult);
  rpc GetDevice(GetDeviceReq) returns (GetDeviceResp);   // 单台查询
}
```

**三个都是"单台/指令"语义，没有"统计"语义。** M5 的在线率卡片需要 `在线台数 / 总台数`，现在只能一台一台问。

## 3. 为什么 M5 不能绕开（四条路都试过，都不行）

| 方案 | 为什么不可行 |
|---|---|
| 调 M1 的 HTTP `GET /api/devices` 拿 total | **违反团队规范**：`docs/服务协议规范-HTTP与gRPC.md` 明确「服务间调用一律走 gRPC」 |
| 循环调 `GetDevice` 逐台查询 | N 台设备 = N 次 RPC 往返。大屏聚合接口总预算只有 **800ms**，1263 台设备完全不可行 |
| 提供 `ListDevices` 返回全量列表，M5 自己 `count` | 把全量设备拉到 M5 内存做计数，数据量不可控；且列表语义会诱导实现成返回数组，成本更高 |
| M5 自己消费 `device-telemetry` 维护 Redis 计数 | ① 冷启动没有总数 ② 与 M1 库里的状态**必然对不上**，大屏会出现两个数 |

**结论：只有 M1 能提供这个数，因为设备状态的真相源在 M1 的库里。**

## 4. 建议的接口契约（可直接复制）

```proto
service DeviceService {
  // ... 现有三个方法保持不变 ...

  // GetDeviceStat 设备数量统计, 供 M5 dashboard-service 大屏计算在线率(清单 #69 / #72).
  // 注意: 返回的是"统计数", 不是设备列表 —— 大屏只需要台数。
  rpc GetDeviceStat(GetDeviceStatReq) returns (GetDeviceStatResp);
}

// GetDeviceStatReq 设备统计查询条件
message GetDeviceStatReq {
  string product_key = 1; // 产品Key, 空表示全部产品
  int32  type        = 2; // 设备类型(1地磁 2门禁 3摄像头...), 0 表示全部类型
}

// GetDeviceStatResp 设备数量统计
// 四个字段的关系恒为: total = online + offline + fault
// (device.status 有三个取值, 若只返回 online/offline 会让 total 对不上, 详见 §4.2)
message GetDeviceStatResp {
  int64 total   = 1; // 设备总台数(未删除)
  int64 online  = 2; // status = 1 在线
  int64 offline = 3; // status = 0 离线/未激活
  int64 fault   = 4; // status = 2 故障
}
```

### 4.2 ⭐ 为什么必须带上 `fault` 字段（重要）

`device.status` 有三个取值（见 `app/device-service/internal/model/device_model.go`）：

```go
DeviceStatusOffline int8 = 0 // 离线/未激活
DeviceStatusOnline  int8 = 1 // 在线
DeviceStatusFault   int8 = 2 // 故障
```

**如果响应里只有 `total` / `online` / `offline`，那故障设备两边都不计入 → `total ≠ online + offline`：**

```
大屏会显示: 总 1263 台, 在线 1240, 离线 12
但 1240 + 12 = 1252，比总数少 11 台 → 用户第一反应是"系统算错了"
```

这与 M5 上一轮遇到的**告警卡片问题是同一类**：M3 有 4 个告警等级、M5 卡片原本只有 3 个分项，
导致分项之和 ≠ 总数 —— 已通过在契约里补齐第 4 个字段解决。设备卡片同理。

> 补齐 `fault` 后，M5 会加一条 `online + offline + fault == total` 的断言测试。
> 若将来 `device.status` 增加新取值，**该测试会失败并提醒双方同步契约**，而不是悄悄让大屏数字对不上。

### 4.3 如果希望更通用

也可按 M3 的做法返回分布 map（`GetActiveAlarmsResp` 用的就是 `map<int32,int64> level_count`）：

```proto
message GetDeviceStatResp {
  int64             total        = 1;
  map<int32, int64> status_count = 2; // key = device.status, value = 台数
}
```

两种 M5 都能适配。**推荐 §4.1 的显式字段**（类型安全、自解释）。

## 5. 实现建议（约 30 分钟）

`device_model.go` 里已有现成的过滤与 `Count` 逻辑可复用，只需加一个分组统计：

```sql
SELECT status, COUNT(*) AS cnt
FROM device
WHERE deleted_at IS NULL
  AND (? = '' OR product_key = ?)   -- product_key 为空表示全部
GROUP BY status;
```

然后组装成响应，`total` 由三项相加得到，保证恒等。**不需要新表、不需要改数据模型、不涉及 Kafka。**

## 6. 验收标准

```bash

make genproto

# 2. 启动服务
#    注意: device-service 没有独立的 grpcserver 入口, REST(8001) 与 gRPC(9001)
#    由同一个 main 通过 service.ServiceGroup 一起启动
#    (见 device.go 的 rest.MustNewServer + zrpc.MustNewServer)
go run ./app/device-service/ -f app/device-service/etc/device-api.yaml

# 3. 期望: Ping 通, GetDeviceStat 返回四个数且 total = online + offline + fault
```

M5 侧验收（接口一就绪立刻做）：

```

```

# 事项二：`gateway` 对 M5 的转发配置

## 1. 两个问题

### 问题 A：M5 三个服务的端口**全部配错**

`gateway/etc/apigateway-api.yaml` 当前：

```yaml
  - Prefix: /api/leasing     Target: http://127.0.0.1:8015    # ← M5 实际是 8051
  - Prefix: /api/dashboard   Target: http://127.0.0.1:8016    # ← M5 实际是 8052
  - Prefix: /api/dispatch    Target: http://127.0.0.1:8017    # ← M5 实际是 8053
```

M5 三个服务的 `etc/*.yaml` 实际端口（已核对）：

```
leasing-api.yaml:   Port: 8051
dashboard-api.yaml: Port: 8052
dispatch-api.yaml:  Port: 8053
```

**后果：前端经网关调 M5 的三个服务，全部返回 502（upstream unavailable）。**

### 问题 B：大屏 WebSocket 没有路由

`/ws/dashboard` 不在 `/api/dashboard` 前缀下，且配置里**完全没有 `/ws` 开头的上游**，
因此请求会走到 `ServeHTTP` 末尾的 `writeJSONError` → **404 `M6-E-0004 no upstream route`**。

## 2. 修改方案（可直接替换）

```yaml
  # ===== M5 运营招商 + 指挥调度 =====
  # 端口口径: 按《接口清单》(8051/8052/8053)。M2 用的是 8091(清单口径) 而非 README 的 8005,
  # 说明全队实际按清单走, 故 M5 也统一到清单口径。
  - Prefix: /api/leasing
    Target: http://127.0.0.1:8051
  - Prefix: /api/dashboard
    Target: http://127.0.0.1:8052
  - Prefix: /api/dispatch
    Target: http://127.0.0.1:8053

  # 大屏 WebSocket 实时推送(清单 #73)。
  # 路径打全 /ws/dashboard 而不是 /ws —— 网关是最长前缀优先匹配,
  # 若用 /ws, 将来 M3 的 WebSocket(M3 有专门设计文档)会被一并转发到 M5, 造成冲突。
  - Prefix: /ws/dashboard
    Target: http://127.0.0.1:8052
```

## 3. 好消息：**不需要改代理实现**

已核实 `gateway/internal/proxy/proxy.go`：

- 第 45 行用的是标准库 `httputil.NewSingleHostReverseProxy(target)`
- **Go 标准库的 `ReverseProxy` 自 1.12 起原生支持 WebSocket 升级转发**（识别 `101 Switching Protocols` 并接管连接）
- `Gateway.ServeHTTP` 只做「CORS 头 → 注入 requestId/RBAC 头 → 转发」，
  **没有读取 body、没有包装 ResponseWriter、没有缓冲**，因此**不会破坏 Upgrade 握手**

所以**只加配置即可，零代码改动**。

## 确认 1：端口口径以哪个为准（**这是问题 A 的根因**）

| 来源 | M5 端口 |
|---|---|
| README 端口表 | 8015 / 8016 / 8017 |
| **《接口与链路技术点清单》** | **8051 / 8052 / 8053**（M5 现按此实现） |

组长此前给的 P0-6 验收标准写的是 **8015/8016/8017**，而 M5 在合并 `develop` 后发现 **M2 实际用 8091**（清单口径）而非 README 的 8005 —— 判断全队实际按《清单》走，故统一到 **8051/8052/8053**。

**请拍板：若以 README 为准，M5 改 3 个 yaml；若以《清单》为准，改网关那 3 行。**
建议按《清单》——因为 M2 已经是清单口径，且其余多数服务端口尚未对齐 README。

## 确认 2：JWT 的全链路口径

M5 已按 M1 的做法挂上 `common/middleware/jwt.go` 的 JWT 中间件，但 **三处 yaml 的 `JwtSecret` 默认留空**
（中间件在 secret 为空时降级为透传）—— 即**机制就位、行为不变**，本地联调不受影响。

有两个点需要统一，否则联调时会出现"求 M5 要 token、求别家不要"：

1. **网关目前不做 JWT 校验**，只注入默认 `x-tenant-id: 1` / `x-user-id: 0`。
   若 M5 先行填上密钥、而前端/网关不带 token，经网关的请求会被 M5 判 401。
2. 目前全队只有 **M1 `device-service`** 挂了 JWT，M2/M3/M4 未挂。

**建议**：由组长统一定"什么时候一起开"，M5 随时可跟进填密钥（无需改代码）。
