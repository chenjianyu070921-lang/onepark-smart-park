### ⭐ 补测过程中抓到一个真 Bug：续签不留审计

写 `TestContractLifecycle` 时断言「创建/生效/续签/终止 各一条审计流水」，结果**只有 3 条，`renew` 那条没有**。

根因在 `ContractUpdate`：

```go
if nextStatus != contract.Status {   // 只认"状态变化"
    写审计
}
```

**续签是「生效中 → 生效中」**（改了租期与租金，但不改状态）→ 按状态变化判断，**人工续签完全不留下痕迹**。

而同一件事由定时任务自动续约时**是写审计的**（`cron/daily.go` 显式写 `from=2 to=2`）→
**两条路径两套标准**，违反架构一致性铁律。

**已修**：审计条件改为「状态变化 **或** 合同条款实质变更（`renew` / `update`）」，
并顺手消掉了 `case "update":` 的魔法字符串（提为 `actionUpdate` 常量）。

> 这类 Bug 的特点：**不报错、不崩溃、数据也"看起来对"** —— 只是想查"这合同什么时候续过、租金从多少调到多少"时查不到。
> 只有写了断言审计条数的测试才会发现。

## 🔵 2026-09-21 复查新增：合并 develop 后暴露的 2 个租户缺口（已修）

平台侧在 09-16~09-18 落地了 RBAC 数据隔离（`l2_tenant_id_migration.sql` 给业务表统一加 `tenant_id`，
鉴权收口到网关 + `IdentityFromHeader` 把 `x-tenant-id` 提升进 ctx）。
M5 随合并接入后，**写入路径没跟上**，暴露出两处缺口：

### 缺口 1：账单三接口的租户越权（**老弟自己 9-20 写的代码**）

| 接口 | 修复前的写法 | 后果 |
|---|---|---|
| `GET /bills` | 用**请求体**的 `req.TenantId`，且 `!= 0` 才过滤 | 传别人园区 id 能看别人账单；**传 0 直接看全部园区** |
| `GET /bills/summary` | 同上 | 同上（金额汇总泄露） |
| `PUT /bill/:id/status` | **完全没有任何租户检查** | 可跨园区给别人账单**缴费/撤销** |

对比：`contractlist/detail/status/occupancy` 全部用 `ctxdata.GetTenantId(ctx)`（网关注入、不可伪造）。

**已修**：三个接口统一改为「只认 ctx 的租户，且始终过滤」；缴费的条件更新也带上租户条件；
不存在与「不属于本租户」返回同一个 NotFound，不泄露「该账单存在」。
并在 `TestBillFlow` 补了**跨租户断言**（另一个租户：列表为空、汇总为 0、缴费被拒且**状态未被改动**）。

### 缺口 2：dispatch 建单不写租户，但查询按租户过滤

- 迁移给 `dispatch_task` 加了 `tenant_id`；`tasklist/detail/status` 都按 ctx 的租户过滤（平台侧改的）
- 但 `taskcreatelogic` 与 `consumer` **都没写这个字段** → 恒为 DB 默认值 0
- **后果**：网关注入非 0 租户（平台口径：默认园区 = 1）时，**用户建完单立刻在列表里看不到自己的单**

**已修**（与 M2/M4 同一约定）：
- HTTP 建单：写 `ctxdata.GetTenantId(ctx)`（谁建的归谁）
- 消费者自动建单：写 `Kafka.DefaultTenantId`（告警消息体不带租户，只能落兜底园区；
  该配置**平台早已存在**且默认 1，只是此前没人用）—— 已把它显式写进 `etc/dispatch-api.yaml`
- 测试补断言：自动建单必须落到兜底园区（用一个非 0 且非 DB 默认值的租户，证明是「配置注入」而非巧合）

### ⚠️ 遗留待确认：**存量数据的租户回填**

迁移脚本只加列（默认 0），**没有回填**。而平台的口径是「默认园区 = 1」。
若网关注入的 `x-tenant-id` 为 1，则**现有 M5 数据（tenant_id=0）会全部查不到**
（工单、合同、账单都按 ctx 租户过滤）。

→ 需确认两件事：① 网关注入的租户到底解析成 0 还是 1；② 存量数据是否回填、回填成几。
迁移脚本原文也提示了这一点：「回填完成前 datascope 默认 ScopeTenant 会过滤真实数据」。

## A5 决策记录：`dispatch` 不加租户维度（本期单园区）

**结论**：`dispatch_task` / `dispatch_staff` **不加 `tenant_id`**，各接口 DTO 也不加租户参数。

### 为什么

| 理由 | 说明 |
|---|---|
| **本期是单园区部署** | 加租户字段会引入一个**永远是常量**的列，属于典型的过度设计（YAGNI） |
| 加它的连带成本不低 | 要改**建的 2 张表 + 所有请求 DTO + 派单候选池过滤 + 列表筛选 + 缓存**，还要为"告警事件不带 tenant_id"专门做兜底（见下） |
| **告警事件本身没有租户信息** | `alarm-event` 的消息体只有 `device_id` / `event_type` 等。若 dispatch 要按租户隔离，**自动建单就必须猜一个租户** —— M2 的 `workorder-service` 就是这么干的（配置项 `DefaultTenantId: 1` 作为"告警未携带租户时的建单兜底园区"）。单园区下完全不需要这份复杂度 |

### ⚠️ 这一条要写清楚的原因（防止后人"误修"）

`leasing` 有 `tenant_id` + `idx_tenant`，`dashboard` 有租户维度缓存与 `AlarmProvider.Stat(ctx, tenantId)` ——
**唯独 `dispatch` 没有**。这个不对称是**有意的**，不是漏做。

**将来若要支持多园区**，改动清单是：

1. `dispatch_task` / `dispatch_staff` 各加 `tenant_id` + 索引（DDL 在 `deploy/sql/m5_mysql_tables.sql`）
2. `DispatchTask` / `StaffItem` 与 4 个请求 DTO 加字段（改 `.api` 后 `goctl` 重新生成）
3. 列表查询加租户过滤；`assign.Pool()` 的候选池按租户过滤（**否则会把 A 园区的人派去 B 园区**）
4. 自动建单需要一个"告警未携带租户时的兜底园区"配置（参考 M2 的 `DefaultTenantId`）
5. 调度人员维护接口要按租户校验归属

> `leasing` / `dashboard` 已有的租户字段**保持不动** —— 它们是数据隔离列、且当前退化为常量，成本为零；
> 为了"对称"去删它们反而是无谓的破坏性改动。
