### ⭐ 补测过程中抓到一个真 Bug：续签不留审计

写 `TestContractLifecycle` 时断言「创建/生效/续签/终止 各一条审计流水」，结果**只有 3 条，`renew` 那条没有**。

根因在 `ContractUpdate`：

```go
if nextStatus != contract.Status {   // 只认"状态变化"
    写审计
}
```

**续签是「生效中 → 生效中」**（改了租期与租金，但不改状态）→ 按状态变化判断，**人工续签完全不留下痕迹**。

而同一件事由定时任务自动续约时**是写审计的**（`cron/daily.go` 显式写 `from=2 to=2`）→
**两条路径两套标准**，违反架构一致性铁律。

**已修**：审计条件改为「状态变化 **或** 合同条款实质变更（`renew` / `update`）」，
并顺手消掉了 `case "update":` 的魔法字符串（提为 `actionUpdate` 常量）。

> 这类 Bug 的特点：**不报错、不崩溃、数据也"看起来对"** —— 只是想查"这合同什么时候续过、租金从多少调到多少"时查不到。
> 只有写了断言审计条数的测试才会发现。


## A5 决策记录：`dispatch` 不加租户维度（本期单园区）

**结论**：`dispatch_task` / `dispatch_staff` **不加 `tenant_id`**，各接口 DTO 也不加租户参数。

### 为什么

| 理由 | 说明 |
|---|---|
| **本期是单园区部署** | 加租户字段会引入一个**永远是常量**的列，属于典型的过度设计（YAGNI） |
| 加它的连带成本不低 | 要改**建的 2 张表 + 所有请求 DTO + 派单候选池过滤 + 列表筛选 + 缓存**，还要为"告警事件不带 tenant_id"专门做兜底（见下） |
| **告警事件本身没有租户信息** | `alarm-event` 的消息体只有 `device_id` / `event_type` 等。若 dispatch 要按租户隔离，**自动建单就必须猜一个租户** —— M2 的 `workorder-service` 就是这么干的（配置项 `DefaultTenantId: 1` 作为"告警未携带租户时的建单兜底园区"）。单园区下完全不需要这份复杂度 |

### ⚠️ 这一条要写清楚的原因（防止后人"误修"）

`leasing` 有 `tenant_id` + `idx_tenant`，`dashboard` 有租户维度缓存与 `AlarmProvider.Stat(ctx, tenantId)` ——
**唯独 `dispatch` 没有**。这个不对称是**有意的**，不是漏做。

**将来若要支持多园区**，改动清单是：

1. `dispatch_task` / `dispatch_staff` 各加 `tenant_id` + 索引（DDL 在 `deploy/sql/m5_mysql_tables.sql`）
2. `DispatchTask` / `StaffItem` 与 4 个请求 DTO 加字段（改 `.api` 后 `goctl` 重新生成）
3. 列表查询加租户过滤；`assign.Pool()` 的候选池按租户过滤（**否则会把 A 园区的人派去 B 园区**）
4. 自动建单需要一个"告警未携带租户时的兜底园区"配置（参考 M2 的 `DefaultTenantId`）
5. 调度人员维护接口要按租户校验归属

> `leasing` / `dashboard` 已有的租户字段**保持不动** —— 它们是数据隔离列、且当前退化为常量，成本为零；
> 为了"对称"去删它们反而是无谓的破坏性改动。
