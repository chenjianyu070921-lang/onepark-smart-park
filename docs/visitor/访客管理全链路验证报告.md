# 访客管理全链路验证报告

> 验证范围: 前台生成访客邀请二维码 → 访客扫码签入 → 核销 → gRPC 调 M1 → 门禁设备开门 → 签出
> 验证方式: 通读 `visitor-service` / `device-service`(M1) 跨服务实现 + 编译与单测
> 日期: 2026-09-27  (M2 物业管理服务模块 / 访客通行联动)
> 结论: 链路在代码层面**完整闭环**, 但存在 1 处实现-预期偏差(无 Redis 核销)、1 处语义高估(开门=指令已受理≠门已开), 及若干文档/路由观察项。

---

## 1. 服务与契约

| 环节 | 入口 | 实现 |
| --- | --- | --- |
| 生成邀请二维码 | `POST /api/visitor/invite` | `visitor-service` `VisitorInviteLogic` |
| 扫码签入(核销+开门) | `POST /api/visitor/checkin` | `visitor-service` `VisitorCheckinLogic` |
| 调 M1 开门 | gRPC `DeviceRPC.SendCommand` | `device-service`(M1) `DeviceServer.SendCommand` |
| 门禁设备开门 | MQTT 下行 `onepark/cmd/{deviceId}/down` | `device-service` `DeviceCommandLogic` |
| 签出 | `POST /api/visitor/checkout` | `visitor-service` `VisitorCheckoutLogic` |

- **M1 = `device-service`**: `config.DeviceRPC` 注释明确 "M1 device-service gRPC(调用 SendCommand 开门)"，`ServiceContext` 持有 `devicepb.DeviceServiceClient`。`DeviceServer` 注释: "供 M2 访客签入开门/停车道闸、M3 门禁远程开门、M5 大屏设备状态查询调用"。
- **仓库内 `gateway-service` 不是前端 HTTP 网关**: 它是设备 CoAP/TCP 接入网关(物联设备侧认证与指令回执), 见 `app/gateway-service/etc/gateway.yaml`。`/api/visitor/*` 的 HTTP 路由不在本仓库, 推测由外部 API 网关或前端直连 `visitor-service`。

## 2. 链路逐环节走通与正确性

### 2.1 前台生成邀请二维码 (`VisitorInviteLogic`)
- 校验租户(`x-tenant-id`)、DB 就绪(未配置 MySQL 提前报错, 防 nil panic)。
- **黑名单实时拦截(fail-closed)**: 邀请阶段按手机号/身份证查 `visitor_blocklist`, 命中即拒绝生成通行码; 查询异常也拒绝(防止 DB 抖动绕过黑名单)。
- `genQRCode`: 载荷 `{tenant_id, inviter_id, visitor, expire}` 经 `md5(tenant|inviter|visitor|expire|salt)` 签名后 base64, **防伪造**。salt 来自配置中心, 不硬编码。
- 落 `visitor_record`(`status=1` 待使用), `qr_code` 有唯一索引。
- `go-qrcode` 渲染图片为 base64 PNG(渲染失败降级不阻断, `qr_code` 串始终可用)。
- 发布 Kafka `invite` 事件(尽力而为, 不阻断主流程)。

### 2.2 访客扫码签入 (`VisitorCheckinLogic`)
- 前端/小程序解码二维码得到 base64 串, `POST /api/visitor/checkin{qr_code}`。
- `verifyQRSign`: base64 解码 + constant-time 验签, 防伪造/防时序攻击。
- 按 `qr_code + tenant_id` 查记录(**租户隔离**); `VerifyChannel!=1` 则拒绝(核验方式一致)。
- 黑名单拦截(fail-closed, 命中写 `blacklisted=1` 并拒绝通行)。
- **过期校验**: `ExpireTime < now` → 置 `status=4` 已过期并拒绝。
- **重复核销校验**: `status` 已签入/签出 → "二维码已被核销"。
- **幂等核销 = DB CAS**: `UPDATE ... WHERE id=? AND tenant_id=? AND status=1(Pending)`, `RowsAffected==0` → "已被核销", **绝不重复开门**(并发双扫安全)。

### 2.3 gRPC 调 M1 开门 (`openDoor`)
- `DeviceRPC.SendCommand(ctx, &commonpb.DeviceCommand{DeviceId, Command})`, 短超时 `800ms`(`m1OpenDoorTimeout`)。
- M1 未配置/不可达/超时 → **降级不阻断签入**, `open_msg="门禁未响应，请联系前台人工开门"`。

### 2.4 门禁设备开门 (`device-service`)
- `SendCommand` → `DeviceCommand`: 设备存在性校验 → **离线设备直接拒绝** → 落 `command_log(status=0)` → **MQTT 下行 Publish `onepark/cmd/{deviceId}/down`** → 状态置 `已下发(1)` → 返回 `CommandResult{Success:true, DeviceId}`。
- 物理开门由门禁设备消费 MQTT 报文执行, **异步**, 服务端不等设备回执。

### 2.5 签出 (`VisitorCheckoutLogic`)
- 按 `Id` 或 `qr_code`(二选一) + `tenant_id` 查记录。
- **CAS**: `UPDATE ... WHERE status IN (1,2)` → `3` 签出, `RowsAffected==0` → "已签出, 无需重复签出"(防重复签出覆盖 `checkout_at` 致时长失真)。
- 发布 Kafka `checkout` 事件。

## 3. 验收发现 (Findings)

### F1(中·实现-预期偏差) 链路中无 Redis 核销环节  **[已处理]**
用户描述的 "Redis 核销" 与实现不符。幂等核销由 **DB CAS**(`status=Pending` 条件 + `RowsAffected==0`)实现; Redis 在 `visitor-service` 仅用于 `/api/health`、`/api/readyz` 探针(`ServiceContext.Redis` 已初始化但**未在任何业务逻辑使用**)。
- 若设计/需求要求 Redis 做双重保险、限流或防重放, 则存在实现偏差。
- 若仅为术语混用, 则 DB CAS 已满足幂等目标(且更持久、跨进程一致)。
- **建议**: 与产品/设计确认口径; 若需 Redis, 在 CAS 之外叠加 `SETNX(qr_code, ttl)` 作为防重放第一道闸。

### F2(中·语义高估) "开门成功" = 指令已受理, 不等于门已开  **[已处理]**
`device-service.SendCommand` 是**异步 MQTT 下发**, 仅落库+Publish 即返回 `Success:true`; 物理开门由设备异步执行, 无同步回执。但 `visitor-service.openDoor` 把 `res.DeviceId!=""` 当作开门成功, 回显 `open_msg="开门成功"`, 并回填 `device_id`。
- 实际门可能未开(设备执行失败/超时), 前台与访客会被误导。
- 已有指令结果 Kafka 回执设计(`docs/superpowers/specs/2026-09-21-device-command-kafka-result-design.md`)**未接入**此路径。
- **建议**: ① 文案改为 "开门指令已下发/已受理"; ② 或接入 Kafka 结果回执, 真正将 `visitor_record` 推进到 "已开门" 状态, 避免虚高确认。

### F3(低·文档缺口) M2 设计文档缺失  **[已标注]**
`visitor.api` 注释引用 "docs/M2物业管理服务模块设计文档(V1.1) 第三节/第十一节", 但仓库内不存在该文档(`docs/design` 仅有 `coap-integration-plan.md`)。链路以代码为准, 建议补齐权威设计文档。

### F4(信息·路由) 前端→visitor-service 路由未在本仓库
仓库内 `gateway-service` 是设备 CoAP/TCP 接入网关, 非前端 HTTP API 网关; `/api/visitor/*` 路由未在本仓库配置。部署时需确认外部 API 网关或前端直连 `visitor-service` 可达, 否则前端调不通 invite/checkin/checkout。

### F5(低·多门岗) 开门设备由配置决定, 二维码不绑定门岗
开门设备来自 `Door.DeviceID`(或 device-service 回执), 二维码内容不含目标门岗。多入口园区需产品确认 "哪个门开"。

### F6(信息·安全正向) 稳健设计
- 二维码 md5 签名 + constant-time 验签防伪造;
- 黑名单 fail-closed(DB 异常即拒绝, 防绕过);
- `tenant_id` 贯穿 RBAC 行级隔离;
- CAS 防并发重复核销/签出;
- M1 不可达降级不阻断签入, 提示人工兜底。

### F7(信息·权限边界) 开门未走 access-control-service
本链路开门直接调 `device-service`, 未经过 `access-control-service`(门禁权限)集中校验; 权限兜底由 visitor-service 自身的黑名单+状态+过期校验承担。若产品期望统一门禁策略中枢, 需评估是否经 `access-control-service`。

## 6. 已落地修复(F1/F2/F3, 2026-09-27)

- **F1(已修·真实 Redis 核销)**: `visitorcheckinlogic.go` 在 DB CAS 之前新增 **Redis SETNX 第一道闸** `redeemLockKey(recID)`(`visitor:redeem:{id}`, TTL=至二维码过期, 无过期兜底 24h)。SETNX 成功=获核销权, 失败=窗口内已核销直接拒绝; **Redis 不可达时降级跳过此闸, 退回 DB CAS 单一防护(与原行为一致), 不误伤正常签入**。DB 核销失败/被并发抢先时 `releaseRedeemLock` 释放锁, 避免残留锁误伤。新增 `redeemTTL/redeemLockKey/releaseRedeemLock` 三个纯函数并补 `visitorcheckinlogic_redeem_test.go`(DB-free 单测)。
- **F2(已修·开门语义)**: `openMsgSuccess` 由"开门成功"改为"**开门指令已下发**"; 同步 `openDoorMsg` 注释与 `visitor.api`/`types.go` 的 `OpenMsg`/`DeviceID` 注释, 明确 device-service `SendCommand` 为异步 MQTT 下行, "成功"=指令已受理≠物理门已开(消除虚高确认)。
- **F3(已标注)**: `visitor.api` 头部注明所引用的 M2 设计文档未纳入仓库, 链路以本契约+代码为准(详见本报告); api 核心注释同步"Redis SETNX + DB CAS 双保险核销"。

## 7. 结论

访客管理全流程在代码层面**闭环且已按验证发现加固**: 二维码防伪造、租户隔离、黑名单 fail-closed、Redis SETNX + DB CAS 双保险幂等核销、M1 开门异步下行语义已校正、签出防重复均落地。剩余建议: **F4 前端路由**(确认外部 API 网关/直连可达)、**F2 后续**(可选接入 Kafka 开门结果回执做真正"已开门"确认)、**F5 多门岗**待产品确认; F6/F7 为安全正向观察项。
