## 场景一：停车设备事件 → Kafka → parking-service 消费联动（P0）

### 1.1 链路说明（已实现）
- 事件源（三路同构，标准信封）：`event-dispatcher`(MQTT) / `device-service`(HTTP fallback) / `tcp-gateway`(帧解析) → Kafka `device-telemetry`
- parking-service 后台消费者（`internal/svc/consumer.go`，Group 独立）消费 `device-telemetry`：
  - `normalizeTelemetry` 兼容标准信封与旧扁平格式；业务字段在 payload：`{"tenant_id":1,"plate_no":"苏A12345","vehicle_type":2}`（1月卡 2临时 3VIP 4异常）
  - **入场**：建 `parking_record`（status=1 停车中）→ 生产 `parking-entry`
  - **离场**：按事件时间 `occurred_at` 计费（CalcFee：月卡/VIP 0、临时≤15min 0、超出 5元/h 向上取整）→ 置已完成 → 生产 `parking-exit`
  - **异常车**：入场即生产 `alarm-event`
  - HTTP 入口 `POST /api/parking/entry|exit` 与 Kafka 路径行为一致，便于联调

## 场景二：workorder-service gRPC 供大屏调用验证（P1）

### 2.1 接口与统计口径（已实现并优化）
`workorderpb.WorkorderService/ListWorkOrders`（9091），返回：
| 字段 | 口径 |
|---|---|
| total | 工单总数（按 tenant 过滤） |
| pending_count | 待处理 = 待派单(0)+处理中(1) |
| today_count | 今日新建（created_at ≥ 今日零点） |
| completed_today | 今日完成（status=3 且 finished_at ≥ 今日零点） |
| avg_process_minutes | 已完成工单平均处理时长(分钟) |
| completion_rate | 完成率(%) = 已完成/总数×100 |
| list | 分页摘要（可按 status 过滤） |

**统计查询优化（本次）**：原实现 5 次 COUNT + 1 次 AVG 串行扫表；现合并为**单次聚合扫描**（COUNT/SUM/AVG + COALESCE），大屏高频轮询下统计查询开销降为原来的 1/6。
