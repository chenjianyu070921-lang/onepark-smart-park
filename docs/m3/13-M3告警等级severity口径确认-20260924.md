# M3 ↔ M5 告警等级（severity）口径确认

> 发起方：M3 成员4 · 确认方：M5 成员6
> 日期：2026-09-24 · 状态：**M3 结论=不翻转 severity，另用 `priority` 显式下发派单优先级；请 M5 书面回复确认**

---

## 一、待确认的分歧

| 口径 | 数值方向 | 出处 |
|------|---------|------|
| M3 `severity` | **1提示 / 2一般 / 3严重 / 4紧急（值越大越严重）** | `docs/m3/04` §5.1；`alarm-service` 全链路与种子 SQL 均按此实现 |
| M5 确认书注释 | 1 critical / 2 major / 3 minor（值越小越严重） | M5 确认书注释（**未落代码**） |

当日任务表的建议是「统一为 M5 的 1=critical 最严重（即翻转 M3 的 severity）」。
**M3 的建议是不翻转**，理由如下。

---

## 二、为什么不建议翻转（三条证据）

1. **M5 已在按 M3 语义编码**：`dashboard-service/internal/provider/alarm.go:11-16` 的等级常量为
   `info=1 / minor=2 / major=3 / critical=4`，大屏读的就是 M3 语义。翻转后大屏等级与告警真实等级**同时反向**。
2. **翻转会让两条链路同时反向**：大屏展示（`severity` 直读）+ 派单优先级（由 `internal/dispatch` 换算），
   两边代码各自看起来都自洽，但整体语义与运营认知相反 —— 这类缺陷只在真实告警发生时才暴露。
3. **M3 已把派单语义显式化，不再依赖任何隐式映射**：`onepark.alarm.event` 载荷新增 `priority` 字段，
   由 M3 按 `4→1 / 3→2 / 2→3 / 1→3` 换算为 **M5 语义**后随事件下发（见 §三）。
   M5 消费方**无需反推 severity**，也就不存在"两边各猜一套"的风险。

---

## 三、已落地的机制（M3 侧，2026-09-21 Wave 10）

| 项 | 说明 | 位置 |
|----|------|------|
| 默认映射表 | 4紧急→1紧急 / 3严重→2高 / 2一般→3普通 / 1提示→3普通 | `internal/dispatch/priority.go` |
| 换算时机 | **在发布器统一补齐**，create 与 resolve 两条路径都不会漏填 | `internal/notify/notify.go` |
| 可运营覆盖 | 配置 `Dispatch.LevelPriority`（如把"严重"也提到 1），非法条目打 WARN 后按默认 | `alarm-api.yaml` |
| 一致性 | 同设备 create / resolve 分区键一致、优先级一致（防"单据刚建就被关闭"、优先级抖动） | `notify` 用例锁定 |

**M5 只需按 `priority` 取派单优先级（1紧急/2高/3普通），按 `severity` 取展示等级（1提示~4紧急）。**

---

## 四、若 M5 仍坚持翻转 severity，需同步改动清单（成本提示）

1. `deploy/sql/m3_mysql_tables.sql` 三条种子规则 `level` 全部改写；
2. `deploy/sql/m3_mysql_migrations.sql` 追加存量 UPDATE（含已落库历史告警）；
3. `alarm-service` 全量等级常量、排序（等级降序）、阈值判定、ES 双写文档；
4. `docs/m3/04` 契约 §5.1 与全部示例；
5. **M5 侧同时改** `dashboard-service/internal/provider/alarm.go` 常量与前端展示 ——
   只改一边必然出现"等级显示反了"。

> 结论：翻转的收益（注释与代码对齐）远小于成本与风险，且 `priority` 已经解决了真正的派单问题。

---

## 五、请 M5 回复的三点

1. 是否同意 **severity 不翻转**（M3 语义原样发送）？
2. 派单优先级是否确认取新增的 **`priority`** 字段（1紧急/2高/3普通）？
3. `onepark.alarm.event` 载荷**多一个 `priority` 字段**（create 与 resolve 都带）——
   按 name 取值无影响；若按固定字段数解析需同步。
