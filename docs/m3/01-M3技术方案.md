## 2. 业务范围与边界

### 2.1 In Scope（M3 负责）

- **视频监控**：摄像头点位管理、在线状态、视频流地址管理（RTSP/GB28181 接入地址）  
- **门禁告警**：门禁异常事件（非法闯入、门磁超时、胁迫报警）产生的安防告警
- **人员检测**：基于摄像头/门禁的人员检测事件接入与告警
- **安防事件处理**：消费 M1 设备事件，规则匹配生成告警，告警全生命周期管理
- **告警规则管理**：阈值 / 组合条件 / 时间窗口规则的 CRUD 与启用禁用
- **告警实时推送**：WebSocket 实时推送到管理后台与安防大屏
- **历史告警查询**：基于 Elasticsearch 的多条件检索与聚合统计
- **门禁权限及远程开门**：人员授权、白名单、时间段权限、远程开门与操作审计
- **摄像头及视频流管理**：点位 CRUD、状态缓存、流地址下发

### 2.2 Out of Scope（非 M3 职责，禁止越界实现）

| 能力             | 归属                                    | M3 的边界                                     |
|----------------|---------------------------------------|--------------------------------------------|
| 设备注册/物模型/影子    | M1 device-service / shadow-service    | M3 只消费设备 ID，不维护设备主数据                       |
| MQTT/EMQX 命令通道 | M1 gateway-service / event-dispatcher | M3 通过 gRPC 调 M1 `SendCommand`，**不直连 EMQX** |
| JWT 签发与校验      | M6 auth-service                       | M3 只透传 Token，由网关注入 UserId                  |
| RBAC 权限模型      | M6 user-manage                        | M3 调 M6 `CheckPermission`，不自建权限表           |
| 物业工单 / 调度工单    | M2 workorder / M5 dispatch            | M3 只发 Kafka 事件，不创建工单                       |
| 视频转码 / AI 识别算法 | 不涉及                                   | M3 只管理流地址与状态，**不实现编解码与算法**                 |
| 遥测时序数据存储       | M4 + TDengine                         | M3 不写 TDengine                             |

## 3. 整体架构

### 3.1 架构分层

```
┌─────────────────────────────────────────────────────────┐
│  接入层  管理后台 / 安防大屏 → Gateway(:8080)            │
│          JWT 鉴权 · RequestId 注入 · 限流 · 路由          │
└───────────────────────────┬─────────────────────────────┘
                            │ HTTP / WS
┌───────────────────────────▼─────────────────────────────┐
│  M3 业务层                                                │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐     │
│  │alarm-service │ │access-control│ │video-service  │     │
│  │ 规则管理      │ │ 权限/开门    │ │ 摄像头/流     │     │
│  │ 规则引擎      │ │ 通行记录     │ │ 状态缓存      │     │
│  │ 告警生命周期  │ │ 审计         │ │               │     │
│  │ WS 推送       │ │              │ │               │     │
│  └──────┬───────┘ └──────┬───────┘ └───────┬───────┘     │
│         │  Kafka消费      │ gRPC            │ gRPC        │
└─────────┼────────────────┼─────────────────┼────────────┘
          │                │                 │
┌─────────▼────────────────▼─────────────────▼────────────┐
│  数据层  MySQL(alarm/access/video_db) · Redis · ES · Kafka│
└─────────────────────────────────────────────────────────┘
```

### 3.2 alarm-service 内部模块划分（Day 2 落地骨架依据）

```
alarm-service/
├── internal/
│   ├── config/         # Config: MySQL/Redis/Kafka/ES/Nacos
│   ├── svc/            # ServiceContext: DB, Redis, KafkaPusher/Consumer, ES, WS Hub
│   ├── handler/        # HTTP handlers (goctl 生成)
│   ├── logic/          # 业务逻辑
│   ├── model/          # GORM Model + DAO (Day 3)
│   ├── rule/           # 【规则引擎】阈值/组合/时间窗口 Evaluate (Day 5-7)
│   ├── mq/             # 【Kafka】Consumer Group 消费 M1 事件 (Day 6)
│   ├── dedup/          # 【Redis】告警冷却去重 (Day 8)
│   ├── ws/             # 【WebSocket】Hub + 连接池 + 心跳 (Day 11-12)
│   └── search/         # 【ES】历史告警检索 (Day 13-14)
```

**分层铁律**：`handler → logic → model/rule/dedup/search`，handler 不直接操作存储；规则引擎、去重、WS、ES 各自独立包，通过 `svc.ServiceContext` 注入，便于单测。

### 3.3 部署形态

- 三服务各自独立 go module（`app/alarm-service` 等），**互不 import**，跨服务调用走 gRPC（proto module 共享）
- 共用 `common` 包（response/errorx/ctxdata/middleware）
- 容器化由 `deploy/docker-compose.yml` 统一编排（中间件已就绪）

## 4. 技术选型与中间件使用场景

| 组件                | M3 使用场景                                                                                                                 | 关键设计                                                                                                                                       | 涉及接口                    |
|-------------------|-------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------|-------------------------|
| **Kafka**         | ① 消费 M1 设备事件触发告警（Consumer Group）<br>② 告警确认/解决后向 M5 发事件（Producer）                                                        | Topic：`onepark.device.event`（消费）、`onepark.alarm.event`（生产）<br>消费组：`alarm-service-group`<br>幂等：RequestId 去重<br>失败：死信队列 DLQ                  | #44 #40                 |
| **Redis**         | ① 告警冷却去重（`SET NX + TTL`）<br>② 规则缓存（规则变更失效）<br>③ 活跃告警计数缓存<br>④ 门禁权限缓存<br>⑤ 摄像头在线状态缓存                                     | Key 前缀 `alarm:cooldown:{deviceId}:{eventType}`<br>规则缓存 `alarm:rule:{id}`<br>权限缓存 `access:perm:{personId}`<br>状态 `video:camera:status:{id}` | #36 #38 #44 #45 #46 #50 |
| **MySQL**         | 告警规则、告警记录、门禁权限、通行记录、摄像头点位的主存储                                                                                           | 三库分离：`alarm_db`/`access_db`/`video_db`，**禁止跨库 JOIN**<br>GORM + 软删除 + 乐观锁                                                                   | #34-#51                 |
| **Elasticsearch** | ① 历史告警多条件检索（时间/等级/设备/区域/事件类型）<br>② 门禁通行记录检索<br>③ 聚合统计（按级别分布）                                                            | 索引：`alarm_history`、`access_record`<br>写入：告警入库后异步双写<br>查询：ES DSL + 分页                                                                       | #41 #48                 |
| **WebSocket**     | 告警实时推送到管理后台 / 安防大屏                                                                                                      | 端点 `/ws/alarm`<br>gorilla/websocket + Hub 连接池<br>心跳保活（ping/pong）+ 断线重连<br>广播：新告警 + 状态变更                                                    | #42 #39                 |
| **gRPC**          | ① 对外提供 `GetActiveAlarms`（供 M5 大屏聚合）<br>② 作为 Client 调 M1 `SendCommand`（远程开门）<br>③ 作为 Client 调 M6 `CheckPermission`（权限校验） | proto：`proto/alarm/alarm.proto`、`proto/access/access.proto`<br>共享 `proto/common`（PageRequest/AlarmEvent/DeviceCommand）                     | #43 #47                 |
| **MQTT/EMQX**     | **不直连**。远程开门经 M1 gRPC → M1 下发 MQTT → 设备                                                                                 | M3 只记录命令结果审计                                                                                                                               | #47                     |

| **M5** dashboard-service | M5 → M3      | gRPC `GetActiveAlarms`       | 大屏聚合查活跃告警数                | proto 待定义              | ⚠️ proto 仅 Ping，待补 |

## 8. 统一规范（M3 必须遵守）

| 规范项       | 约定                                                | 依据                                |
|-----------|---------------------------------------------------|-----------------------------------|
| 响应体       | `{code, msg, data}`，成功 `code="0"`                 | `common/response`                 |
| 错误码       | `M3-E-1xxx`（告警）/ `M3-E-2xxx`（门禁）/ `M3-E-3xxx`（视频） | `common/errorx`，**Day 1 需追加常量**   |
| RequestId | 网关注入 `x-request-id`，M3 透传并写入日志                    | `common/ctxdata`                  |
| 用户信息      | 从 ctx 取 `x-user-id`，用于告警确认人/操作审计                  | `common/ctxdata`                  |
| 分页        | `page` / `page_size`，响应含 `total`                  | `common.PageRequest/PageResponse` |
| 数据库       | 每服务独立库，禁止跨库 JOIN                                  | README 公共约定                       |
| 配置        | 环境变量占位 `${VAR}`，参考 `deploy/.env`                  | README 公共约定                       |
