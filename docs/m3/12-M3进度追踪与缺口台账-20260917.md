新增路由：`GET /api/alarm/dlq`、`POST /api/alarm/dlq/:id/replay`

**两个关键设计取舍**

1. **重放前先删 L1 幂等键**。死信多是「过了 L1 之后的下游步骤失败」产生的，`alarm:dedup:{requestId}` 仍在 24h TTL 内；不清键则重放被判为「已处理」直接返回 nil，表现为**点了重放却什么都没发生**。重复落库由 L3 唯一索引 `uk_request_rule` 兜底。
2. **重放失败不更新台账状态**（保持待处理）。死信的价值就是「失败可见」，标记为已重放会让它永远消失；反之主链路成功但状态回写失败**必须报错**，否则该条会被反复重放、每次都真实产生告警。两者都有单测锁定。

### 8.2 P1-4 硬编码回退改为显式开关（已交付）

新增 `Rule.DisableLegacyFallback`（`config.go` + `alarm-api.yaml`），`evaluateRules` 关闭回退时打 WARN 后丢弃事件。

> **为何用负向开关**：Go 零值为 `false` = 不关闭回退。测试与非 yaml 入口是直接构造 `ServiceContext` 的，若用正向 `LegacyFallback` + `default=true`，零值会变成「关闭」，在**没人改过配置**的情况下静默漏报。已有回归用例 `TestEvaluateRules_ZeroValueConfigKeepsFallback` 锁死这条语义。

### 8.3 顺带修掉的既有缺陷

`TestIntegration_RecordList` **用例不可重复执行**：建表脚本为 `CREATE TABLE IF NOT EXISTS`（无 DROP）而用例不清理数据，第二次运行记录累加，租户隔离断言 `total=3` 必然失败（实测第二次得到 6）。已补清理逻辑，连跑两次验证通过。

> 这类缺陷只在「真的重复跑」时才暴露——这正是 P0-1 在线验收的价值所在。

### 10.3 补强过程中发现的真实缺陷（已修）

**`rule.ParseSpec` 扁平写法丢失操作符**：`Spec` 结构体只声明了 `operator` 标签，
当规则条件写成文档 07 风格的 `{"field":"event_type","op":"eq",...}`（扁平形式）时，
操作符被解析为空串，报错为 `不支持的操作符 ""` —— **而报错里的条件看起来完全合法**，极易误判成"配置写错"。

- 修复：`Spec` 增加 `Op` 字段 + `Spec.OperatorOf()` 归一（与 `Condition.OperatorOf` 同一套兼容策略）
- 回归：`TestParseSpec_FlatFormAcceptsBothOperatorKeys`（`op` / `operator` / 符号三种写法）
- 暴露方式：种子 SQL 的契约测试（`internal/rule/seedrule_test.go`）在首次运行时立刻失败并定位

> 这条缺陷此前从未暴露，说明扁平写法在本仓上线后**从未被真实使用过**；
> 也说明 §7.6 那条教训（不能只靠 grep 下结论）同样适用于"某条代码路径是否被执行过"。
