### 7.6 一次误判与撤销（重要教训）

Wave 2 开始时我依据「全仓 grep `os.Getenv` 在 access-control-service 零命中」判定该服务没有 MySQL 集成用例（记为 P1-11）。**该结论错误。**

- **误判根因**：仓库 `.gitignore` 含 `**/*_test.go`，而 `search_content` / ripgrep **默认遵守 .gitignore**，因此 `os.Getenv` 在所有 `*_test.go` 里的命中全部不可见，搜出来就是「0 命中」。
- **已验证纠正**：注入 `ACCESS_TEST_DSN` 后
  ```
  --- PASS: TestIntegration_OperateLogCreate (0.07s)
  --- PASS: TestIntegration_GrantIdempotentAndRevoke (0.05s)
  --- PASS: TestIntegration_RecordList (0.03s)
  ok  access-control-service/internal/model 0.828s
  ```
  授权幂等、撤销、通行记录分页筛选排序、开门审计三种结果 —— **DB 读写路径已真实验证**。
- **已撤销**：P1-11 从缺口台账中删除；误判期间新建的重复用例文件已删除（避免幽灵代码）。

> **教训固化（KI-17）**：本仓任何"某能力不存在 / 某服务没有 X"的结论，**不能只靠全仓 grep 得出**——测试文件、生成物、本地配置大概率被 ignore。必须先确认被搜目标是否在 .gitignore 覆盖范围内，必要时用 `read_file` / `search_file` 直读目录验证。**这条同样适用于评价任何外部审计报告。**

新增路由：`GET /api/alarm/dlq`、`POST /api/alarm/dlq/:id/replay`

**两个关键设计取舍**

1. **重放前先删 L1 幂等键**。死信多是「过了 L1 之后的下游步骤失败」产生的，`alarm:dedup:{requestId}` 仍在 24h TTL 内；不清键则重放被判为「已处理」直接返回 nil，表现为**点了重放却什么都没发生**。重复落库由 L3 唯一索引 `uk_request_rule` 兜底。
2. **重放失败不更新台账状态**（保持待处理）。死信的价值就是「失败可见」，标记为已重放会让它永远消失；反之主链路成功但状态回写失败**必须报错**，否则该条会被反复重放、每次都真实产生告警。两者都有单测锁定。

## 十一、Wave 5：告警规则缓存主动失效（2026-09-18）

> 背景：§2.1 把规则引擎列为「完成」，依据是它能从 DB 加载规则；但**加载时机**依赖进程内 30s 快照 TTL（`ruleCacheTTL`），规则变更后最长 30s 内仍按旧规则判定。本轮补上主动失效，让「规则 CRUD 后立即生效」成为事实而非承诺。

### 11.1 变更清单

| 层 | 变更 |
|----|------|
| `internal/rule/engine.go` | 新增 `Invalidate()`：加锁后置空 `cached` / `cacheLoad` / `cachedAt`，使下一次评估重新从 `Store` 加载 |
| `internal/logic/rulelogic.go` | 新增 `invalidateRuleCache()` 辅助函数，`CreateRule` / `UpdateRule` **写库成功后**各调一次 |
| `internal/rule/engine_test.go` | 新增 3 例：`...Immediately` / `...DoesNotPreload` / `...ConcurrentSafe` |

### 11.2 三个设计决策

**① 为什么是「失效」而不是「立即重载」**

| 方案 | 问题 |
|------|------|
| 立即重载 | 连续改 N 条规则退化为 N 次全表查询；且把 DB 错误引入「改规则」路径 —— 一次临时抖动就导致**规则改不动** |
| 失效（采纳） | O(1) 且天然合并（连续 N 次失效等价于 1 次）；错误留给评估路径，那边已有成熟处理（上抛 → 消费端重投），且不丢事件 |

**② 为什么只接 Create / Update，不接 Delete**

本服务规则**没有 Delete 接口**（`rulelogic.go` 只有 C/U/R/L）。不为虚构的调用点写代码。
其中 Update 覆盖了「禁用规则」（`status=0`）—— 这是最需要立即生效的一条：**被运维禁用的规则若还继续报 30 秒，现象与「规则没配好」完全一样，无法区分。**

**③ 为什么这里不用负向开关**

与 §8.2 的 `DisableLegacyFallback` 相反，这里**没有配置语义**，不受「测试/非 yaml 入口直接构造 `ServiceContext` 导致零值失真」的影响，故直接用正向的方法调用。判定依据：**只有当该项存在 yaml 配置项时，才需要考虑零值语义。**

### 11.3 两个边界行为

| 场景 | 行为 | 理由 |
|------|------|------|
| 引擎未初始化（MySQL 未配置） | 静默跳过 | 此时规则库本身不可用，也没有快照可失效 |
| 失效后加载失败 | 返回空规则集并上抛，由 `DisableLegacyFallback` 决定丢弃或回退 | **不拿陈旧规则继续判定**。代价是放弃了「用旧快照兜底」这条路，但它正是本次要消灭的行为 |

## 十二、Wave 6：关键词检索与分词器可配置（2026-09-18）

### 12.1 原 P1-8「ES 未配 ik 分词」是一个**伪命题**

动手前核对契约，发现两处自相矛盾，直接改 mapping 是空转：

| 事实 | 出处 |
|------|------|
| 契约 #41 的 Query 参数**没有关键词字段** | `docs/m3/04` §#41（原 Query 列表 8 项，无 keyword） |
| mapping 却给 `content` 配了 `ik_max_word` | `docs/m3/04` §7.1 |

**ik 分词服务的对象是全文检索；接口根本不接受关键词，装了 ik 也没有任何调用路径。**
所以真正的缺口不是「没配 ik」，而是「**没有关键词检索能力**」—— ik 只是它的前置条件。

据此把 P1-8 重新定义为：先补关键词检索，再让分词器可配置。

|----|------|
| `types/types.go` | `ListAlarmsReq` 新增 `Keyword`（`form:"keyword,optional"`，**不传即不参与检索**） |
| `search/search.go` | `Query` 新增 `Keyword` |
| `search/esclient.go` | ① `indexMapping` 常量 → `buildIndexMapping(analyzer)` 生成函数<br>② `ESClient` 新增 `analyzer` 字段，`NewESClient` 增加第 5 个参数<br>③ `EnsureIndex` 在插件缺失时降级为默认分词器并记 WARN<br>④ `buildQueryBody` 关键词生成 `match` on `content` |

| `proto/video/video.proto` | 关闭 TODO，写明「全仓无 `videopb` 消费方」与将来变更条件 |

### 12.3 三个设计决策

**① 为什么 MySQL 降级路径也要支持关键词，而不是「ES 不可用就忽略」**

忽略会静默返回**未过滤的全量**：用户以为搜过了，实际什么都没过滤。这类错误不报任何异常、
列表看起来完全正常，比「召回略窄」难发现得多。宁可让两条路径的召回粒度不同
（ES 分词后更宽，MySQL 是子串），也不制造静默错误。

**② 为什么 `match` 放 `bool.filter` 而不是 `bool.must`**

排序固定为「等级降序 + 时间降序」，**不按相关性打分**，因此 `must` 的打分语义用不上；
放 `filter` 还能复用 ES 的 filter 缓存。

**③ 为什么分词器可配置 + 缺失时降级，而不是硬编码 ik**

官方镜像不含 ik 插件，硬编码会让 `PUT /{index}` 直接 400 —— 表现为「配了 ES，检索反而完全不可用」。
降级后中文按单字切分，检索质量差但**功能在**。这个取舍与 §8.2 `DisableLegacyFallback` 的方向相反，
原因不同：那边是「宁可暴露问题也不要静默漏报」，这边是「索引建不出来 = 整体不可用」，
属于可用性兜底而非正确性兜底。

### 12.4 顺带修掉的隐患：LIKE 通配符转义

用户输入 `50%` 若不转义，会拼成 `LIKE '%50%%'` 匹配所有行。
这不是 SQL 注入（参数化已挡住），而是**语义劫持**：用户以为在搜，实际返回全量，且无任何报错。
已加 `escapeLike`（先转义 `\`，再转义 `%` `_`）+ `ESCAPE '\'`。

### 13.3 一个值得单独记录的教训：不能复用 `UpdateAlarmStatusReq`

首版实现直接复用 `UpdateAlarmStatusReq` 解析请求体，结果 6 个用例里 3 个失败：

```
{"code":"M3-W-1001","msg":"请求参数解析失败"}
```

根因：`Action` 的 tag 是 `json:"action"`（**没有 `,optional`**），go-zero 视为必填。
而按 #39/#40 契约调用时 body 里本就不该出现 `action`（动作写在路径上）——
**复用让"正确调用"在参数校验阶段就被拒**。该字段在 `/status` 接口上从未暴露问题，因为那里调用方总会传 action。

修正：新增专用入参 `AlarmActionReq`（`remark` 为 optional，无 `action` 字段），并在其注释里写明「勿合并回一个结构体」。

> **教训固化（KI-18）**：复用请求结构体时，必须逐个字段检查 `optional` 约束是否仍成立。
> 结构体是为某个入口设计的；换个入口（尤其改成「参数由路径决定」）时，原本合理的必填约定
> 会退化成**静默拦截正确请求**的规则。这类问题静态编译与 logic 层测试都发现不了 ——
> 本次由 alarm-service 首个 handler 层用例捕获。

### 15.2 关键澄清：`alarm-event` 与 `onepark.alarm.event` 是两条链路

`common/kafka/topics.go` 刻意分成两个 topic，当日任务描述把它们当成了一条：

| topic | 生产者 | 消费者 | 载荷 |
|---|---|---|---|
| `alarm-event` | **M1** event-dispatcher | M5 dispatch（自动建单） | M1 信封：`request_id`/`device_id`/`device_type`/`event_type`/`occurred_at`/`payload`/`source` |
| `onepark.alarm.event` | **M3** alarm-service | M5（告警生命周期） | M3 载荷：`alarm_id`/`action`/`alarm_type`/`severity`/`status`/... |

**结论：M5「告警→自动建单」走的是 M1 的 `alarm-event`，与 M3 代码无关**，不需要 M3 改动，也不该让 M3 去对齐 M1 的信封。
M3 负责的是后者（告警生命周期事件）。两者混在同一条 topic 会让消费方解码互相打架（缺字段即丢消息）。

### 15.3 修复一（P0）：M1 报文入站兼容 —— 修的是一个"静默丢告警"

`event-dispatcher` 的 `Message` 用 **`occurred_at`** 承载事件时间，且不带 `tenant_id`/`area_id`；
而 M3 的 `DeviceEvent` 原本只读 **`timestamp`**。直接按 M1 报文解析 → `Timestamp` 恒为 0。

后果链：`request_id` 缺失时 `IdempotentID()` 降级为 `sha1(deviceId|eventType|timestamp)`，
时间恒为 0 **意味着同一设备同一类型的所有事件指纹相同** → 第二条起被 L1 幂等判为已处理直接丢弃。
**现象不是报错，是告警静默变少。**

修复（`svc/consumer.go`）：
- `DeviceEvent` 增 `OccurredAt` 字段 + `EventTime()` 归一化（两者都有时以 `timestamp` 为准，不影响 device-service 通道）；
- `tenant_id=0` 时打 WARN：M3 不维护设备主数据，**无法反查也不允许臆造租户**，
  但该告警会以 `tenant_id=0` 落库 → 后台/大屏按租户查不到、WS 因"宁可不推也不推错园区"跳过。
  这条日志是"告警产生了却没人看得到"的唯一线索。彻底解决依赖 P0-13。

### 15.4 修复二（P1）：补「告警产生」事件

`notify.go` 注释从设计之初就写了"带 action 是为了让 M5 能区分产生与解决"，但长期只发了 `resolve` ——
M5 只能看到告警的终点。补齐 `ActionCreated = "create"`：

- `Notifier` 接口增 `AlarmCreated`；`KafkaNotifier` 抽出 `publishAlarmEvent` 复用重试与超时；
- 消费链路落库成功后调用，**失败只记日志、不回滚也不阻塞位移**。

> 为什么这里与 resolve 的错误处理不同：告警已落库后返回 error 只会让消费端重投，
> 而重投会被 L1/L3 幂等拦下，**通知永远补不上**，却把消息推到死信。
> resolve 是 HTTP 请求路径，需要返回错误码让调用方补偿 —— 两者语境不同，不该强行统一。

### 16.2 告警等级 → 工单优先级映射（真缺口 #1）

| 层 | 变更 |
|----|------|
| `internal/dispatch/priority.go`（新增） | 映射表 `Table` + `DefaultTable`：4紧急→1紧急 / 3严重→2高 / 2一般→3普通 / 1提示→3普通；`ParseTable` 合并配置覆盖并逐条返回被拒原因 |
| `internal/notify/notify.go` | `AlarmEvent` 新增 `priority` 字段；发布器在未显式传值时按等级自动补齐（新增 `Option`/`WithPriorityTable`，**不改构造函数签名**，既有调用方零改动） |
| `internal/config/config.go` + `etc/alarm-api.yaml` | 新增 `Dispatch.LevelPriority` 覆盖项（运营可按园区调派单紧急度） |
| `internal/svc/servicecontext.go` | 装配映射表；非法覆盖项打 WARN 后按默认继续 |

**三个关键取舍**

1. **方向必须显式翻译，不能透传**：M3 等级值越大越严重，M5 优先级值越小越紧急 —— 方向相反。
   透传会让"紧急告警"以"普通"优先级派出，而代码表面完全自洽。默认表 + 用例（`TestDefaultTable_SeverityMapsToFewerBuckets`）双向锁定方向。
2. **优先级在发布器补齐，而不是让两个调用点各自填**：`resolve` 路径在 `logic`，`create` 路径在 `svc`，
   任何一条漏填都会让 M5 收到 0（不在 1/2/3 合法域内，会被 `validPriority` 拒单）。
   放在发布器后，**将来新增调用点也漏不掉**。
3. **"提示/一般"同落普通**：M5 只有三档，编造一个"低=4"会被 M5 校验直接拒 ——
   结果是低等级告警一条都派不出去。宁可三档共用，也不制造必然被拒的单据。

**未做（需与 M5 书面确认后才动）**：`severity` 数值方向本身的口径分歧（M3 越大越严重 vs M5 确认书写的越小越严重）仍未定；
本轮**没有翻转 severity**，而是新增 `priority` 把 M5 语义显式下发，使派单不再依赖那条未确认的映射。

**边界（必须显式声明，避免被误读为"已实现完整录像能力"）**：
M3 实现的是**策略层 + 回放授权层** —— "什么时候录、录多久可回看、哪段能回放"。
媒体文件本身仍由流媒体网关承载（`docs/m3/11` 阶段二），因此：
- 未配置 `Record.PlaybackBaseURL` 时 `playback_url` 为空串，但**时间窗口照常返回**（不编造地址）；
- 回放结果由计划推导，**不探测网关侧文件是否真的存在**（这一点写在接口文档的语义边界里）。

**四个关键取舍**

| 取舍 | 理由 |
|---|---|
| 三重裁剪（查询区间 → 计划创建时间 → 保留期），后两者取**较晚者** | 只取其一会出现"新建计划能查到上个月的录像"或"已过期却提示可回放"；前者是凭空造录像，后者是给出必然 404 的链接 |
| 不跨零点（22:00-06:00 拆两条） | 跨零点属于哪一天没有唯一解释口径，强拆再合并会让"这段到底有没有录"说不清楚 |
| 回放签名多绑 `start`/`end` | 沿用只绑 `camera_id+expires` 的实况签名时，一个合法签名可被挪到同一摄像头的**任意时段**重放，时段授权形同虚设 |
| 离线/故障设备**不阻断**回放 | 查的是网关侧历史文件；把"设备坏了"与"不能看证据"绑在一起，会让排障时最需要录像的场景恰恰拿不到 |
