# M3 — 告警处理流程（从设备事件到告警闭环）

> 2026-09-28 · 适用 alarm-service · 配套文档：07（规则引擎）、06（Kafka 消费与幂等死信）、08（滑动窗口与冷却去重）
> 本文描述**单条告警的完整生命周期**：产生 → 落库 → 推送 → 确认 → 解决 → 通知，以及每一环失败时的处置口径。

---

## 1. 全景

```
M1 设备上报
   │  Kafka topic: onepark.device.event
   ▼
[1] 解析与归属校验      svc/consumer.go#HandleDeviceEvent
   │  解析失败 / 缺 device_id / 缺 event_type  → ErrMalformedEvent（不可重试，直接入台账）
   │  缺 tenant_id                            → 按 Tenant.MissingPolicy 入台账或降级
   ▼
[2] 规则评估            rule/engine.go#Evaluate  （详见 docs/m3/07）
   │  未命中任何规则 → 记 Info 后丢弃（有计数日志，不做静默丢弃）
   ▼
[3] L1 消息幂等         alarm:dedup:{requestId}   TTL 24h
   │  命中 → 视为已处理，返回 nil（提交位移）
   │  不可用 → 返回 error（不提交位移，等待重投）
   ▼
[4] L2 业务冷却         alarm:cooldown:{deviceId}:{eventType}:{ruleId}   TTL 60s
   │  冷却中 → 抑制本条（不落库、不报错）
   │  不可用 → 释放 L1 键并返回 error
   ▼
[5] 落库（L3 兜底）      uk_request_rule(request_id, rule_id)
   │  唯一索引命中 → 视为已处理，继续下一条草稿
   │  其它失败      → 释放 L1 键并返回 error
   ▼
[6] 旁路（失败均不阻塞主链路）
      WS 广播（ws.Hub）→ ES 双写（search.Searcher）→ Kafka 通知 M5（notify.Notifier）
   ▼
[7] 人工处置            PUT /api/alarm/:id/ack → /resolve
   │  状态跃迁 + 审计流水在同一事务
   ▼
[8] 解决后通知 M5       notify.AlarmResolved（失败返回专属错误码提示补偿）
```

**三条贯穿全流程的口径**：

| 口径 | 内容 | 违反后果 |
|---|---|---|
| 幂等键语义 | 键存在 ≡ 该动作确实成功执行过；失败路径必须 `Release` | 不释放会让重投被判成"已处理"，告警永久丢失 |
| 去重不可用 = 处理失败 | 不降级跳过去重（宁积压不误报） | 降级会在 Redis 故障期间持续产生重复告警 |
| 主链路优先 | 广播 / ES / M5 通知失败只记日志，不回滚已落库的告警 | 旁路故障把主链路挡住，会让告警整体丢失 |

## 2. [1] 解析与归属校验

设备事件按 `common/kafka.DeviceTelemetry` 统一契约解析（`DeviceEvent`）。两处判为**不可重试的坏消息**（`ErrMalformedEvent`）：

1. JSON 反序列化失败，或缺 `device_id` / `event_type`；
2. 缺 `tenant_id`（默认策略 `dlq`）。

为什么坏消息不重试：消息内容不会因重试而改变，重试 3 次退避纯属白跑；且直接入台账可查可重放，M1 补齐字段后重放即补回告警。

**事件时间**取 `occurred_at`（秒）→ `timestamp`（毫秒，历史消息）→ 0。两个字段都必须认：只认其中一个时，另一类消息的时间恒为 0，而幂等指纹把时间算进哈希，会让"同一设备同一类型"的所有事件指纹相同，被 L1 判为已处理而丢弃。

**幂等键**优先取消息自带 `request_id`；缺失时退化为 `sha1(deviceId|eventType|eventTime)` 指纹并打 WARN 推动 M1 补齐。禁止用 partition-offset 作幂等键 —— 重放时 offset 变化会导致重复处理。

## 3. [2] 规则评估与告警草稿

引擎输出 0..N 条 `Draft`（命中多条规则各生成一条告警，互不被去重）。三个要点：

- **适用范围四维**：事件类型 / 设备类型 / 设备 / 区域 + **租户**（2026-09-28 补齐）。租户维度里 `alarm_rule.tenant_id = 0` 表示平台级规则，对所有园区生效（种子规则即按此写入）。
- **窗口长度取值**：`conditions.window_sec` → `alarm_rule.window_seconds` 列 → 默认 60s。
- **规则类型取值**：以 `alarm_rule.rule_type` 列为准，列值非法时才回退 JSON 推断。

详见 `docs/m3/07`；本文不重复。

## 4. [3][4][5] 三层去重

| 层 | 键 | TTL | 命中含义 | 不可用时 |
|---|---|---|---|---|
| L1 消息幂等 | `alarm:dedup:{requestId}` | 24h | 同一条消息已处理过 | 返回 error |
| L2 业务冷却 | `alarm:cooldown:{deviceId}:{eventType}:{ruleId}` | 60s | 同一现象刚报过，抑制 | 释放 L1 键后返回 error |
| L3 存储兜底 | `uk_request_rule(request_id, rule_id)` | — | Redis 失效但库里已有 | —（最后一次拦截） |

三层目的不同、不可替代：L1 管"同一条消息"，L2 管"同一个现象"，L3 管"Redis 没了"。

L2 的键**必须带 rule_id**：一条规则进入冷却后，同一设备随后命中的另一条规则不能被一起抑制 —— 那是漏报且不报错。

**命中 L3 时返回 nil 而非 error**：库里确实已经有了，再返回错误会让消费端无限重投一条其实已处理完的消息。

## 5. [6] 三条旁路的失败取舍

| 旁路 | 失败处置 | 理由 |
|---|---|---|
| WS 广播 | 只记日志 | 前端重连可拉列表补偿；租户缺失时直接跳过（宁可不推也不推错园区） |
| ES 双写 | 只记日志 | ES 是检索副本，MySQL 才是唯一事实来源 |
| 创建事件通知 M5 | 只记日志 | 告警已落库，重投不会再执行到这里（L1/L3 会拦），通知永远补不上却让消息反复重试 |
| **解决事件通知 M5** | **返回错误码** | 与上面刻意不同：这里没有幂等键拦着重投，调用方拿得到错误才能补偿 |

## 6. [7] 告警状态机

```
                 ┌────────── ack ──────────┐
                 ▼                          │
   [0] 未处理 ────────────────────►  [1] 已确认 ──── resolve ────► [2] 已解决（终态）
   (Pending)                        (Acked)                        (Resolved)
```

| 跃迁 | 前置状态 | 说明 |
|---|---|---|
| 创建 | — | 消费链路落库，`status` 恒为 0 |
| ack | 0 | 记录 `ack_by` / `ack_at` + 审计流水 |
| resolve | 1 | 记录 `resolve_by` / `resolve_at`，并通知 M5 |

约束：

- **禁止跨级**：未处理不可直接解决 —— 跳过确认会让告警缺少"谁认领了"这个审计点。
- **已解决是终态**，任何动作都不再改变它。
- 跃迁条件落在 SQL 的 `AND status = from` 上（`model#transition`），天然并发安全：并发确认只有一次生效，其余返回"状态不允许"。
- 处理意见 `remark` 上限 255（与 `alarm_operate_log.remark` 列宽一致），超长在入库前拦截 —— 否则整条事务因列宽回滚，用户只看到"操作没生效"。

已知口径缺口（未做，留给后续）：

- `ErrNotFound` 既表示"告警不存在"也表示"前置状态不符"，两者共用 `M3-W-1004`，调用方拿不到 404/409 的区分。
- 确认后没有"取消确认"路径，误 ack 不可逆。若产品要求撤销，需新增状态与动作并同步 M5 事件语义。

## 7. 失败处置与死信

`HandleWithDeadLetter` 包裹 `HandleDeviceEvent`：

1. 坏消息（`ErrMalformedEvent`）**不重试**，直接写 `alarm_dlq` 台账；
2. 其余错误按 100ms / 500ms / 2s 退避重试 3 次（累计 2.6s，远小于重平衡超时 60s）；
3. 仍失败则写台账并**提交位移** —— 毒丸消息必须提交位移，否则卡死整个分区；
4. 台账不可用时保留降级路径并打 ERROR，明确它不是"正常处理"。

重放（`ReplayDeadLetter`）只清 L1 幂等键，**不清 L2 冷却键**；重放失败不会再次入台账。

## 8. 2026-09-28 本轮修复

| # | 问题 | 现场 | 处置 |
|---|---|---|---|
| 1 | 规则加载无租户过滤 | A 园区配的启用规则命中 B 园区事件，生成的告警归属 B 园区，不报错 | `Rule` 增 `TenantID`，`AppliesTo` 增加租户维度；平台级规则（0）保持全局生效 |
