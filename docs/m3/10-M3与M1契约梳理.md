## 1. 契约一：Kafka `onepark.device.event`（M3 ← M1）

### 1.1 建议消息结构（`DeviceEvent`，待 M1 确认 = P0-2）

```json
{
  "request_id": "uuid-v4",          // 【必需】幂等键，缺失则 M3 降级为 sha1 指纹
  "device_id": "dev-xxx",
  "device_type": "access_control|camera|sensor",
  "event_type": "intrusion|door_timeout|duress|person_detect|...",
  "area_id": "area-1",              // 规则可按区域匹配
  "event_time": 1757...,            // 毫秒时间戳（设备侧）
  "trace_id": "...",                // 可选，链路追踪
  "payload": { "temperature": 88, "door_status": "open", "auth_result": "fail" }
}
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `request_id` | ✅ | L1 幂等依赖；**缺失则 M3 降级**（`sha1(deviceId\|eventType\|eventTime\|payload)` + WARN 日志） |
| `event_type` | ✅ | 规则匹配主键 |
| `payload` | ✅ | 阈值/组合规则取数字段（路径 `payload.xxx`） |
| `area_id` | 建议 | 支持按区域配置规则 |

> **若 M1 无法提供 `request_id`**：需改用 Kafka 侧去重（`{topic}-{partition}-{offset}`），但重放时 offset 变化会导致重复告警——**强烈建议 M1 补该字段**。

### 1.2 通道参数

| 项 | 值 |
|---|---|
| topic | `onepark.device.event` |
| 分区数 / 副本 | 6 / 1（单 broker） |
| 分区键 | `device_id`（同设备保序） |
| 消费组 | `alarm-service-group`（仅 alarm-service） |
| 语义 | at-least-once + M3 三层幂等 |

### 1.3 建议 M1 补充的 topic（非 M3 消费，供整体设计参考）

`onepark.device.online`（上下线）、`onepark.device.telemetry`（遥测，M4）。
⚠️ `device.online` 消费归属未定：video-service 需更新摄像头在线状态，但 video 当前不消费 Kafka → **待定，需架构确认**（见 §5-D3）。

## 2. 契约二：gRPC `DeviceService.SendCommand`（M3 → M1，远程开门）

### 2.1 建议定义（需 M1 确认后写入 `proto/device/device.proto`）

```protobuf
service DeviceService {
  rpc Ping(onepark.common.Empty) returns (onepark.common.Empty);
  rpc SendCommand(SendCommandRequest) returns (SendCommandResponse);
}

message SendCommandRequest {
  string command_id   = 1;  // 幂等键（M3 生成 uuid），M1 侧去重
  string device_id    = 2;
  string command      = 3;  // "remote_open" / "door_always_open" ...
  bytes  payload      = 4;  // 命令参数 JSON
  string operator_id  = 5;  // 操作人（审计）
  int32  timeout_ms   = 6;  // M3 侧等待上限
}

message SendCommandResponse {
  string command_id = 1;
  bool   accepted   = 2;  // true=已被 M1 接收并下发，非"设备已执行"
  string message    = 3;
}
```

> 复用 `common.DeviceCommand` 亦可，但需补 `command_id` / `operator_id` 两个字段（幂等与审计必需）。

### 2.2 同步 vs 异步（**关键语义，需 M1 决策**）

| 方案 | 语义 | 权衡 |
|---|---|---|
| 同步 | RPC 阻塞至设备回执后返回"执行成功/失败" | 前端体验直观；但设备离线/网络差时 RPC 长挂，需长超时，易拖垮调用方 |
| **异步（推荐）** | M1 接收命令即返回 `accepted=true`；设备执行结果经 Kafka `onepark.device.command.result` 回传，M3 更新 `access_operate_log` + WS 推送 | 解耦、无长挂；前端需轮询或等 WS |

**推荐异步**：门禁设备在线率不可控，同步语义会把 M1/MQTT 的不确定性传导到 M3 HTTP 接口。

### 2.3 调用规则

- 超时 3s、重试 2 次（仅对 `accepted=false` 或网络错误；**`accepted=true` 不可重试**，否则重复开门）
- 幂等：`command_id` 由 M3 生成并落 `access_operate_log`，M1 侧按 `command_id` 去重
- 失败错误码：`M3-E-2003`（远程开门失败，KI-2：`M3-E-*` → 500，参数类用 `M3-W-*`）

## 3. 契约三：EMQX Publish 门禁控制（M1 内部）

### 3.1 边界

**M3 不直连 EMQX**（文档 01 §2.2 已定）：M3 → gRPC `SendCommand` → M1 → MQTT → 设备。M3 只记录命令审计。

### 3.2 但 M1 侧缺口（本次实证发现）

event-dispatcher 仅规划了**上行**（EMQX → Kafka），**下行 Publish 无任何实现**。因此远程开门全链路需要 M1 新增：

| M1 需新增 | 说明 |
|---|---|
| ① `SendCommand` gRPC Server | 接收命令、鉴权设备、生成 `command_id` |
| ② MQTT Publish 客户端（paho） | 按 topic 下发到设备 |
| ③ 命令结果回传 | 设备 → EMQX → event-dispatcher → Kafka `onepark.device.command.result` → M3 |

建议 topic 约定（M1 内部，M3 不感知，供对齐参考）：

| 用途 | topic | QoS |
|---|---|---|
| 下行命令 | `onepark/cmd/{deviceId}/down` | 1 |
| 上行回执 | `onepark/cmd/{deviceId}/up` | 1 |

### 3.3 M3 侧实现要点（Day 15-16）

- `access-control-service` 作为 gRPC Client 调 M1，需 `zrpc.NewClient`（M1 地址走配置/Nacos）
- 命令落 `access_operate_log`（含 operator_id、command_id、结果）
- 结果消费：若采纳异步语义，需订阅 `onepark.device.command.result` → **这会使 access-control-service 也具备 Kafka 消费能力**（此前设计仅 alarm-service 消费，需同步更新认知）
