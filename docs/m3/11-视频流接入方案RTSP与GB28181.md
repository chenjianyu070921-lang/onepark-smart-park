# M3 — RTSP / GB28181 视频流接入方案（定案 v1.0）

> 2026-09-14 · 适用 video-service · 接口 #49/#50/#51
> 现状实证：`app/video-service` 内 **零 rtsp/stream 代码**；`deploy/docker-compose.yml` **无媒体网关组件**

---

## 1. 前提事实（决定方案边界）

| 事实 | 影响 |
|---|---|
| 浏览器**无法直接播放 RTSP**（非 HTTP 协议族） | 「把 RTSP 地址返回给前端直接播」在 Web 后台不可行 |
| GB28181 是**信令协议**（基于 SIP），设备主动注册到平台，平台发 Invite 点播，媒体为 PS over RTP/UDP | 需要 SIP 服务端 + 媒体转封装，**不可能在 M3 业务服务内实现** |
| 视频转码/AI 识别已在文档 01 §2.2 列为 **Out of Scope** | M3 只做「地址簿 + 状态」，不碰码流 |

---

## 2. 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 纯地址簿** | video-service 只存 RTSP/GB 地址并下发 | 零新增组件、零协议实现，符合 M3 边界 | **Web 后台无法预览**；只能给 VLC/客户端用 | ✅ 阶段一 |
| **B. 引入媒体网关 ZLMediaKit** | RTSP 拉流 → 转 HTTP-FLV / HLS / WebRTC；GB28181 需配套 SIP 服务（如 wvp-GB28181-pro + ZLM） | 浏览器可预览、支持录像/截图、生态成熟 | 新增组件与运维；GB28181 需额外 SIP 服务；端口多（TCP 80/554/1935 + UDP 10000 段） | ✅ 阶段二（有预览需求时） |
| C. 第三方国标平台/云直播 | 外部服务接入 | 快 | 依赖外部、成本高、数据外流 | ❌ 不推荐 |

**推荐：分阶段落地 A → B**。本迭代（接口 #49-51）按 **A** 实现，把「流地址」作为数据资产管起来；预览需求明确后再引入 B，届时只需在 camera 表增加「转封装播放地址」字段，**不推翻阶段一设计**。

## 3. 阶段一：地址簿（本期实现）

### 3.1 `video_db.camera` 表字段建议

| 字段 | 类型 | 说明 |
|---|---|---|
| id / name | | 主键 / 点位名 |
| device_id | varchar | 关联 M1 设备（**M3 不维护设备主数据**） |
| area_id | varchar | 区域 |
| `stream_type` | varchar | `rtsp` / `gb28181` / `hls` / `http_flv` |
| `stream_url` | varchar | 原始流地址（`rtsp://...` 或 GB 设备编码） |
| `gb_device_id` | varchar | GB28181 20 位设备编码（`stream_type=gb28181` 时必填） |
| `gateway_id` | varchar | 预留：阶段二接入的媒体网关实例 |
| `playback_url` | varchar | **预留**：阶段二转封装后的浏览器可播地址 |
| status | tinyint | 0-离线 / 1-在线（Redis 缓存 `video:camera:status:{id}`） |
| location | varchar | 安装位置 |

> `playback_url` / `gateway_id` 现阶段**允许为空**，不留死代码——阶段一接口返回 `stream_url`，阶段二增加 `playback_url` 字段即可。

### 3.2 接口行为

| 接口 | 阶段一行为 |
|---|---|
| #49 添加摄像头 | 校验 `stream_type` 与地址格式（RTSP 前缀 / GB 20 位编码），参数错误用 `M3-W-3xxx`（KI-2：`M3-E-*` 会返回 500） |
| #50 摄像头列表 | 返回点位 + 在线状态（读 Redis 缓存，miss 回源 DB） |
| #51 获取视频流 URL | 返回 `stream_url`（阶段二同时返回 `playback_url`） |

### 3.3 在线状态来源（待定）

文档 01 未定 `onepark.device.online` 的消费归属 → 两种：
1. video-service 自行消费该 topic 更新状态（需引入 Kafka 消费）
2. M1 通过 gRPC 通知 video-service
**推荐 1**（事件驱动、解耦），需架构确认（见文档 10 §5-D3）。

## 4. 阶段二：媒体网关（预览需求明确后）

### 4.1 组件与职责

| 组件 | 职责 |
|---|---|
| ZLMediaKit | 拉 RTSP → 转封装 HTTP-FLV / HLS / WebRTC；支持 RTSP/GB28181 推流接入 |
| wvp-GB28181-pro（若接入国标设备） | SIP 信令：设备注册、点播 Invite、云台控制；对接 ZLM 取流 |
| video-service | 调用 ZLM 的 `addStreamProxy` / `getMediaInfo` 生成播放地址，写入 `playback_url` |

### 4.2 compose 新增（阶段二）

```yaml
zlm:
  image: zlmediakit/zlmediakit:master
  ports: ["80:80", "554:554", "1935:1935", "10000-10010:10000-10010/udp"]
```
GB28181 另需 wvp 服务（SIP 端口 5060 TCP/UDP）。

### 4.3 M3 侧工作量（阶段二）

- video-service 增加 `media` 包：封装 ZLM HTTP API（拉流代理、取播放地址、断流检测）
- camera 增加 `gateway_id` 路由到对应 ZLM 实例
- **不实现 SIP 栈、不处理码流**（严守边界）

## 5. 安全（P1-6 未决）

| 项 | 建议 |
|---|---|
| 流地址是否签名 | RTSP 含用户名密码明文 → 建议**不直接下发**给前端，返回时脱敏或走阶段二签名 URL |
| 时效性签名 | 阶段二对 `playback_url` 加时效 token（ZLM 支持 hook 鉴权） |
| 权限 | 预览需 M6 `CheckPermission` 校验，禁止仅靠前端隐藏 |
