## 1. 定位与边界

- 输入：**单条** `DeviceEvent`（来自 Kafka，已过 L1 幂等）
- 输出：**0..N 条告警草稿**（命中多条规则则生成多条告警）
- 不做：告警入库 / ES 双写 / WS 推送（由调用方 logic 层负责）；规则 CRUD（handler/logic）
- Redis API 已实证可用（go-zero v1.10.3）：`SetnxExCtx`、`ZaddFloatCtx`、`ZremrangebyscoreCtx`、`ZcardCtx`、`ExpireCtx`、`EvalCtx` / `ScriptRunCtx`（Lua 原子）

## 2. 规则数据模型

`alarm_rule` 表核心字段（文档 04 §2 扩展）：

| 字段 | 说明 |
|---|---|
| id / name | 主键 / 规则名 |
| device_id / area_id | 适用范围（`*` 或空 = 全部） |
| event_type | 触发的事件类型（精确匹配） |
| rule_type | `threshold` / `combination` / `time_window` |
| conditions | JSON，见下 |
| window_seconds | 时间窗口长度（秒），见 §2.1 |
| level | 告警等级 1-4（P1-1 待确认） |
| status | 启用/禁用 |
| cooldown_sec | L2 冷却秒数，默认 60 |

### 2.1 列与 JSON 的关系（2026-09-28 定案）

`rule_type` 与 `window_seconds` 两列曾经只写不读 —— 引擎只读 `conditions` JSON，
运维在控制台改这两列不会产生任何效果，而详情接口照常回显新值，现象与"配置已生效"完全一致。
现按下列优先级取值：

| 配置项 | 取值顺序 | 冲突时 |
|---|---|---|
| 规则类型 | `rule_type` 列 → `conditions.type` → 按字段推断 | **以列为准**；列值非法（脏数据）才回退推断 |
| 窗口长度 | `conditions.window_sec` → `window_seconds` 列 → 默认 60s | **以 JSON 为准**；JSON 未配才回退列 |

两者优先级方向相反，是有意为之：

- 规则类型以列为准，因为 `rule_type` 是创建接口必填且经归一化的值，是运维看到的那个；
  `conditions.type` 是可选字段（文档 04 的扁平写法就没有），缺了只能推断。
  认 JSON 会出现"控制台写着时间窗口、实际按阈值逐条触发"——现象是告警风暴，配置面却一切正常。
- 窗口长度以 JSON 为准，因为它是规则作者显式写下的意图；列是控制台后来补的配置面，
  只在 JSON 没写时兜底。

**时间窗口规则必须给出窗口长度**（创建 / 更新期校验）：两处都空时引擎会静默落到 60s，
运维以为配的是 5 分钟，实际 1 分钟 —— 误报量与排查难度不成比例。宁可创建期报 400 让他填。

### conditions JSON

```json
// ① threshold
{"type":"threshold","conditions":[{"field":"payload.temperature","op":"gte","value":80}]}

// ② combination
{"type":"combination","logic":"AND","window_sec":60,
 "conditions":[{"field":"payload.door_status","op":"eq","value":"open"},
               {"field":"payload.auth_result","op":"eq","value":"fail"}]}

// ③ time_window
{"type":"time_window","window_sec":300,"threshold":3,
 "match":{"field":"event_type","op":"eq","value":"intrusion"}}
```

字段取值路径统一为 `payload.xxx` / `event_type` / `device_id`；`op` 支持
`gt gte lt lte eq ne in between`。

## 3. 三类规则

### 3.1 threshold（阈值）—— 无状态

- 单事件即时判定，纯内存评估，**零 Redis 依赖**
- 例：`temperature >= 80` → 严重告警
- 多条件时按 `logic`（默认 AND）组合（仍是单事件内字段）

### 3.2 combination（组合）—— 有状态（跨事件时需中间态）

两种形态：

| 形态 | 是否需要 Redis | 实现 |
|---|---|---|
| a) 单事件内多字段组合 | 否 | 与 threshold 同，只是条件多条 |
| b) **跨事件时序组合**（如「门磁开 且 5s 内无刷卡」） | **是** | Redis 记录条件满足标记 |

形态 b 实现：

1. 条件逐条评估，命中则写 `SetnxEx("alarm:cond:{ruleId}:{deviceId}:{condIdx}", "1", windowSec)`
2. 每次事件到达时读取全部标记：AND → 全齐才触发；OR → 任一即触发
3. 触发后 `Del` 全部标记（**防重复触发**）
4. `window_sec` 默认 60s，与 TTL 一致，过期自动失效

### 3.3 time_window（时间窗口）—— 滑动窗口计数

- 例：5 分钟内非法闯入 ≥ 3 次
- **滑动窗口（推荐）**，非固定窗口：固定窗口在边界处会产生最多 2× 误差（如 2+2 次跨窗被判为 2 次不触发）

实现（**Lua 脚本保证原子**，用 `EvalCtx`）：

```lua
-- KEYS[1]=window key  ARGV[1]=now_ms  ARGV[2]=window_ms  ARGV[3]=member  ARGV[4]=threshold  ARGV[5]=ttl_sec
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])
redis.call('ZADD', KEYS[1], ARGV[1], ARGV[3])
local cnt = redis.call('ZCARD', KEYS[1])
redis.call('EXPIRE', KEYS[1], ARGV[5])
if cnt >= tonumber(ARGV[4]) then redis.call('DEL', KEYS[1]); return cnt end
return 0
```

- key：`alarm:window:{ruleId}:{deviceId}`，member = `requestId`（保证同消息不重复计），score = 事件毫秒时间戳
- TTL = `window_sec + 60`（防冷设备 key 残留）
- **窗口长度来源**：`conditions.window_sec` → `window_seconds` 列 → 默认 60s（见 §2.1）。
  TTL 恒比窗口长 60s，否则窗口还没走完 key 就过期、计数被提前清零。
- **触发后清空窗口** + 依赖 L2 冷却，否则每来一条都会触发、持续刷屏

### 3.4 三类对比

| 维度 | threshold | combination | time_window |
|---|---|---|---|
| 状态 | 无 | 有（Redis 标记，短 TTL） | 有（ZSet，窗口 TTL） |
| 触发依据 | 单事件字段 | 多条件 AND/OR | 窗口内计数 |
| Redis | 否 | 是 | 是（Lua 原子） |
| 典型场景 | 温度/烟雾超标 | 门磁开+无授权 | 短时反复闯入 |

## 4. 评估流程

```
Evaluate(ctx, ev) ([]*AlarmDraft, error)
  ├─ 取适用规则：Redis 缓存全量活跃规则，内存按 eventType/deviceId/areaId 过滤
  ├─ 逐规则 rule.Evaluate：
  │    ├─ status 禁用 → 跳过
  │    ├─ 按 rule_type 分派到注册表中的 Evaluator
  │    ├─ 命中 → 构造 AlarmDraft（level 取规则 level，content 按模板渲染）
  │    └─【L2】冷却键 SetnxEx → 命中则抑制本条
  └─ 返回草稿列表（由调用方批量入库）
```

### 4.0 适用范围的五个维度（2026-09-28 补齐租户维）

`Rule.AppliesTo` 依次判定：**租户 → 事件类型 → 设备类型 → 设备 → 区域**，空值表示该维度不限。

租户维度的语义：

| 规则 tenant_id | 含义 |
|---|---|
| `0` | 平台级规则，对所有园区生效（种子规则①②③即按此写入） |
| 非 0 | 只对同 tenant_id 的事件生效 |

为什么必须补：`ListEnabled` 是全表加载（`status = 1`）**不带租户条件** —— 平台级规则必须被加载，
不能靠 SQL 过滤。租户隔离因此落在 `AppliesTo` 上，与"平台级规则"这条语义放在同一处，避免两处各判一半。

缺了这一维的现场：A 园区配的启用规则命中 B 园区的设备事件，告警的 `tenant_id` 取自事件，
于是 B 园区看到一条"自己从没配过的规则"产生的告警 —— 不报错、不告警、日志正常，
只能靠人工比对规则列表发现。

事件侧 `tenant_id` 为 0 时不命中任何园区规则（仍命中平台级规则）：归属未定的事件本就被消费链路
按 `Tenant.MissingPolicy` 挡在引擎之前或直接入死信，引擎再放行只会生成一条 `tenant_id=0`、
任何视图都看不见的告警。

### 4.1 规则缓存（实现现状）

**实际实现与本文档初稿不同，以下为现状口径（2026-09-17 校正）**：

| 项 | 现状（`internal/rule/engine.go#snapshot`） | 初稿设计（未采用） |
|---|---|---|
| 载体 | **进程内快照**（`sync.RWMutex` 保护的 `[]Rule`） | Redis `alarm:rules:active` |
| TTL | **30s**（`svc.ruleCacheTTL`），过期后首次评估时重新查库 | 300s |
| 失效 | 被动过期（无主动 Del） | 规则 CRUD → `Del` |
| 异常 | 加载失败**保留旧快照并上抛错误**（宁重投不误报），不用过期规则继续评估 | — |

**为什么没用 Redis（取舍记录）**：

1. 规则是**低频变更、高频读取**的数据，进程内快照省掉每条事件的 Redis 往返；
2. Redis 方案的"CRUD → Del"在多实例下仍要处理"删除广播"，否则每个实例都要等 TTL；
   与其引入半套失效机制，不如统一按 TTL 承担最长 30s 的生效延迟；
3. 代价明确：**规则变更最长 30s 后生效**，且多实例间存在同一量级的不一致窗口。
   若未来要求秒级强一致，再补 Redis + pub/sub 失效广播（R5）。

> 因此 `docs/m3/04` 中「清 Redis 规则缓存」的链路描述与实现不符，按本节为准。

### 4.2 代码结构（`internal/rule/`）

```go
type Evaluator interface {
    Type() string                                                  // "threshold" ...
    Evaluate(ctx context.Context, rule *model.AlarmRule, ev *DeviceEvent) (bool, error)
}

type Engine struct {
    evals map[string]Evaluator   // 注册表：新增规则类型只需实现接口 + 注册

func (e *Engine) Evaluate(ctx context.Context, ev *DeviceEvent) ([]*AlarmDraft, error)
```

分层：`logic → rule.Engine → model/redis`，Engine 不感知 HTTP/Kafka。

### 4.3 种子规则（建库脚本）

`deploy/sql/m3_mysql_tables.sql` 末尾以 `INSERT IGNORE` 写入三条**平台级默认规则**（`tenant_id=0`）：

| id | 名称 | rule_type | 用途 |
|----|------|-----------|------|
| 1 | 门禁非法闯入告警 | threshold | 主链路默认规则（与硬编码回退规则语义等价） |
| 2 | 温度超过80℃告警 | threshold | 阈值规则样例（`payload.temperature > 80`） |
| 3 | 短时反复闯入告警(5分钟≥3次) | time_window | 时间窗口规则样例（`window_sec=300, threshold=3`） |

**为什么不留空表**：`alarm_rule` 是规则的唯一事实来源；表空 + `Rule.DisableLegacyFallback=true` 时，
消费链路会把事件直接丢弃（只打 WARN）—— 部署后没人手工建规则，安防主链路等于静默停摆。

**契约测试**：`internal/rule/seedrule_test.go` 直接读取该 SQL，断言每条种子条件都能被 `ParseSpec` 解析。
理由是 `ListEnabled` 对解析失败的规则是**静默跳过**的，写错字段名的现象是"规则配了却不告警"，排查成本极高。
该用例上线时即刻发现并修掉了一个真实缺陷：扁平写法只认 `operator` 不认 `op`（详见 §6 R7）。

**键名兼容**：`op` 与 `operator` 两种写法在嵌套（`conditions[]`/`match`）与扁平（顶层 `field/op/value`）中**均被接受**。

## 5. 测试要点（Day 5-7 一并交付）

| 场景 | 断言 |
|---|---|
| 阈值边界 | `value == threshold` 时 `gte` 命中、`gt` 不命中 |
| 组合 AND/OR | 缺一条件不触发 / 任一命中即触发 |
| 组合重复触发 | 触发后标记已清 → 同一组合不连续告警 |
| 租户维度 | 园区规则不命中其它园区事件；平台级规则（0）对所有园区生效 |
| 窗口长度来源 | JSON 优先、列兜底、两者皆空取 60s；TTL 恒大于窗口 |
| 声明类型覆盖 | `rule_type` 列覆盖 JSON 推断；列值脏时不覆盖（未知类型会被整条跳过） |
| 窗口边界 | 第 N 次触发；窗口外事件被 `ZREMRANGEBYSCORE` 清除后不计数 |
| 窗口触发后 | key 已清空，不持续刷屏 |
| 规则禁用 | 不评估 |
| Redis 故障 | 返回错误进 DLQ（不静默吞掉，避免丢告警） |
| 冷却生效 | 冷却期内同设备同事件不产生第二条告警 |
