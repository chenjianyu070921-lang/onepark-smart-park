## 2. alarm-service 内部模块架构（Day 2 骨架依据）

```mermaid
graph TB
    subgraph ENTRY["入口层"]
        HTTP_API["HTTP API<br/>handler/ → logic/"]
        RPC_SRV["gRPC Server<br/>GetActiveAlarms (M5 调用)"]
        CONSUMER["Kafka Consumer<br/>mq/ (后台 goroutine)"]
    end

    subgraph CORE["核心业务层"]
        RULE_LOGIC["规则管理 logic<br/>CRUD + 缓存失效"]
        ENGINE["<b>规则引擎 rule/</b><br/>阈值 / 组合 / 时间窗口<br/>Evaluate(event)"]
        ALARM_LOGIC["告警生命周期 logic<br/>生成 → 确认 → 解决"]
    end

    subgraph INFRA["基础设施层"]
        DEDUP["去重 dedup/<br/>Redis SET NX + TTL"]
        DAO["数据访问 model/<br/>GORM"]
        SEARCH["检索 search/<br/>ES DSL"]
        WSHUB["推送 ws/<br/>Hub + 心跳 + 广播"]
        PRODUCER["Kafka Producer<br/>告警事件 → M5"]
    end

    subgraph STORE["存储"]
        DB[("alarm_db")]
        RDS[("Redis")]
        ESS[("ES")]
        KFK{{"Kafka"}}
    end

    HTTP_API --> RULE_LOGIC
    HTTP_API --> ALARM_LOGIC
    RPC_SRV --> ALARM_LOGIC
    CONSUMER --> ENGINE

    ENGINE -->|"命中规则"| DEDUP
    DEDUP -->|"未冷却 → 创建"| ALARM_LOGIC
    ALARM_LOGIC --> DAO
    ALARM_LOGIC --> WSHUB
    ALARM_LOGIC -->|"异步双写"| SEARCH
    ALARM_LOGIC -->|"确认/解决"| PRODUCER

    DAO --> DB
    DEDUP --> RDS
    RULE_LOGIC --> RDS
    SEARCH --> ESS
    WSHUB -->|"WS /ws/alarm"| CLIENT["前端大屏"]
    PRODUCER --> KFK

    style ENGINE fill:#ffe6e6,stroke:#e74c3c,stroke-width:2px
    style DEDUP fill:#e6f7ff,stroke:#1890ff,stroke-width:2px
    style WSHUB fill:#f6e6ff,stroke:#9b59b6,stroke-width:2px
```

**分层铁律**：`入口层 → 核心业务层 → 基础设施层 → 存储`，禁止跨层反向调用；`rule/`、`dedup/`、`ws/`、`search/` 各自独立成包，通过 `svc.ServiceContext` 注入依赖，保证可单测。

## 3. 部署拓扑图（Docker Compose 网络 `onepark`）


**说明**：
- 服务通过容器名互访（如 `kafka:9092`、`redis:6379`），配置走 `${VAR}` 环境变量占位，值来自 `deploy/.env`
- M3 不直连 EMQX / TDengine / MinIO（EMQX 经 M1，TDengine 属 M4，MinIO 属文件存储）
- 中间件镜像已于 2026-09-13 修复：Kafka `bitnami/kafka:3.9`、MinIO `coollabsio/minio:latest`（原 tag 已失效）
