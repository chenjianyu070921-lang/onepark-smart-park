#### #34 POST /api/alarm/rule — 创建告警规则

**请求体**（`conditions` 为 JSON 字符串存储，Day 5 定义完整规则模型）：

```json
{
  "name": "1号厂房温度越限",
  "deviceId": "dev-1001",
  "areaId": 12,
  "eventType": "temperature",
  "level": 3,
  "ruleType": "threshold",
  "conditions": "{\"type\":\"threshold\",\"field\":\"temperature\",\"operator\":\">\",\"value\":50}",
  "windowSeconds": 60,
  "status": 1
}
```

| 字段            | 类型           | 必填 | 说明                                              |
|---------------|--------------|----|-------------------------------------------------|
| name          | string       | 是  | 规则名称                                            |
| deviceId      | string       | 否  | 设备 ID；为空表示按 eventType 全局生效                      |
| areaId        | int64        | 否  | 区域 ID                                           |
| eventType     | string       | 是  | 事件类型（见 §5.3）                                    |
| level         | int          | 是  | 告警等级 1-4（见 §5.1）                                |
| ruleType      | string       | 是  | `threshold` 阈值 / `composite` 组合 / `window` 时间窗口 |
| conditions    | string(JSON) | 是  | 规则条件，GORM JSON 字段                               |
| windowSeconds | int          | 否  | 时间窗口（秒），仅 window/composite 用                    |
| status        | int          | 是  | 1 启用 / 0 禁用                                     |

**响应**：`data = { "id": 1001 }`
**链路**：前端 → Gateway → M6 鉴权 → alarm-service → MySQL → 清 Redis 规则缓存
**错误码**：`M3-E-1001` 参数非法 · `M3-E-1002` 规则条件 JSON 解析失败 · `M6-E-0003` 无权限

#### #39 PUT /api/alarm/:id/ack — 确认告警

**请求体**：`{ "remark": "已派安保现场核实" }`
**处理**：`status: 0 → 1`，记录 `ack_by`（取自 ctx `x-user-id`）、`ack_at`；**WS 广播状态变更**
**错误码**：`M3-E-1004` 告警不存在 · `M3-E-1006` 状态不允许确认（如已解决）
**链路**：操作员 → Gateway → M6 鉴权 → alarm-service → MySQL → WS 推送

#### #40 PUT /api/alarm/:id/resolve — 解决告警

**请求体**：`{ "remark": "现场已处理" }`
**处理**：`status: 1 → 2`，记录 `resolve_by`/`resolve_at`；**生产 Kafka `onepark.alarm.event`** 通知 M5；WS 广播
**错误码**：`M3-E-1004` 告警不存在 · `M3-E-1006` 状态非法 · `M3-E-1007` Kafka 发送失败（告警状态仍需落库，需补偿）
**链路**：操作员 → Gateway → alarm-service → MySQL + Kafka → M5 dispatch-service

#### #41 GET /api/alarms — 历史告警（ES 检索 + 聚合）

**Query**：`startTime` `endTime` `level` `deviceId` `areaId` `eventType` `status` `keyword` `page` `pageSize`
**响应 data**：

```json
{
  "list": [ { "alarmId": "9001", "deviceId": "dev-1001", "areaId": 12,
              "eventType": "temperature", "level": 3, "status": 2,
              "content": "...", "createTime": "2026-09-13T10:00:00Z" } ],
  "total": 128,
  "aggs": { "levelCount": { "1": 36, "2": 25, "3": 10, "4": 2 } }
}
```

**技术点**：ES DSL 组合查询（term + range + match）+ 聚合桶；ES 不可用时降级查 MySQL（需记录降级日志）
**错误码**：`M3-E-1008` ES 查询失败

> **`keyword`（2026-09-18 新增，向后兼容）**：告警 `content` 的关键词检索，空/不传表示不参与检索，
> 行为与新增前完全一致。
>
> - ES 路径：`match` on `content`（分词后匹配，需映射的分词器支持）
> - MySQL 降级路径：`content LIKE '%kw%'`，并对用户输入的 `%` `_` `\` 做 `ESCAPE '\'` 转义
>
> **为什么 MySQL 侧也要支持，而不是「ES 不可用就忽略关键词」**：忽略会静默返回**未过滤的全量**，
> 用户以为搜过了、实际什么都没过滤 —— 这种错误不会有任何报错，比召回略窄更难发现。
> 两条路径的召回粒度不同（ES 分词后更宽、MySQL 是子串），这是降级场景下可接受的差异，已在
> `AlarmHistoryFilter.Keyword` 注释中固化口径。

#### #42 WS /ws/alarm — 实时推送

**连接**：`ws://{gateway}:8080/ws/alarm`（网关需支持 Upgrade 转发，见 P0-4）
**鉴权**：连接时携带 JWT（query 参数或首帧）
**服务端 → 客户端消息**：

```json
{
  "type": "alarm.new",
  "data": { "id": 9001, "alarmNo": "AL...", "deviceId": "dev-1001",
            "level": 3, "content": "...", "createdAt": "..." }
}
```

```json
{ "type": "alarm.update", "data": { "id": 9001, "status": 1, "ackBy": 8, "ackAt": "..." } }
```

**消息类型**：`alarm.new`（新告警）· `alarm.update`（状态变更：确认/解决）
**心跳**：服务端每 30s 发 `{"type":"ping"}`；客户端回 `{"type":"pong"}`；连续 2 次未响应则断开
**技术点**：gorilla/websocket · Hub 连接池 · 广播 · 断线清理

#### #43 gRPC GetActiveAlarms（供 M5 大屏）

```protobuf
// proto/alarm/alarm.proto 待扩展（P0-3）
message GetActiveAlarmsReq {
  int64 area_id = 1;        // 可选，0 表示全部
  repeated int32 levels = 2; // 可选，按等级过滤
}
message GetActiveAlarmsResp {
  int64 total = 1;                  // 活跃告警总数
  map<int64, int32> level_count = 2; // 按等级分布 {3: 5, 4: 2}
}
rpc GetActiveAlarms(GetActiveAlarmsReq) returns (GetActiveAlarmsResp);
```

**调用方**：M5 dashboard-service（链路 5 四路并发 gRPC 之一）
**注意**：M5 侧有 `errgroup + context` 超时（建议 M3 响应 < 200ms，Redis 计数缓存兜底）

#### #44 BG Kafka 消费 → 规则引擎（后台进程）

**消费**：Topic `onepark.device.event`，消费组 `alarm-service-group`
**流程**：解析 → RequestId 幂等 → 取规则 → Evaluate → Redis 冷却去重 → 创建告警 → ES 双写 → WS 广播
**幂等**：`alarm:req:{requestId}` Redis SET NX（TTL 24h），已存在则丢弃
**失败**：重试 3 次后入 DLQ `onepark.device.event.dlq`
**技术点**：Kafka 消费组 · 规则引擎 · Redis SET NX · 死信队列

### 1.2 access-control-service（4 个）

#### #45 POST /api/access/grant — 授权门禁权限

**请求体**（支持批量）：

```json
{
  "personIds": [101, 102],
  "deviceIds": ["door-01", "door-02"],
  "timeWindow": { "start": "08:00", "end": "20:00", "days": [1,2,3,4,5] },
```

| 字段         | 类型       | 必填 | 说明             |

| deviceIds  | []string | 是  | 门禁设备 ID（支持批量）  |
| timeWindow | object   | 否  | 时间段权限；为空表示全天   |
| whitelist  | bool     | 否  | 是否白名单（跳过时间段校验） |
| expireAt   | string   | 否  | 过期时间           |

**处理**：批量写入 `access_permission`；**清除相关 Redis `access:perm:{personId}` 缓存**
**错误码**：`M3-E-2001` 参数非法 · `M3-E-2002` 授权失败
**链路**：管理员 → Gateway → M6 鉴权(`access:write`) → access-control → MySQL + Redis

#### #46 DELETE /api/access/revoke — 撤销权限

**请求体**：`{ "personIds": [101], "deviceIds": ["door-01"] }`

#### #47 POST /api/access/remote-open — 远程开门

**请求体**：`{ "deviceId": "door-01", "reason": "访客放行" }`
**处理**：权限校验 → gRPC 调 M1 `SendCommand(deviceId, "open_door")` → 记录审计 `access_operate_log`（含成功/失败/超时）

**错误码**：`M3-E-2004` 无该门禁权限 · `M3-E-2005` 调用 M1 失败 · `M3-E-2006` 设备响应超时

#### #49 POST /api/video/camera — 添加摄像头

**请求体**：

```json
{
  "name": "1号厂房西北角",
  "deviceId": "cam-2001",
  "areaId": 12,
  "rtspUrl": "rtsp://192.168.1.50:554/stream1",
  "location": { "lng": 113.12, "lat": 23.03, "floor": "3F" },
  "status": 1
}
```

**错误码**：`M3-E-3001` 参数非法 · `M3-E-3002` RTSP 地址格式非法

#### #50 GET /api/video/cameras — 摄像头列表 + 在线状态

**Query**：`areaId` `status` `page` `pageSize`
**响应 data**：列表含 `id/name/deviceId/areaId/status/lastHeartbeatAt`
**技术点**：MySQL 查询 + Redis 状态缓存
**缓存实现（已落地，2026-09-17）**：

- key `video:camera:heartbeat:{deviceID}`，值为最近心跳的毫秒时间戳，TTL = `Heartbeat.OfflineAfterSeconds`（默认 180s）
- 写入点：Kafka 心跳消费唯一命中该设备时 `SETEX`（`svc/heartbeat.go`）；失败只记日志不回错，避免 Redis 抖动卡住分区
- 读取点：列表接口命中缓存时把 `status` 修正为在线（`logic/cameralogic.go#effectiveStatus`），
  使"设备刚上线"无需等最长 60s 的离线扫描；**故障态(2)不被覆盖**（人工排障结论优先）
- 缓存不可用/未配置时全部回退 MySQL，接口语义不变

**错误码**：`M3-E-3003` 查询失败

#### #51 GET /api/video/stream/:id — 获取视频流 URL

**响应 data**：

```json
{
  "cameraId": 2001,
  "rtspUrl": "rtsp://...",
  "flvUrl": "http://.../live/cam-2001.flv?expires=1758092400&sign=9f2c...",
  "expiresAt": 1758092400,
  "sign": "9f2c...",
  "signAlg": "HMAC-SHA256"
}
```

**说明**：M3 只管理与下发流地址，**不实现转码/推流**。`flvUrl` 若有独立流媒体服务则由其提供。

**签名鉴权（已落地，2026-09-17；原 P1-6 待确认项）**：

| 项 | 约定 |
|---|---|
| 密钥 | 环境变量 `VIDEO_STREAM_SIGN_SECRET` → `Stream.SignSecret`；**留空则整条签名链路关闭**（`sign`/`signAlg` 为空串、FLV 不带参数），行为与上线前一致 |
| 算法 | `HMAC-SHA256(secret, "{cameraId}|{expiresAt}")`，十六进制输出 |
| 绑定维度 | `cameraId` + `expiresAt`：签名被搬到别的摄像头或延期都会失效 |
| 下发位置 | FLV(HTTP 拉流) 追加 `?expires=&sign=`；RTSP 不追加 query（部分设备不接受），其鉴权改用响应中的 `sign` 字段 |
| 校验 | `logic.VerifyStreamSign`（恒定时间比较 + 有效期校验），供网关/流媒体 hook 调用 |

**错误码**：`M3-E-3004` 摄像头不存在 · `M3-E-3005` 设备离线

## 7. Elasticsearch 索引设计（Day 13 落地）

### 7.1 `alarm_history`

```json
{
  "mappings": {
    "properties": {
      "alarm_id":   { "type": "keyword" },
      "alarm_no":   { "type": "keyword" },
      "device_id":  { "type": "keyword" },
      "area_id":    { "type": "long" },
      "event_type": { "type": "keyword" },
      "level":      { "type": "integer" },
      "status":     { "type": "integer" },
      "tenant_id":  { "type": "long" },
      "content":    { "type": "text", "analyzer": "ik_max_word" },
      "create_time":{ "type": "date" }
    }
  }
}
```

> **`content` 的 `analyzer` 是配置项，不是硬编码（2026-09-18 更正）**
>
> `deploy/docker-compose.yml` 起的是 **ES 官方镜像，不含 ik 插件**，硬编码 `ik_max_word` 会让
> `PUT /{index}` 直接以 `illegal_argument_exception: analyzer [ik_max_word] not found` 失败 ——
> 表现是「配了 ES，检索反而完全不可用」。
>
> 因此实现改为：`analyzer` 由配置 `ES.Analyzer` 决定，留空用 ES 默认分词器；
> 且 `ESClient.EnsureIndex` 在插件缺失（400 + "analyzer ... not found"）时
> **自动降级为默认分词器并记 WARN**，不让检索整体失效。
>
> 引入 ik 插件后只需在 `alarm-api.yaml` 填 `Analyzer: ik_max_word`，无需改代码。
> 注意：索引一旦建成，改分词器**必须重建索引**（已存在的索引会命中 `resource_already_exists` 直接返回）。

**分片**：单机 1 分片 0 副本（⚠️ P1-4 生产需评估）
