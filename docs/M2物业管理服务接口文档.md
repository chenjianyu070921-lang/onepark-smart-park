> **模块名称：** M2 物业管理服务（Property Service）
> **版本：** V1.0
> **更新时间：** 2026-09-15
> **接口范围：** 4 个微服务、共 **16 个接口**（15 个 HTTP + 1 个 gRPC）

## 二、通用约定

### 2.1 请求头（由网关注入，服务侧只读）

| Header | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `x-tenant-id` | int64 | 是（经网关可缺省） | 园区/租户 ID，**所有业务数据按此隔离**。经网关缺省为 `DefaultTenantId`（联调默认 `1`） |
| `x-user-id` | int64 | 否 | 当前用户 ID（工单发起人、公告发布人等），缺省 `0` |
| `x-role-ids` | string | 否 | 角色 ID 列表，逗号分隔；供后续行级权限扩展 |
| `x-request-id` | string | 否 | 全链路追踪 ID；缺省时网关生成并回写响应头，同时作为 Kafka 事件的 `event_id` |
| `Content-Type` | string | 是（写接口） | 固定 `application/json` |

> 服务侧由 `common/middleware.Tenant` 读取上述头写入 `common/ctxdata`，logic 层通过 `ctxdata.GetTenantId/GetUserId/GetRoleIds` 读取。**直连服务时若缺 `x-tenant-id`，业务会返回 `M6-E-0001`（缺少租户信息）**。
>
> ⚠️ 当前网关为**无鉴权联调模式**（未接 M6 JWT）。接入 M6 `ValidateToken/CheckPermission` 后，`x-user-id`/`x-role-ids`/`x-tenant-id` 将由鉴权中间件按 Token 解析并覆盖缺省值。

### 2.2 统一响应体

所有业务接口（成功与业务失败）统一返回：

```json
{
  "code": "0",
  "msg": "ok",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | string | `"0"` 表示成功；非 `"0"` 为业务错误码（格式 `{模块}-{级别}-{4位数字}`） |
| `msg` | string | 提示信息，成功固定 `"ok"` |
| `data` | object / array | 业务数据载荷，失败时不返回该字段 |

### 2.3 HTTP 状态码与错误码映射（**重点**）

错误码级别决定 HTTP 状态码（`common/errorx/http_status.go`）：

| 错误码级别 | HTTP 状态码 | 触发示例 |
| --- | --- | --- |
| `-E-`（Error） | **500** | `M2-E-1001` 工单不存在、`M6-E-0001` 缺少租户信息、`M2-E-5001` 内部错误 |
| `-W-`（Warn） | **400** | 参数/状态类提示（M2 当前未启用） |
| `-I-`（Info） | 200 | 提示类（M2 当前未启用） |

> ⚠️ **联调须知**：M2 现有业务错误码均为 `-E-` 级，因此"工单不存在"等**正常业务失败会返回 HTTP 500**，但响应体仍是统一信封。**前端判定业务结果请以 body 的 `code` 字段为准，不要只看 HTTP 状态码。**

### 2.4 参数校验失败（非统一信封）

请求参数不满足 go-zero 校验（必填缺失、类型错误）时，handler 直接走 `httpx.ErrorCtx`，返回 go-zero **默认错误响应**（约 HTTP 400，形如 `{"error":"..."}`），**不是** `{code,msg,data}` 信封。

**必填判定规则**：`.api` 中字段未标注 `optional` 即为**必填**，语义是**该字段必须出现在请求中**（query 必须带该 key、JSON body 必须包含该字段）；**缺失**时校验失败返回 400。例如不传 `page`、`page_size`、`plate_no` 等均会 400。

> ⚠️ **重要**：go-zero 的必填校验是"**键必须存在**"，**不是**"值不得为 0"。因此显式传 `page=0`、`vehicle_type=0`、`type=0` **会通过校验并进入业务逻辑**：
> - 分页字段（`page`/`page_size`）由 logic 层兜底（见 2.5），无副作用；
> - 枚举字段（`type`/`priority`/`vehicle_type`）传 `0` 会作为**非法值写入数据库**，调用方必须按各接口的取值约束传参（枚举一律 ≥ 1）。

### 2.5 分页约定

| 参数 | 类型 | 必填 | 缺失时 | 传 0 时 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `page` | int64 | 是 | 400 | 业务层兜底为 `1` | 页码，从 1 开始 |
| `page_size` | int64 | 是 | 400 | 业务层兜底为 `10` | 每页条数 |

分页响应统一结构：

```json
{ "total": 100, "list": [] }
```

- `total`：满足筛选条件的**总条数**（非当前页条数）
- `list`：当前页数据，**恒为数组**（空结果返回 `[]`，不返回 `null`）

各列表默认排序见对应接口说明。

### 2.6 时间与金额约定

| 类型 | 约定 |
| --- | --- |
| **时间** | 统一为**秒级 Unix 时间戳（int64）**，如 `1757894400`；`0` 表示该时间不存在/未设置 |
| **金额** | 统一为 **decimal 字符串**（两位小数），如 `"15.00"`，避免浮点精度误差；无费用时为 `"0.00"` |
| **枚举** | 统一为 `int8` 数值，字典见[附录 A](#附录-a枚举字典) |

## 四、接口详细定义

## 4.1 workorder-service（工单服务）

> 工单状态机见[附录 A.1](#a1-工单)；所有写操作均带 `tenant_id` 与**乐观锁 `version`** 校验。

### 4.1.1 创建工单

| 项 | 值 |
| --- | --- |
| 方法 / 路径 | `POST /api/workorder` |
| 直连地址 | `http://127.0.0.1:8091/api/workorder` |
| Handler / Logic | `CreateWorkOrderHandler` / `CreateWorkOrderLogic` |
| 权限 | 业主/企业租户、物业客服、园区管理员 |

**请求参数（JSON Body）**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `type` | int8 | 是 | 工单类型：1 报修、2 投诉、3 巡检、4 保洁、5 装修、6 搬运、7 其他；**取值必须为 1~7** |
| `title` | string | 是 | 工单标题 |
| `description` | string | 是 | 详细描述 |
| `priority` | int8 | 是 | 优先级：1 紧急、2 普通、3 低；**取值必须为 1~3** |
| `location` | string | 是 | 位置/楼栋房号 |

> `tenant_id`、`reporter_id`（发起人）由网关注入 Header，**请求体不需要传**。

**请求示例**

```json
{
  "type": 1,
  "title": "3 号楼 2 单元水管漏水",
  "description": "厨房主水管接口处持续渗水，需要紧急处理",
  "priority": 1,
  "location": "3 号楼 2 单元 502"
}
```

**响应参数（`data`）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int64 | 工单主键 ID |
| `order_no` | string | 工单号，格式 `WO-YYYYMMDD-XXXX`（如 `WO-20260915-0431`） |
| `status` | int8 | 当前状态，建单固定为 `0`（待派单） |

**响应示例**

```json
{
  "code": "0",
  "msg": "ok",
  "data": { "id": 1001, "order_no": "WO-20260915-0431", "status": 0 }
}
```

**业务规则**

1. 建单即进入 `待派单(0)`，`assignee_id`/`department_id` 默认 `0`，乐观锁 `version` 初始 `0`。
2. 同步写入建单流水 `work_order_flow`（`from_status=-1`、`action="create"`）。
3. 异步发布 Kafka 事件 `workorder-event`（`event="created"`），**尽力而为**：Kafka 不可用时仅记日志，不影响建单成功。

**错误码**

| code | HTTP | 场景 |
| --- | --- | --- |
| `M6-E-0001` | 500 | 缺少租户信息（直连未带 `x-tenant-id`） |
| `M2-E-5001` | 500 | 写库失败等内部错误 |

### 4.1.2 派单

| 项 | 值 |
| --- | --- |
| 方法 / 路径 | `PUT /api/workorder/:id/assign` |
| Handler / Logic | `AssignWorkOrderHandler` / `AssignWorkOrderLogic` |
| 权限 | 物业客服、园区管理员 |

**路径参数**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int64 | 工单 ID |

**请求参数（JSON Body）**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `assignee_id` | int64 | 是 | 处理人 ID（维修人员）；应为有效用户 ID（≥1） |
| `department_id` | int64 | 否 | 处理部门 ID |

**请求示例**

```json
{ "assignee_id": 2001, "department_id": 12 }
```

**响应参数（`data`）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int64 | 工单 ID |
| `order_no` | string | 工单号 |
| `status` | int8 | 流转后状态 `1`（处理中） |

**业务规则**

1. FSM 校验：仅允许 `待派单(0)` --assign--> `处理中(1)`。
2. **乐观锁**：更新条件为 `id + tenant_id + version`，并置 `version = version + 1`；
   `RowsAffected == 0` 即判定为并发冲突，返回 `M2-E-1003`，前端应提示"刷新后重试"。
3. 写派单流水 + 发布 `workorder-event`（`event="assigned"`，key=工单号）。

**错误码**

| code | HTTP | 场景 |
| --- | --- | --- |
| `M2-E-1001` | 500 | 工单不存在（或不属于当前租户） |
| `M2-E-1002` | 500 | 当前状态不允许派单（非待派单） |
| `M2-E-1003` | 500 | 派单冲突（并发修改，`version` 不匹配） |
| `M2-E-5001` | 500 | 内部错误 |

### 4.1.3 工单状态流转

| 项 | 值 |
| --- | --- |
| 方法 / 路径 | `PUT /api/workorder/:id/status` |
| Handler / Logic | `UpdateWorkOrderStatusHandler` / `UpdateWorkOrderStatusLogic` |
| 权限 | `submit`：维修人员；`approve`/`reject`：报修人/客服；`close`：客服、管理员 |

**路径参数**：`id`（int64，工单 ID）

**请求参数（JSON Body）**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `action` | string | 是 | 流转动作：`submit` / `approve` / `reject` / `close` |
| `remark` | string | 否 | 流转备注（验收意见、驳回原因等） |

**动作与状态迁移**

| action | 含义 | 允许的 from 状态 | to 状态 |
| --- | --- | --- | --- |
| `submit` | 提交完成 | 处理中(1) | 待验收(2) |
| `approve` | 验收通过 | 待验收(2) | 已完成(3) |
| `reject` | 驳回 | 待验收(2) | 处理中(1) |
| `close` | 关闭/取消 | 待派单(0)、处理中(1)、待验收(2)、已完成(3) | 已关闭(4) |

> `已关闭(4)` 为终态，**无任何出边**，不可再流转。

**请求示例**

```json
{ "action": "approve", "remark": "处理及时，验收通过" }
```

**响应参数（`data`）**：同 4.1.2（`id`、`order_no`、`status`）

**业务规则**

1. FSM 校验失败 → `M2-E-1002`。
2. 乐观锁更新，冲突 → `M2-E-1003`。
3. 目标状态为 `已完成(3)` 或 `已关闭(4)` 时，同步写入 `finished_at`。
4. 写流转流水 + 发布 `workorder-event`（`event="status_changed"`，含 `from_status`/`to_status`）。

**错误码**：`M2-E-1001`、`M2-E-1002`、`M2-E-1003`、`M2-E-5001`（映射同 4.1.2）

**Query 参数**

| 字段 | 类型 | 必填 | 说明 |

| `type` | int8 | 否 | 类型筛选，`0`/缺省表示不限 |
| `assignee_id` | int64 | 否 | 处理人筛选，`0`/缺省表示不限 |

| `page_size` | int64 | 是 | 每页条数，≥1 |

**请求示例**

```
GET /api/workorders?status=1&page=1&page_size=10
```

**响应参数（`data`）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `total` | int64 | 符合条件总数 |
| `list` | array | 工单列表项 |

列表项 `WorkOrderItem`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int64 | 工单 ID |
| `order_no` | string | 工单号 |
| `type` | int8 | 类型 |
| `title` | string | 标题 |
| `status` | int8 | 状态 |
| `priority` | int8 | 优先级 |
| `assignee_id` | int64 | 处理人 ID |
| `created_at` | int64 | 创建时间（秒级） |

**响应示例**

```json
{
  "code": "0",
  "msg": "ok",
  "data": {
    "total": 37,
    "list": [
      {
        "id": 1001,
        "order_no": "WO-20260915-0431",
        "type": 1,
        "title": "3 号楼 2 单元水管漏水",
        "status": 1,
        "priority": 1,
        "assignee_id": 2001,
        "created_at": 1757894400
      }
    ]
  }
}
```

**业务规则**

1. 强制按 `tenant_id` 隔离，未传筛选条件时返回本园区全量。

3. 列表项**不含**大字段（`description`、`attachments`），避免列表接口过载。

**处理流程**

1. 按 `qr_code + tenant_id` 查询记录；

5. **降级策略**：M1 不可达或未配置时仅记日志，**签入仍然成功**，`device_id` 为空 —— 前端不应因 `device_id` 为空而判定签入失败。

| `M2-E-2002` | 500 | 二维码无效（记录不存在）或已被核销（已签入/已签出） |
| `M2-E-2003` | 500 | 签入写库失败 |
| `M2-E-5001` | 500 | 内部错误 |

| `top` | bool | 是否置顶 |
| `publish_at` | int64 | 发布时间（秒级），未发布为 `0` |
| `created_at` | int64 | 创建时间（秒级） |

**业务规则**：强制 `tenant_id` 隔离；排序 **`top DESC, id DESC`**（置顶优先，其次最新在前）。

**错误码**：`M2-E-5001`；参数缺失返回默认 400

### 附录 B：错误码总表

错误码格式：`{模块}-{级别}-{4 位数字}`；M2 占用前缀 `M2-E-1xxx~5xxx`。

| code | HTTP | 含义 | 触发接口 |
| --- | --- | --- | --- |
| `0` | 200 | 成功 | 全部 |
| `M6-E-0001` | 500 | 请求参数错误（如缺少 `x-tenant-id`、签出未传 id/qr_code） | 建单、邀请、公告、签出 |
| `M2-E-1001` | 500 | 工单不存在 | 派单、状态流转、详情 |
| `M2-E-1002` | 500 | 工单状态非法或流转被禁止 | 派单、状态流转 |
| `M2-E-1003` | 500 | 工单派单/流转并发冲突（乐观锁失败） | 派单、状态流转 |
| `M2-E-2001` | 500 | 访客二维码已过期 | 签入 |
| `M2-E-2002` | 500 | 访客二维码无效或已被核销 | 签入、签出 |
| `M2-E-2003` | 500 | 访客签入失败 | 签入 |
| `M2-E-3001` | 500 | 停车记录不存在（无在场记录） | 离场 |
| `M2-E-3002` | 500 | 停车计费失败（已定义，暂未单独抛出） | 离场 |
| `M2-E-3003` | 500 | 停车设备不存在或未接入（已定义，暂未单独抛出） | 入场/离场 |
| `M2-E-4001` | 500 | 公告不存在（已定义，暂未使用） | 公告 |
| `M2-E-5001` | 500 | M2 服务内部错误兜底（含 DB 未初始化） | 全部 |
| `M6-E-0004` | 404 | 网关未匹配路由前缀 | 网关 |
| `M6-E-0006` | 502 | 网关上游服务不可用 | 网关 |

> 错误码定义见 `common/errorx/codes.go`，HTTP 映射见 `common/errorx/http_status.go`。

### 附录 C：异步事件契约（Kafka）

M2 部分能力为**事件驱动**，非 HTTP 调用，对接方（M5 大屏、M3 安防、通知类服务）按主题订阅。

| 主题 | 生产方 | 消息 key | 触发时机 | 载荷要点 |
| --- | --- | --- | --- | --- |
| `workorder-event` | workorder-service | 工单号 | 建单/派单/状态流转 | `event_id`(取自 `x-request-id`)、`event`(created/assigned/status_changed)、`action`、`tenant_id`、`work_order_id`、`order_no`、`from_status`、`to_status`、`operator_id`、`assignee_id`、`timestamp` |
| `parking-entry` | parking-service | 车牌号 | 车辆入场 | `ParkingRecord` 序列化 |
| `parking-exit` | parking-service | 车牌号 | 车辆离场 | `ParkingRecord` 序列化 |
| `alarm-event` | parking-service | 车牌号 | 异常车离场 | `device_id`、`severity`、`content`、`timestamp` |
| `notice-event` | notice-service | 公告标题 | 公告发布成功（含定时发布调度到期发布） | `Notice` 序列化 |
| `visitor-event` | visitor-service | 访客记录 ID | 邀请签发 / 扫码签入 / 签出离场 | `event_id`(取自 `x-request-id`)、`event`(invite/checkin/checkout)、`tenant_id`、`visitor_id`、`visitor_name`、`visitor_phone`、`inviter_id`、`status`、`device_id`、`timestamp` |
| `device-telemetry` | M1 event-dispatcher（**消费方**为 parking-service） | 设备 ID | 地磁/门禁上报 | 标准信封 `request_id`/`event_type`/`occurred_at` + `payload{tenant_id,plate_no,vehicle_type}`；兼容旧扁平格式；**入场按 `request_id` 幂等**（`parking_record.uk_request` 去重） |

**投递语义**

- M2 生产侧均为**尽力而为**：Kafka 不可用时仅记日志，**不回滚、不阻断**主业务（HTTP 仍返回成功）。
- 消费侧（停车）对格式非法/未知 `event` 的消息记 warn 后跳过，不阻塞后续消费；重复消费按业务键幂等处理。
- 主题与消费组常量定义于 `common/kafka/topics.go`。

### 附录 D：联调示例（curl）

```bash
# 0) 统一约定: 经网关 8080, 携带园区上下文头
BASE=http://localhost:8080

# 1) 创建工单
curl -i -X POST $BASE/api/workorder -H "Content-Type: application/json" -H "x-tenant-id: 1" -H "x-user-id: 3001" \
  -d '{"type":1,"title":"水管漏水","description":"厨房渗水","priority":1,"location":"3号楼502"}'

# 2) 派单 (工单ID=1001)
curl -i -X PUT $BASE/api/workorder/1001/assign -H "Content-Type: application/json" -H "x-tenant-id: 1" -H "x-user-id: 2000" \
  -d '{"assignee_id":2001,"department_id":12}'

# 3) 状态流转: 提交 -> 验收
curl -i -X PUT $BASE/api/workorder/1001/status -H "Content-Type: application/json" -H "x-tenant-id: 1" \
  -d '{"action":"submit"}'
curl -i -X PUT $BASE/api/workorder/1001/status -H "Content-Type: application/json" -H "x-tenant-id: 1" \
  -d '{"action":"approve","remark":"验收通过"}'

# 4) 工单列表 / 详情
curl -i "$BASE/api/workorders?status=1&page=1&page_size=10" -H "x-tenant-id: 1"
curl -i "$BASE/api/workorder/1001" -H "x-tenant-id: 1"

# 5) 访客邀请 -> 签入 -> 签出
curl -i -X POST $BASE/api/visitor/invite -H "Content-Type: application/json" -H "x-tenant-id: 1" -H "x-user-id: 3001" \
  -d '{"visitor_name":"张三","visitor_phone":"13800000000","visit_time":1757905200,"expire_time":1757991600,"reason":"探亲"}'
curl -i -X POST $BASE/api/visitor/checkin -H "Content-Type: application/json" -H "x-tenant-id: 1" \
  -d '{"qr_code":"<上一步返回的 qr_code>"}'
curl -i -X POST $BASE/api/visitor/checkout -H "Content-Type: application/json" -H "x-tenant-id: 1" -d '{"id":5001}'

# 6) 停车入场 -> 离场 -> 在场列表
curl -i -X POST $BASE/api/parking/entry -H "Content-Type: application/json" -H "x-tenant-id: 1" \
  -d '{"plate_no":"粤B12345","vehicle_type":2,"device_id_in":"geomag-in-01"}'
curl -i -X POST $BASE/api/parking/exit -H "Content-Type: application/json" -H "x-tenant-id: 1" \
  -d '{"plate_no":"粤B12345","device_id_out":"geomag-out-01"}'
curl -i "$BASE/api/parking/active?page=1&page_size=10" -H "x-tenant-id: 1"

# 7) 公告发布 -> 列表
curl -i -X POST $BASE/api/notice -H "Content-Type: application/json" -H "x-tenant-id: 1" -H "x-user-id: 2000" \
  -d '{"title":"停水通知","content":"9月18日停水","type":4,"top":true,"publish_at":0}'
curl -i "$BASE/api/notices?page=1&page_size=10" -H "x-tenant-id: 1"
```

### 附录 E：已知限制与注意事项

| # | 事项 | 影响 | 建议 |
| --- | --- | --- | --- |
| 1 | 业务错误码均为 `-E-` 级 → HTTP 500 | 前端若按 HTTP 状态码判定会误判为服务异常 | **一律以响应体 `code` 判定**；后续可改用 `-W-` 级返回 400 |
| 2 | 参数校验失败走 go-zero 默认错误体 | 该分支**不是**统一信封 | 前端对 400 做兼容解析 |
| 3 | 数据库未就绪时列表接口可能空指针 panic | 返回 500（非 `M2-E-5001`） | 加 nil-DB 守卫返回 `M2-E-5001`（**待修复**：`listworkorderslogic.go:35` 等） |
| 4 | 网关当前**无鉴权**，`x-tenant-id` 缺省为 `1` | 联调数据落在默认园区；无越权防护 | 接入 M6 `ValidateToken/CheckPermission` 后由鉴权中间件覆盖 |
| 5 | M1 `device-service` 尚无 gRPC server 实现 | 访客签入必然走降级，`device_id` 为空 | 属预期行为；M1 就绪后自动回填真实设备 ID |
| 6 | Kafka 事件"尽力而为" | 极端情况下可能丢事件（业务成功但事件未达） | 对账类场景以 DB 为准，不依赖事件做账 |
| 7 | 计费规则为代码内固定规则（5 元/小时、15 分钟免费） | 无法在线调整费率 | `parking_fee_rule` 表已就绪，可改为可配置 |
| 8 | 公告"定时发布"依赖调度任务 | `publish_at > 0` 的公告由 `PublishCron` 调度到期自动发布（2026-09-18 已实现，默认每分钟 + 启动补偿，多实例条件更新防重） | 调度精度为分钟级 |
