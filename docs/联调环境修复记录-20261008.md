## 三、⚠️ 要反馈给 M2 的两个问题

1. **两个迁移文件用的是 MariaDB 语法，MySQL 8 会直接报语法错**：
   - `deploy/sql/m2_p2_monthly_card_unique.sql`：`ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...`
   - `deploy/sql/m2_p2_visitor_blocklist_unique.sql`：同上 + `CREATE UNIQUE INDEX IF NOT EXISTS ...`
   - MySQL 8 **不支持** 列/索引上的 `IF NOT EXISTS`（MariaDB 支持）→ 在 MySQL 8 上执行会
     `ERROR 1064`。本机我按等价 DDL（去掉 `IF NOT EXISTS`）手工应用。
   - 建议：改成先查 `information_schema` 判断再 `ALTER`，或统一成 MySQL 8 兼容写法。
2. **三个迁移文件没有 `USE <库>` 语句**：`m2_p2_notice_recall.sql`、`m2_p2_parking_fee_rule.sql`、
   `m2_p2_visitor_blocklist.sql` 必须由调用方指定库（`mysql -D <db>`）。
   若 `run-all.sh` 是按“文件自带 USE”来编排的，这三个会落到 `No database selected`（实测）。

## 四、能耗（M4）：原来为什么没跑起来 + 2026-10-13 已补齐

**原来的判断（保留，便于追溯）**：

- `energy_data_db` 在本机**没有表**（`information_schema` 里 0 张），M4 的服务起来也查不到数据；
- 我当时还写了一条"能耗数据按设计落在 TDengine，本机未起 TDengine" —— **这条也不准**：
  `energy-data-service` 的配置里只有 MySQL/Redis/Kafka，**不依赖 TDengine**（TDengine 是 M1 设备遥测那条线）。
- 所以当时的结论"能耗卡保持降级是预期行为"只说对了一半：降级机制确实是设计内，但**服务本来就能在本机跑起来**。

**补齐步骤（本机已执行，可复现）**：

1. 建库：`mysql -uroot < deploy/sql/init.sql`（建出 `energy_data_db` 等全部库，幂等）；
2. 建表：`mysql -uroot -D energy_data_db < deploy/sql/m4_tables.sql`
   （建 `energy_reading` / `billing_rule` / `bill`；该脚本不带 `USE`，必须用 `-D` 指定库）；
3. **补 `tenant_id`（关键，仓库缺这个迁移）**：
   `ALTER TABLE ... billing_rule ADD COLUMN tenant_id ..., ADD KEY idx_tenant_status(...)`，
   `bill` 同理。为什么必须补：billing 代码按 `FindRule(tenantID)` / `FindBillByPeriod(tenantID)` 查，
   而 `billing_tables.sql` 的注释自己写着"bill/billing_rule 无 tenant_id，是已知遗留" —— **不补，新环境必崩**；
4. 造数：`cmd/seeddemo`（9 块表 × 每小时一条，9/1 补到当前整点，共 **9153 行**）。
   ⚠️ 这个脚本 `conf.MustLoad` **没带 `UseEnv()`**、且配置路径写死、不支持 `-f`：
   直接跑会报 `Kafka.Brokers: invalid character '$'`。做法是编译成 exe，
   另建一份"已解析"的配置放到 `<工作目录>/etc/energydata-api.yaml`，把进程工作目录指过去（**不动仓库文件**）；
5. 起三个服务（见第一节表格），三者的 MySQL 都指向 `energy_data_db`；
6. 出账走产品接口：`POST /api/billing/rule`（全园区单一电价 0.78）→
   `POST /api/billing/generate`（A/B/C 栋 × 2026-09）→ 3 张账单，金额自洽（A栋 12868.3 度 = 10037.27 元）。
7. **跨天要重跑一次第 4 步的造数**：大屏能耗卡与「能耗日报」的口径是**"当日"累计（当天 0 点起算）**，
   读数最大时间只到昨天的话，今天这一路就是 0 度。实测（2026-10-14 早上，答辩当天）：
   跨天后 `GET /api/dashboard/overview` 的 `energy.total_kwh` 从 226 变成 **0**（`degraded` 仍是空 ——
   这不是降级，是"今天确实还没用电"）；重跑造数补了 207 行，等 30s 聚合缓存过期后回到 **143.2**。
   脚本**幂等**：只补缺的小时，落在已有读数 45 分钟内的点不生成、不覆盖，不用清库。

**结果**：`GET /api/dashboard/overview` → `energy:{total_kwh:226}`、**`degraded: null`** —— 四路齐全。

**顺带发现的两个仓库级问题（未擅自改别人模块，待负责人确认）**：

1. `bill` / `billing_rule` 的 `tenant_id` **在仓库里没有任何建表/迁移脚本**，而代码依赖它 → 建议补一个
   `deploy/sql/m4_billing_tenant_id_migration.sql`；
2. `app/billing-service/etc/billing-api.yaml` 里**明文硬编码了共享库的 DSN（含 root 密码）**且已入库 →
   建议改为环境变量注入，并轮换该凭据（历史里删不干净）。

## 五、前端为什么有的页面“数据是空的”——两个真实原因

1. **服务没起** → 请求打到没监听的端口，页面空。
   本次已补齐 M1/M2/M3/M5 共 10 个进程后，8 个页面全部出数据。
2. ⭐ **角色头缺失导致 RBAC 把结果裁空**（更隐蔽）：部分接口（如 M2 发公告、访客列表）
   会按角色做行级收缩，缺 `x-role-ids` 时结果被裁成“只看自己发起的”。
   实测：带 `x-role-ids: 1` 才看得到 3 条访客；不带就是 0 条 —— **不是没数据，是被裁掉了**。
   因此本地演示代理（`vite.config.local.ts`）除 `x-tenant-id` 外**必须同时注入
   `x-user-id: 1` 与 `x-role-ids: 1`**，否则页面看起来是空的。

### 7.2 ⚠️ M1 的库也缺表，而且这次我踩了一个坑（如实记录）
