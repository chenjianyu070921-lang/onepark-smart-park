## 二、本机数据库：补上的缺失结构（**M2 的表结构漂移**）

本机的 M2 三张表是**旧版本**：只应用过基础建表 + `l2_tenant_id_migration.sql`，
**`m2_p2_*` 系列迁移从未应用**，导致代码写入时报 `Error 1054 Unknown column`。已补齐：

| 库.表 | 补的列 / 索引 | 触发它的报错 |
|---|---|---|
| `workorder_db.work_order` | `alarm_id VARCHAR(64) NULL` + `uk_alarm_id` + `idx_tenant_status_assignee` | 建工单报 `M2-E-5001`，日志 `Unknown column 'alarm_id'` |
| `notice_db.notice` | `source VARCHAR(64) NULL` + `uk_source` + `idx_tenant_status` | 发公告报 `M2-E-5001`，日志 `Unknown column 'source'` |
| `notice_db.notice` | `recalled_at DATETIME NULL`（来自 `m2_p2_notice_recall.sql`） | 同上，接着报 `Unknown column 'recalled_at'` |
| `parking_db.parking_record` | `request_id VARCHAR(64) NULL` + `uk_request` + `idx_plate_status` | 录入场报 `M2-E-5001`，日志 `Unknown column 'request_id'` |
| `parking_db.monthly_card` | 生成列 `active_plate_key` + 唯一键 `uk_monthly_active_plate` | 见第三节（该迁移文件在 MySQL 8 上语法不兼容） |
| `visitor_db.visitor_blocklist` | 生成列 `phone_key` / `id_no_key` + 两个唯一键 | 同上 |

其余 M2/M3 的建表与迁移 SQL（`m2_*`、`m3_mysql_tables.sql`）已用
`mysql --force --default-character-set=utf8mb4 -D <库> < 文件` 全量跑过，可重复执行。

## 三、⚠️ 要反馈给 M2 的两个问题

1. **两个迁移文件用的是 MariaDB 语法，MySQL 8 会直接报语法错**：
   - `deploy/sql/m2_p2_monthly_card_unique.sql`：`ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...`
   - `deploy/sql/m2_p2_visitor_blocklist_unique.sql`：同上 + `CREATE UNIQUE INDEX IF NOT EXISTS ...`
   - MySQL 8 **不支持** 列/索引上的 `IF NOT EXISTS`（MariaDB 支持）→ 在 MySQL 8 上执行会
     `ERROR 1064`。本机我按等价 DDL（去掉 `IF NOT EXISTS`）手工应用。
   - 建议：改成先查 `information_schema` 判断再 `ALTER`，或统一成 MySQL 8 兼容写法。
2. **三个迁移文件没有 `USE <库>` 语句**：`m2_p2_notice_recall.sql`、`m2_p2_parking_fee_rule.sql`、
   `m2_p2_visitor_blocklist.sql` 必须由调用方指定库（`mysql -D <db>`）。
   若 `run-all.sh` 是按“文件自带 USE”来编排的，这三个会落到 `No database selected`（实测）。

## 四、能耗（M4）为什么没跑起来

- `energy_data_db` 在本机**没有表**（`information_schema` 里 0 张），M4 的服务起来也查不到数据；
- 能耗数据按设计落在 **TDengine**（时序库），本机只起了 MySQL/Redis/Kafka，未起 TDengine；
- 因此**能耗卡保持降级为 `null`**，这是 M5 侧「逐源降级」的预期行为，不是 M5 的缺陷。

要补的话：起 TDengine 容器 → 应用 `deploy/sql/m1_tdengine_tables.sql` 与 M4 的建表脚本 → 起
`energy-data-service`（8061/9061）→ 重启 dashboard。

## 五、前端为什么有的页面“数据是空的”——两个真实原因

1. **服务没起** → 请求打到没监听的端口，页面空。
   本次已补齐 M1/M2/M3/M5 共 10 个进程后，8 个页面全部出数据。
2. ⭐ **角色头缺失导致 RBAC 把结果裁空**（更隐蔽）：部分接口（如 M2 发公告、访客列表）
   会按角色做行级收缩，缺 `x-role-ids` 时结果被裁成“只看自己发起的”。
   实测：带 `x-role-ids: 1` 才看得到 3 条访客；不带就是 0 条 —— **不是没数据，是被裁掉了**。
   因此本地演示代理（`vite.config.local.ts`）除 `x-tenant-id` 外**必须同时注入
   `x-user-id: 1` 与 `x-role-ids: 1`**，否则页面看起来是空的。

### 7.2 ⚠️ M1 的库也缺表，而且这次我踩了一个坑（如实记录）

`device_db` 在本机只有 **1 张表**（`device`），`product` / `shadow` / `command_log` 都不存在
→ 产品接口直接 **500**。补表时我执行了 `deploy/sql/m1_mysql_tables.sql`，**没有先读它**：

> ⚠️ 该脚本头部是 `DROP TABLE IF EXISTS` + `CREATE TABLE`（**给全新初始化用的**，不是幂等迁移），
> 结果把本机原有的 **5 台设备与产品数据全部清空**。

**已恢复**：重新建了 3 个产品（`pk_smoke` / `pk_camera` / `pk_meter`）并重新注册了 **6 台设备**
（走真实接口 `POST /api/device/register`），状态分布 在线 4 / 离线 1 / 故障 1（状态是演示补的，
真实取值由遥测驱动）。**原数据是 M5 e2e 测试留下的设备（`m5e2e-*`），不是人工维护的资产**，但性质上仍是误删。

**教训（与本文第二节同一个道理）**：执行任何 SQL 前先看它有没有 `DROP` / `TRUNCATE`；
`deploy/sql/` 下**混着两类文件**——给全新环境用的初始化脚本（含 DROP）与增量迁移（幂等），
文件名与注释都不足以区分，只能打开看。

### 7.3 同类问题：M1 的两个迁移也缺 `USE`

`m1_device_add_tenant_zone.sql`、`m1_device_add_type_location.sql` 没有 `USE device_db`
→ 必须由调用方 `-D device_db`，否则 `No database selected`（与第三节 M2 的三个文件同一问题，
**这是仓库里一类普遍现象，建议在 `run-all.sh` 里统一处理**）。
