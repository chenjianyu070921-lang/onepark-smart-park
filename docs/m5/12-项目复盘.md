## 二、本轮抓到并修掉的 Bug（按危害排序）

| # | Bug | 危害 | 怎么发现的 |
|---|---|---|---|
| 1 | **工单号同秒撞号 → 告警静默丢单** | ⭐⭐⭐ **真实告警建不出工单且无人察觉**（消息位移已提交，不会重投）。同秒 5 张单约 1% 撞号、50 张约 71% | 演示 seed 脚本连建 5 张工单**挂了 1 张** |
| 2 | **入驻率经 gRPC 查询恒为 0** | ⭐⭐ 非 0 租户拿到"已租面积 0"，**看起来像业务问题**而非故障 | 功能点复核（逐条对照实现） |
| 3 | **重派锁 TTL 与扫描周期脱钩** | ⭐⭐ 周期调大后出现"锁已过期、下一轮还没开始"的**保护空窗**，两实例可能并发扫同一批 | 功能点复核 |
| 4 | **审计表 4/5 个写入点漏 `tenant_id`** | ⭐ 按租户查流水会整段查不到，工单时间线"缺一半" | 做详情时间线时顺带发现 |
| 5 | **状态机"靠失败路径拿到正确的 0"** | ⭐ 定时炸弹：一旦补上建单转移边，`FromStatus` 语义**当场反转** | 功能点复核 |
| 6 | **我自己写的前端对接文档 4 处与实现不符** | ⭐ 前端照它联调会直接 404 / 误判 | 静态扫描子任务交叉核对 |

> **共同特征**：这 6 个没有一个是"写错的代码"，全是**接线 / 联动 / 参数 / 文档**层面的问题 ——
> 代码看起来是对的，但那个参数不生效、那个常量不跟配置、那份文档不是照代码写的。
>
> **另一条规律**：#1 是**交付脚本**（演示 seed）抓出来的。这类"按真实接口批量造数"的脚本，
> 实际就是最好的集成测试。

### 2. 代码生成器的输出**必须逐行 diff 后才提交**

用 `goctl api go` 重新生成 leasing 时，它**顺手删掉了两处手工添加**：
`routes.go` 里的 `GET /health` 路由（`.api` 无对应语法，生成器不认识）与
`types.go` 里的 `BillAutoResp.Failed`（`.api` 里缺失，属**源头漂移**）。
前者会打挂健康检查，后者直接编译不过。
→ 已回滚生成产物、改为手工最小改动，并把警告写进 `leasing.api` 头部；同时把 `Failed` 补进 `.api` 消除漂移。

### 3. 排障信息不能吞

- 压测工具第一版**只报失败次数不报原因** → 差点把"本机端口耗尽"算到被测服务头上。
- `go build` 混在大段脚本里、输出还被 `Select-String` 过滤 → **错误行被吞、`EXIT=1` 被后续 test 结果盖过**
  → 带病文件被提交（`wsload` 残留 import）。
- 推送失败时用 `2>&1 | Out-Null` → 把 TLS 握手失败误判成"代理没开"，白试 7 次。
→ **规矩：构建单独一条命令跑、只看 EXIT；错误必须打出来。**

### 4. 长期记忆里的"机制性结论"要用前回代码确认

记忆写着"重派锁加完不自解、靠 TTL 过期"，而代码里其实有 `defer` + Lua **会主动释放**，
TTL 只是崩溃兜底。差点按错误前提去改一个本来就对的实现。
同样地，记忆里"重试几次通常就好"的推送建议，实际 7 次全败、**绕过代理一次就过**。

## 四、亮点

1. **可用性优先的设计被数据证明**：逐源降级下，上游全挂时聚合层仍 **7.9→8.7 µs**，
   **降级几乎不额外花钱**；大屏永远 200，用 `degraded` 如实告诉前端哪几路不可用。
2. **WS 广播隔离经得起压力**：500 客户端 p50 **6.5 ms**、零丢帧、21.4 KB/连接；
   一个卡住的连接**不拖累**其他人（每连接缓冲 + 异步写泵）。
3. **没把"能跑"当"跑得好"**：性能数字全部附**采集命令**与**口径限制**
   （压测端端口耗尽、零耗时桩会得出反直觉结论、穿透与命中要分开给）。
4. **诚实留痕**：修不了的（表结构变更、需外部服务的指标）一律写进"未做/已知限制"，不藏。
