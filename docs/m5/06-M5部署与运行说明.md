# 06 · M5 部署与运行说明

> 适用：`leasing-service` / `dashboard-service` / `dispatch-service`
> 配套：`deploy/sql/m5_*.sql`、`deploy/m5/`（容器化片段）
>
> 本文只讲**怎么把它跑起来**。设计原理见 01~04，接口契约见 05。

---

## 1. 服务清单与端口

M5 一共 **4 个进程**：

| 进程 | 端口 | 职责 | 启动入口 |
|---|---|---|---|
| leasing-service (HTTP) | **8051** | 招商租赁，面向前端/网关 | `app/leasing-service/leasing.go` |
| leasing-service (gRPC) | **9051** | 服务间聚合调用 | `app/leasing-service/grpcserver/main.go` |
| dashboard-service | **8052** | 指挥大屏聚合 + WebSocket 推送 | `app/dashboard-service/dashboard.go` |
| dispatch-service | **8053** | 指挥调度（工单/派单） | `app/dispatch-service/dispatch.go` |

**为什么 leasing 是两个进程**：HTTP 面向前端与网关，gRPC 面向服务间调用，二者生命周期与暴露面不同。
**定时任务（合同到期/自动续约/月度出账）只在 HTTP 侧启动** —— 定时任务只能有一个执行方，
两个进程都跑会重复扫描（虽有 Redis 锁兜底，但没必要制造这种竞争）。

## 2. 依赖的中间件与上游

| 依赖 | 用途 | 说明 |
|---|---|---|
| MySQL 8.0 | 三张业务库 | `leasing_db` / `dashboard_db` / `dispatch_db`（每服务独立库，禁止跨库 JOIN） |
| Redis 7 | 聚合缓存、分布式锁 | ⚠️ 宿主机端口是 **6380**（6379 被本机原生 redis 占用） |
| Kafka | 告警/工单事件消费 | ⚠️ **两个消费者默认关闭**（`Enabled: false`），开启前需确认 topic 授权 |
| M1~M4 gRPC | 大屏四路数据源 | device 9001 / workorder 9091 / alarm 9009 / energy 9061 |

只依赖 MySQL + Redis 就能起；**上游没起也不影响启动** ——
`dashboard` 的四路上游配了 `NonBlock: true`，调用失败由聚合层**逐源降级**为 `null` 并列入 `degraded`，
接口整体仍返回 200，不抛 5xx。

## 3. 首次准备：数据库

```bash
# 1) 中间件（只需 mysql + redis 也能跑 M5）
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d mysql redis

# 2) 三张库由 init.sql 建好（leasing_db / dashboard_db / dispatch_db 都在其中）
#    全新环境执行全量建表 —— 幂等，可反复执行
docker cp deploy/sql/m5_mysql_tables.sql onepark-mysql:/tmp/m5.sql
docker exec onepark-mysql sh -c "mysql -uroot -p<密码> < /tmp/m5.sql"

# 3) 已经建过库的环境要补列，执行增量迁移（非幂等，用 --force 忽略已存在列的 1060）
docker cp deploy/sql/m5_mysql_migrations.sql onepark-mysql:/tmp/m5m.sql
docker exec onepark-mysql sh -c "mysql --force -uroot -p<密码> < /tmp/m5m.sql"
```

### ⚠️ 两个必须知道的坑

1. **`mysql < file.sql` 遇错即停** —— 多语句文件里若前段有非幂等语句报错，**后面所有语句会被静默跳过**。
   所以增量改表要么单独 `-e` 执行，要么只跑迁移文件。
2. **平台级租户迁移也要执行**：`deploy/sql/l2_tenant_id_migration.sql` 给 `dispatch_task`、
   `dispatch_task_log`、`lease_contract_status_log` 等加了 `tenant_id`。
   不执行的话，M5 任何写库操作都会报 `Unknown column 'tenant_id' in 'field list'`。
   （该文件是全平台共用的，M5 只需其中 M5 那几段。）

## 4. 本地开发运行

```bash
# 招商租赁：HTTP + gRPC 两个进程
go run ./app/leasing-service       -f app/leasing-service/etc/leasing-api.yaml
go run ./app/leasing-service/grpcserver -f app/leasing-service/etc/leasing-grpc.yaml

# 大屏聚合 + WebSocket
go run ./app/dashboard-service     -f app/dashboard-service/etc/dashboard-api.yaml

# 指挥调度
go run ./app/dispatch-service      -f app/dispatch-service/etc/dispatch-api.yaml
```

### 配置说明

- `etc/*.yaml` 里写的是**本地开发默认值**（`127.0.0.1:3306` / `127.0.0.1:6380`）。
- 三个 HTTP 入口都已启用 `conf.UseEnv()`，因此也可以改成 `${VAR}` 形式由环境变量注入（容器部署走这条路）。
- `Redis.DB` 必须是**数字字面量**：写成 `${REDIS_DB}` 会被展开成字符串，导致 int 字段类型不匹配。
- `JwtSecret` 为空 = **鉴权放行**（开发期行为）。填上密钥后：
  - HTTP 侧审计流水的 `operator_id` 才会从 token 取值；
  - `/ws/dashboard` 的 `?token=` 会被真正校验（**未配置密钥时 WebSocket 直接拒绝接入**，这是刻意的 fail-closed）。

## 6. 部署后验证

> ⚠️ **直连服务时必须手动带上 `x-tenant-id`**（下面的 `-H` 就是干这个的）。
> 生产环境这个头由**网关注入**，业务服务自己不解析 JWT；直连（本地联调 / curl / gRPC 测试）
> 绕过了网关，不加这个头 ctx 里的租户就是 0 ——
> 而合同/账单/工单都按 ctx 的租户做行级过滤，**不加头会看到空列表**（不是接口坏了）。
> 本地与联调环境已把存量数据统一回填到默认园区 **1**（对齐 `l2_tenant_id_migration.sql` 的口径）。

```bash
# 招商租赁
curl -s -H 'x-tenant-id: 1' http://127.0.0.1:8051/api/lease/zones        # 园区列表(全局主数据, 不隔离)
curl -s -H 'x-tenant-id: 1' http://127.0.0.1:8051/api/lease/contracts    # 合同列表
curl -s -H 'x-tenant-id: 1' http://127.0.0.1:8051/api/lease/bills        # 租金账单列表
curl -s -H 'x-tenant-id: 1' http://127.0.0.1:8051/api/lease/bills/summary # 账单汇总
# 指挥调度
curl -s -H 'x-tenant-id: 1' http://127.0.0.1:8053/api/dispatches         # 工单列表
curl -s -H 'x-tenant-id: 1' http://127.0.0.1:8053/api/dispatch/staffs    # 人员池
# 健康检查(无前缀, 且不需要租户)
curl -s http://127.0.0.1:8051/health
```

> **路径注意**：租赁前缀是 `/api/lease`（**不是** `/api/leasing`）；
> 调度列表是 `/api/dispatches`（复数）—— 写成 `/api/dispatch/tasks` 会命中 `/dispatch/:id`
> 并把 `tasks` 当 id 转数字，报 **400**（不是 404，容易误判成"路由不存在"）。

**大屏四路是否真的通**：看 `overview` 返回的 `degraded` 数组 ——
四路正常时为空；某路起不来时该字段为 `null` 且其名字出现在 `degraded` 里。

## 7. 常见问题

| 现象 | 原因与处理 |
|---|---|
| 服务起不来，日志 `redis ping failed` | 宿主机 Redis 在 **6380**（不是 6379），确认 yaml 里的 `Addr` |
| **列表是空的 / 单据"建完就查不到"** | 99% 是租户维度对不上：直连没带 `x-tenant-id`，或写入与查询用的不是同一个租户。合同/账单/工单**全部按 ctx 的租户过滤**。本地统一用 `1` |
| 自动建的工单在列表里看不到 | 消费者建的工单落 `Kafka.DefaultTenantId`（默认 1）；若与你调用时用的租户不同就看不见，见 `etc/dispatch-api.yaml` 的注释 |
| `gofmt` 报一堆文件需格式化 | 全仓 CRLF 行尾所致，**别批量重排**（会制造整文件 diff），只格式化自己改的文件 |
| 写库报 `Unknown column 'tenant_id'` | 未执行 `l2_tenant_id_migration.sql`，见 3.2 |
| 大屏数据"没更新" | `overview` 有 **30s 租户维度缓存**。验证前先 `redis-cli -p 6380 -a <密码> DEL m5:dashboard:overview:tenant:0` |
| 大屏某张卡是 `null` | 该路上游没起或调用失败，看 `degraded`；这是设计内的降级，不是故障 |
| WebSocket 连不上 | `JwtSecret` 未配置时**拒绝接入**（fail-closed）。本地联调要么配密钥并带 `?token=`，要么经网关注入身份头 |
| 工单卡在「已指派」不动 | 超时重派 cron 每 60s 扫一次（`Reassign.IntervalSec`），最坏迟到约 1 分钟；重派达 3 次会释放回「待指派」交人工 |
| 账单重复生成 | 有唯一键 `uk_contract_period(contract_id, billing_period)` 兜底，重复插入会被数据库拒绝并计入 `skipped` |

## 8. 定时任务一览（只在 leasing HTTP 侧启动）

| 任务 | 时机 | 说明 |
|---|---|---|
| 合同到期 | 每日 00:05 | `自动续约` 开关关闭的合同到期即转「已到期」 |
| 自动续约 | 每日 00:05 | 仅对合同条款显式约定 `auto_renew=1` 的合同顺延租期 |
| 月度出账 | 每月 1 号 00:10 | 生成上月经租账单，靠唯一键幂等 |
| 指派超时重派 | 每 60s | 派单后 5 分钟无人接单则改派；无人可派或达上限则释放回池 |

以上四个都用 **Redis 分布式锁** 防多实例重复执行。
