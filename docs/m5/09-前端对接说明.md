## 一、基地址与端点数

| 服务 | 直连端口 | 网关路径 | 端点数 |
|---|---|---|---|
| 租赁 `leasing-service` | `:8051` | `/api/lease/**` | 13 |
| 大屏 `dashboard-service` | `:8052` | `/api/dashboard/**` + `/ws/dashboard` | 3 + 1 WS |
| 调度 `dispatch-service` | `:8053` | `/api/dispatch/**` | 8 |
| | | **合计** | **24 HTTP + 1 WS** |

> 前端统一走网关（`/api/lease`、`/api/dashboard`、`/api/dispatch`、`/ws/dashboard`），
> 网关会把请求转发到上表对应的容器端口。直连端口仅用于本机联调。

⚠️ **健康检查不在网关口径内**：三个服务的 `/health` 都是**无前缀**注册的（`GET /health`），
而网关 upstream 只映射 `/api/**` 与 `/ws/dashboard` —— 所以**探活请直连服务端口**，
不要用 `/api/dispatch/health` 这种拼法（会 404）。

## 二、鉴权与租户（**先看这一节，最容易踩**）

### 2.1 走网关（生产/联调默认）

网关注入身份头，**前端不用自己塞**：

| 头 | 含义 |
|---|---|
| `x-user-id` | 用户 ID |
| `x-role-ids` | 角色列表 |
| `x-tenant-id` | **租户/园区 ID**（数据隔离的口径） |

⚠️ **`x-tenant-id` 可能不注入**：当登录用户自身 `tenant_id == 0` 时网关注入为空，
由服务侧 `DefaultTenantId` 兜底。**前端联调时如果看到"数据不对/查不到"，先确认这个头有没有值**。

### 2.2 直连服务（本机联调）

直连时没有网关，**必须自己带 `x-tenant-id`**：

```http
GET /api/dashboard/overview HTTP/1.1
x-tenant-id: 1
```

> 直接收口到 `types` 的 `header:"X-Tenant-Id,default=0"` —— 不传就按 0 查，可能什么都查不到。
> HTTP 头大小写不敏感，`x-tenant-id` / `X-Tenant-Id` 都行。

### 2.3 WebSocket 鉴权

浏览器 WebSocket **无法自定义请求头**，所以走 query：

```
ws://<host>/ws/dashboard?token=<access_token>
```

- 令牌必须是 **access** 类型（refresh 会被拒）；签名无效 / 过期 → 握手即 401。
- 网关已校验的路径下，服务端优先用网关注入的身份；没有注入头时才回退校验 `?token=`。

## 三、CORS 现状

三个服务**都装了** `middleware.Cors`，且**刻意放在 JWT 外层**（代码注释写明：浏览器 `OPTIONS` 预检不带 token，
JWT 在外层会把预检判成 401）。`OPTIONS` 由 Cors 直接返回 204 并中断，不会走到鉴权。

> 也就是说：**跨域预检已处理**；如果前端仍遇到跨域问题，优先查网关/反代的转发是否透传了 `Origin` 与预检请求。

## 五、大屏主接口：`GET /api/dashboard/overview`

### 5.1 正常形态（字段按 `types.go` 定义，取值仅为示例）

```json
{
  "work_order": {
    "available": true,
    "today_total": 12,
    "unfinished": 7,
    "avg_handle_sec": 3600.5,
    "complete_rate": 0.75
  },
  "alarm":  { "total": 6, "critical": 1, "major": 2, "minor": 2, "info": 1 },
  "device": { "total": 1263, "online": 1240, "offline": 12, "fault": 11 },
  "energy": { "total_kwh": 12483.5, "total_water": 321.2 },
  "degraded": [],
  "cached": true,
  "updated_at": 1790144391,
  "elapsed_ms": 6
}
```

### 5.2 降级形态（**实测抓取**：四路上游全不可达时）

```json
{
  "work_order": null,
  "alarm": null,
  "device": null,
  "energy": null,
  "degraded": ["alarm", "energy", "work_order", "device"],
  "cached": false,
  "updated_at": 1790144391,
  "elapsed_ms": 6
}
```

**这就是逐源降级**：任意一路挂掉，只有那一路变 `null`，**整体仍返回 200**（绝不 5xx），
挂掉的数据源名进入 `degraded`。前端据此把对应卡片标成「暂不可用」——**不要显示 0**。

### 5.3 前端必读的三个语义

| 字段 | 语义 | 前端该怎么做 |
|---|---|---|
| 卡片为 `null` | 该路**数据不可用**（≠ 0） | 显示「暂不可用」占位，**不要当成 0 渲染** |
| `degraded` | 不可用的数据源名单（`work_order`/`alarm`/`device`/`energy`） | 可用它统一给卡片加降级角标 |
| `cached` | 本次是否命中 30s 缓存 | 一般不用展示；**刷新按钮**可据此提示「数据为近 30 秒内快照」 |
| `updated_at` | 聚合时间，**Unix 秒**（不是毫秒） | `new Date(updated_at * 1000)` |
| `elapsed_ms` | 本次聚合耗时（毫秒） | 可放在运维/调试角标 |

> `WorkOrderCard.avg_handle_sec` 与 `EnergyCard.total_water` 是**可空**的：
> 对应上游契约没提供该指标时为 `null`（代码里明确「不用 0 冒充」）。前端同样要按"无数据"渲染。

## 六、WebSocket 推送：`/ws/dashboard?token=...`

**两条通道合一**：`5 秒一帧全量快照` + `事件到达即推增量`。都走同一个连接。

### 6.1 消息一：`snapshot`（每 5 秒一帧）

```json
{
  "type": "snapshot",
  "data": { /* 与 /api/dashboard/overview 的响应体完全一致 */ }
}
```

- `data` 就是上面 5.1 / 5.2 的报文（同一套结构，同一个 `degraded` 语义）。
- 服务端**只在有客户端在线时**才构建快照（无人在线不空转）。
- 事件到达时会让缓存失效并**立即重算**，所以快照可能因事件而提前刷新（不必等满 5 秒）。

### 6.2 消息二：`event`（增量，到达即推）

```json
{
  "type": "event",
  "source": "alarm",
  "topic": "alarm-event",
  "received_at": 1790144391,
  "data": { /* 原始事件体，透传 */ }
}
```

| 字段 | 说明 |
|---|---|
| `source` | `alarm`（告警）/ `workorder`（工单），用于分流 |
| `topic` | 原始 Kafka topic，便于排查与埋点 |
| `received_at` | **服务端接收时间，Unix 秒** |
| `data` | 原始事件体**原样透传**（结构由上游定义，未做裁剪） |

### 6.3 前端分发建议

```js
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  switch (msg.type) {
    case 'snapshot': renderFull(msg.data); break;       // 全量覆盖渲染
    case 'event':    onIncrement(msg.source, msg.data); break;  // 局部高亮/Toast/计数 +1
    default: break;                                     // 未知类型忽略, 不要抛错
  }
};
```

- **未知 `type` 必须忽略**（服务端以后可能加新通道，前端不应崩）。
- 建议实现**自动重连 + 指数退避**；重连成功后先等一帧 `snapshot` 再认为"已恢复"。
- 断线期间事件会丢（增量不补发），**重连后的那帧快照就是真值**——这也是每 5 秒全量存在的意义。

## 七、常见坑（都是会真出问题的）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | ⭐ **金额是字符串**：`amount` / `monthly_rent` / `deposit` / `total_amount` / `unpaid_amount` 等在响应里是 **string**（定长 2 位小数，如 `"10000.50"`） | 直接展示；要计算请用 `decimal` 库或整数分，**不要 `parseFloat` 后回显**（会丢尾零、出现 `10000.5`） |
| 2 | ⭐ **时间戳是秒**（`updated_at` / `received_at` / `end_date` 类字段） | 统一 `* 1000` 后再交给日期库 |
| 3 | ⭐ **错误响应里的 `code` 是字符串**：`{"code":"M5-E-1006","msg":"..."}` | 比较错误码用**字符串相等**，不要 `parseInt`；码表见 `docs/m5/05-接口与数据契约.md` |
| 4 | 卡片 `null` ≠ 0 | 按「暂不可用」渲染（见 5.3） |
| 5 | 幂等：自动建单按 `alarm_id` 幂等 | 重复投递不会重复建单，前端**不要**把"没新增"当成失败 |
| 6 | `dispatch` 的路径是 `/api/dispatch/dispatch/...`（前缀 + 资源名重名） | 照抄第四节表格，别按直觉拼 |
