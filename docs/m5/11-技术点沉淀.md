## 1. 四路聚合的**逐源降级**

**应用场景**：大屏要同时展示工单、告警、设备、能耗四路数据，四个上游分别是 M2/M3/M1/M4 的 gRPC 服务。
演示现场只要有一路没起（或慢），整块大屏就白屏——这是最不能接受的失败形态。

**实现方式**
- 四路**并发**请求，各自带独立超时；任一失败只把该路标成 `degraded`，**不影响另外三路**。
- 未配置地址的路由到 `provider/notready.go`（只返回哨兵错误 `ErrSourceNotReady`），
  而不是让服务启动就 fatal —— "上游没起"和"上游报错"对使用方是同一件事。
- 卡片为 `null` 而不是 `0`：**"没有数据"与"数据是 0"必须能区分**，否则大屏会显示"0 个告警"骗人。

**证据**
- 上游全挂时 `overview` 仍返回 **200**，`degraded = [alarm, device, energy, work_order]`（自检脚本 C 项实测）。
- 聚合层净开销：四路正常 **7.9 µs/op**；单路挂 **8.8 µs**；四路全挂 **8.7 µs**
  → **降级几乎不引入额外代价**（不是"用性能换可用性"）。

**踩过的坑**
- ⭐ `avg_handle_sec` 这类可空指标用 **`*float64`** 而不是 `float64`：
  退化成 0 会被前端读成「1970 年处理完」或「0 秒完成」，语义直接错掉。代码注释里写明了这一点。
- 健康检查靠 `Test-NetConnection` 只探端口是**不够的**：端口开着不代表 gRPC 可用。
  自检脚本因此走**真实 RPC Ping**（B 项），而不是只看端口。

## 2. 缓存的价值与**击穿防护**

**应用场景**：大屏 5 秒推一帧 + 页面高频刷新，同一个租户的聚合结果没必要每次重算。

**实现方式**
- `overview:{tenant}` + **30 秒 TTL**；`cached` 字段显式告诉调用方是否命中。
- `golang.org/x/sync/singleflight`：并发未命中时**只让一个请求去聚合**，其余等它的结果。
- **事件驱动失效**：Kafka 事件到达时置 `Dirty` 并 `InvalidateOverviewCache`，下次推送立即重算
  —— 保证「告警解除」这类变化不会因为 30s TTL 而延迟可见。

**证据**
- 上游各 5ms 时：**命中 0.60ms vs 未命中 6.78ms = 11 倍**；
  且命中耗时**完全不随上游变慢**（565→603 µs）—— 符合"命中路径的成本只是一次 Redis 往返"。
- 防击穿：`TestOverview_StampedeProtection` 断言 500 并发只聚合 **1** 次，实测 PASS。

**踩过的坑**
- ⭐ **用零耗时测试桩会得出"缓存是负优化"的错误结论**：命中 565µs > 聚合 7.9µs。
  那不是缓存慢，是**桩太快** —— 真实上游是毫秒级网络调用，而 Redis 是内网一次往返。
  → 所以补了一对「上游各 5ms」的配对基准，只有对照组才说明价值。

## 3. WebSocket 双通道与**广播隔离**

**应用场景**：大屏既要周期性全量（防止增量丢包后画面永久不一致），也要事件到达即推（告警要"立刻"）。

**实现方式**
- **一个连接两条通道**：`snapshot`（每 5s，`data` 与 `/overview` 同一结构）+ `event`（到达即推，`source`/`topic`/`received_at` 透传）。
- 每连接一个 **16 条缓冲的 channel + 独立写泵 goroutine**，Hub 广播只往 channel 投递，**不直接写 socket**。
- 慢客户端：缓冲满即踢（`TestBroadcast_StaleClientKicked` 覆盖），避免一个卡住的连接拖垮所有人。

**证据**
- 50/200/500 客户端：推送延迟 p50 = **1.51 / 3.02 / 6.50 ms**（≈ **13 µs/客户端**），**零丢帧**。
- 内存 ≈ **21.4 KB/连接** → 1 万客户端约 214 MB（容量估算依据）。
- 全部断开后 **22 ms** 内在... 在线数归 **0**；反复"连 100 → 全断开"3 轮无泄漏。
- ⭐ 一个**连上就不读**的慢客户端在场时，20 个正常客户端仍 **2 ms** 收齐 100/100 —— 证明隔离生效。

**踩过的坑**
- 「只在有客户端在线时才构建快照」是**不准确的说法**：实现是**每 5s 都构建**，只有 `Broadcast` 前判断在线数。
  写对接文档时凭直觉写成前者，被静态扫描抓出来了（见 `09` 的更正）。

## 4. 状态机：唯一事实来源 + 审计同源

**应用场景**：工单（待指派→已指派→处理中→已完成/已关闭）与合同（待生效→生效中→已到期/已终止）
的生命周期，必须"只有一条边能到达某个状态"，否则后人无从判断该走哪条。

**实现方式**
- 转移表 `transitions[from][action] = to`，`Next(from, action)` 是**唯一的合法性判据**；
  所有写入路径都过它，不存在"绕过状态机直接 UPDATE status"。
- 状态流转与**审计流水在同一事务**里写，且初始状态也取自状态机（不与审计里的 `ToStatus` 各写一份）。
- 建单被建模成一条**真实转移**：`0 --create--> 初始状态`（`0` = 「不存在」，也是审计 `FromStatus` 的起点）。

**证据**
- `state.IsValid` 在生产代码里**零调用** → 已从生产包挪进 `fsm_test.go`（生产少一个"看着有校验"的幽灵 API）。
- `IsTerminal` 保留（leasing 生产在用，且三个服务的 `state` 包都有它，属仓库既有约定）。

**踩过的坑**
- ⭐ **靠失败路径拿到"正确的值"是定时炸弹**：建单逻辑原先写

  ```go
  from, _ := state.Next(0, state.ActionCreate)   // 那条边当时不存在
  ```

  被吞掉的正是 `ok=false`，`from` 拿到零值 0 —— **歪打正着**把审计写对了。
  一旦表里补上这条边，`from` 会变成「待生效」写进 `FromStatus`，**语义当场反转**。已改成显式取值。

## 5. 幂等：唯一键 + 分布式锁 + 乐观锁，**每层管的不是同一件事**

**应用场景**：告警重投、消费者多实例、人工重复点击 —— 任何一种都不该产生重复工单或重复流转。

**实现方式（三层，各管一段）**

| 层 | 手段 | 防的是什么 |
|---|---|---|
| 业务幂等 | `uk_alarm_id` 唯一键 + 撞键即"幂等跳过" | 同一条告警被重投/多实例消费 |
| 技术重试 | `uk_task_no` 撞键 → **换号重试** | 单号生成撞号（跨实例/超量） |
| 并发控制 | `version` 乐观锁（`WHERE id=? AND version=?`） | 两个请求同时改同一张工单 |

**证据**：`TestTaskStatus_OptimisticLockPreventsDoubleTransition`（乐观锁）；
`TestReassignLockTTL`（锁 TTL 推导）；演示 seed 连建 5 张单由全挂转为全过。

**踩过的坑**
- ⭐⭐ **同一个 `1062 Duplicate entry` 对不同唯一键的处置是相反的** ——
  `uk_alarm_id` 冲突该跳过，`uk_task_no` 冲突该**换号重试**；
  一律按"已存在"处理，就会把"**没建成单**"当成"**早就建过**"，**真实告警被静默丢弃**（消息位移已提交，不会重投）。
  这个 Bug 是演示 seed 脚本连建 5 张工单挂了 1 张才暴露的（详见第 6 条）。

## 6. 单号生成：从"概率撞号"到"确定性不撞"

**应用场景**：高并发建单（告警爆发时同秒可能建几十张）。

**实现方式**：`DT` + 秒级时间戳 + **进程内原子计数器**（随机起点给多实例错开）；
跨实例/超量仍可能撞 → 两条建单路径都做**换号重试**。

**证据**（旧实现 vs 新实现）

| 同秒建单数 | 5 | 10 | 50 |
|---|---|---|---|
| 旧：`rand.Intn(1000)` 撞号概率 | ~1% | ~4.4% | **~71%** |
| 新：原子计数器（≤1000/秒/进程） | 0 | 0 | 0 |

**踩过的坑**
- ⭐ 这类"概率性唯一"的隐患在于**它平时不发作**：单张建单永远正常，只有批量/爆发时才现形，
  而且失败形态是"某一张单没建成"（很容易被当成偶发）。
- 回归测试用「同秒 900 次生成零重复」把旧实现钉住（旧实现必挂、新实现必过）。

## 7. 分布式锁：**TTL 必须与业务周期联动**

**应用场景**：重派定时任务多实例部署，同一时刻只能一个实例扫。

**实现方式**
- `SetNX` 抢锁 + **Lua 比对 token 再删**（直接 `DEL` 会删掉别人刚抢到的锁）。
- TTL **由扫描周期推导**：`ReassignLockTTL(intervalSec) = 周期 − 10s`，且不小于周期一半。

**证据**：`lockttl_test.go` 表驱动（60→50s 行为不变、300→290s、极短周期有下界）+ 不变量断言
「任何周期下 **0 < TTL < 周期**」。

**踩过的坑**
- ⭐ **硬编码 TTL 与可配置周期脱钩**：原先是 `50s` 写死，只对默认 60s 周期成立；
  一旦有人把周期调成 300s，锁 50s 就过期而扫描窗口有 300s → **另一实例并发进来扫同一批**
  （同一张工单可能被派给两个人）。这类"配置能改、常量不跟"的组合是最容易漏的。
- ⭐ **别凭印象记机制**：长期记忆里写着"这个锁加完不自解、靠 TTL 过期"，
  而代码里其实有 `defer` + Lua **会主动释放** —— TTL 只是**崩溃兜底**
  （进程被杀 / 释放时 ctx 已取消导致 Lua 删除静默失败）。
  差点按错误前提去改一个本来就对的实现。**用之前回代码确认。**

## 8. Kafka 消费：坏消息必须"记录后跳过"

**应用场景**：告警事件 → 自动建单。

**实现方式**
- **解码失败不返回 error**（否则位移不提交，整个分区被这一条卡死）：记日志后跳过。
- 落库走第 5 条的幂等三层。
- 消费者**默认关闭**（`Kafka.Enabled: false`）——这是**刻意的**：共享 broker 上误开消费者会自动建出真实工单。

**证据**：`internal/consumer/handler.go`；`internal/consumer/runner.go`（未启用或 brokers 为空即返回 nil）；
`docs/m5/07-Kafka端到端验证报告.md`（本地 broker 端到端验证）。

**踩过的坑**
- "默认关闭"很容易被读成"功能没做"（缺口清单里就这么写过）→ 在文档里写明**它是设计而非缺失**，并写清开启前提。

## 9. 用**影子表**验证执行计划

**应用场景**：判断列表/扫描 SQL 是否真的用上了设计好的索引——**只在代码里看到 `Where(...)` 不算数**。

**实现方式**：`CREATE TABLE <真表>__x<随机> LIKE <真表>`（完整复制列与索引）→ 灌 5000 行 →
`ANALYZE TABLE` → `EXPLAIN` 10 条真实查询 → 跑完 `DROP`。

- **不往真表灌**：库里是演示数据，灌几千条会改掉列表展示内容；而 EXPLAIN 只关心**数据分布**。
- **必须造数据**：几十行的表上优化器必然全表扫描，小表 EXPLAIN 的结论**没有意义**。
- 关键列按行号做**低基数分布**（`status = n%5+1`），否则"全表同值"会让计划失真。

**证据**：10/10 条查询全部走索引；两条待改进（重派扫描缺 `assign_expire_at` 索引、`lease_bill` 缺 `tenant_id` 索引）。

**踩过的坑（造数六个，全写进代码注释）**
1. `RAND()` 在 `INSERT ... SELECT` 里**不保证逐行求值** → 自我复制翻倍必撞唯一键 → 改用 **Go 侧行号**。
2. 唯一列拼后缀**必须按列长度截断**，否则 `Data truncated for column`。
3. **数值型唯一列不能拼字符串**：`'1-000001'` 被隐式转成 `1`（截断），唯一性当场失效。
4. `bigint` **不以 `int` 开头** → 判数字类型用 `HasPrefix` 会漏判（改用 `Contains`）。
5. **复合唯一键的首列 `COLUMN_KEY` 只报 `MUL` 不报 `UNI`** → 必须查 `information_schema.statistics`。
6. `time.Time` 直接 `%v` 会带 `+0800 CST` → MySQL 拒收；`nil` 必须保持 `nil`。

## 10. 性能数据的**口径陷阱**

**应用场景**：答辩必然被问"性能怎么样"，而性能数字**最容易被误读**。

**三条必须写进报告的限制**
1. **压测工具的失败要先归类**：1000 并发时报的 `bind: ... lacked sufficient buffer space` 是
   **压测端本机端口/缓冲区耗尽**，随后的"连接被拒"是级联 —— **不是服务端问题**。
   只报"失败 41386 次"等于把锅甩给被测服务。
   → 表里的 QPS 是**下限，不是服务上限**。
2. **缓存的收益必须在"接近真实上游延迟"下测**（见第 2 条）。
3. **穿透路径 ≠ 命中路径**：命中 p50 105ms，而穿透 500 并发 p50 605ms、**33.9% 超 800ms 预算**。
   两个数都要给，只给一个都是误导。

**踩过的坑**
- 压测工具第一版**只数失败次数、不吐原因** → 第二轮补上归类才定位到是压测端的问题。
  这与业务代码里"错误信息要能定位"是同一条道理。
