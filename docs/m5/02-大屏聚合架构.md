# M5 大屏聚合架构（dashboard-service）

> 对应组长一周计划书：**周四 P0**「Overview 聚合 + 4 路 gRPC 并发 + Provider + 降级策略」
> 与「WebSocket 实时推送 + 5 秒快照 + 事件增量」。

## 1. 整体结构

```
                   ┌──────────── GET /api/dashboard/overview ────────────┐
   浏览器/大屏 ────►│  ① 读缓存(30s, 租户维度) ──命中──► 直接返回 cached=true │
                   │  ② 未命中 → 并发聚合四路 → 写缓存 → 返回              │
                   └──────────────────────────────────────────────────────┘
                   ┌──────────── WS /ws/dashboard ────────────────────────┐
   浏览器/大屏 ────►│  周期快照: 每 5s 全量 Overview 快照(前端数据基线)     │
                   │  事件增量: Kafka 告警/工单事件 → 立即广播增量消息       │
                   │            + 置脏 → 快照循环失效缓存后重新聚合          │
                   └──────────────────────────────────────────────────────┘
```

## 2. 四路并发聚合

```go
ctx, cancel := context.WithTimeout(l.ctx, overviewTimeout) // 整体预算 800ms
var g errgroup.Group
g.Go(func() error {
    sctx, c := context.WithTimeout(ctx, sourceTimeout)      // 单源预算 600ms
    defer c()
    stat, err := l.svcCtx.Providers.WorkOrder.Stat(sctx, tenantId)
    if err != nil {
        markDegraded(sourceWorkOrder)
        return nil                                          // ← 关键: 不向上抛
    }
    ...
})
```

### 为什么用 `errgroup.Group` 而不是 `errgroup.WithContext`

`WithContext` 在任一路返回 error 时会 **cancel 兄弟任务**，把「部分降级」变成「整体失败」。这里的诉求恰恰相反：**一路挂了，其余三路必须照常返回**。所以：

1. 用不带 cancel 的 `errgroup.Group`；
2. 每路 goroutine **内部吸收错误并 `return nil`**，只把该源记入 `degraded`；
3. 外层 `ctx` 只承担「整体超时」职责。

### 时间预算为什么要两层

- **单源 600ms**：防某个慢源拖垮整体（M4 的 TDengine 聚合查询是候选慢源）；
- **整体 800ms**：给大屏一个可承诺的响应上限。

> 实测：桩源阻塞 5s 时，`TestOverview_SlowSourceTimeout` 整体耗时 **0.60s** 返回，而不是干等 5s。

## 3. 逐源降级

| 情况 | 返回 |
|---|---|
| 某路成功 | 对应卡片对象，`available: true` |
| 某路失败/超时 | 该卡片字段 **`null`**，并在 `degraded` 数组里列出源名 |
| 全部失败 | 全部 `null` + `degraded` 四项，接口**仍是 HTTP 200** |

**为什么失败返回 `null` 而不是「上次缓存的旧值」**（组长验收口径）：返回旧值会让大屏把过期数据当实时数据显示，运维看大屏时无法分辨「数据是旧的」还是「数据是对的」。显式 `null` + `degraded` 至少让前端能标出「此卡片当前不可用」。

**依赖倒置的价值**：四个数据源都定义成 `provider` 包的接口（`WorkOrderProvider` / `AlarmProvider` / `DeviceProvider` / `EnergyProvider`）。因此 M1~M4 不在线时也能用测试桩验证**聚合 / 降级 / 缓存全部路径**（见 `overview_test.go`）。

## 4. 缓存与「事件驱动穿透」

| 项 | 取值 | 理由 |
|---|---|---|
| TTL | **30s** | 组长确认口径（计划书写 5s，以组长口径为准） |
| 维度 | 租户：`m5:dashboard:overview:tenant:{id}` | 多园区共用一个进程，不隔离会串数据 |
| 失效方式 | `SCAN` + `DEL` 匹配 `m5:dashboard:overview:tenant:*` | **`KEYS` 会阻塞 Redis 单线程**，key 一多就是生产事故 |
| 触发时机 | 收到 Kafka 事件后，由快照循环统一失效 | 见下 |

### 为什么必须在事件到达时失效缓存

只推送事件、不管缓存的话，**下一次快照（5s 后）仍会读到旧聚合值**，事件的效果会被 30s 缓存整整盖住 —— 那「事件驱动」就白做了。

### 为什么失效动作放在快照循环里，而不是事件回调里

```
事件到达 ──► Dirty.Mark()          // 纯内存写一个 bool, 极轻量
                │
每 5s 快照循环 ──┴─► if Dirty.Take() { 失效缓存; 重新聚合 }
```

1. **天然节流**：告警风暴时每 5s 最多失效一次，不会每个事件都去 `SCAN` Redis；
2. **不丢效果**：若在回调里做「节流失效」（如 1s 内只失效一次），节流窗口内的事件可能被随后的聚合写成旧值；而脏标记在被取走前一直保留，**最后一条事件的影响必然体现在下一次聚合里**。

> 顺带一个细节：**无论有没有大屏在线都要置脏**。HTTP 的 `/overview` 接口同样吃这份缓存 —— 若「没人看就不失效」，接口会一直返回旧值。

## 5. WebSocket 推送：双通道

| 通道 | 频率 | 作用 |
|---|---|---|
| **周期快照** | 5s | 全量四卡片；前端数据基线，断线重连后靠它恢复 |
| **事件增量** | 事件到达即推 | `{type:"event", source:"alarm"|"workorder", topic, received_at, data}` |

**只有快照**会慢半拍；**只有事件**则前端拿不到全量卡片、重连后没有基线。两者互补。

事件消息里的 `data` **直接透传 Kafka 原始消息体**，本服务不解析：事件 schema 归生产方（M2/M3）所有，在这里再定义一份就等于把同一份契约写两遍，上游改字段时这边会静默失配。前端按 `source` 自行分发即可。

## 6. Hub 的并发安全（容易踩的坑）

`gorilla/websocket` **不支持并发写**，两个 goroutine 同时调 `WriteMessage` 会 panic。因此：

```
每连接 = 1 个独立 writer goroutine + 1 个带缓冲发送通道
Broadcast ──► 向各 client 的通道投递(读锁) ──► 各自 writer 串行写出
```

- `Unregister` 在**写锁内同时**「移出注册表 + 关闭通道」，与广播的读锁互斥 → 杜绝 `send on closed channel`；
- 缓冲打满（客户端卡死）时**异步踢掉该连接**，不阻塞、不 panic 其它客户端。

## 7. 数据源适配中的三个「不显眼但会错」的点

| 点 | 处理 | 不这么做会怎样 |
|---|---|---|
| **M3 告警等级** | 1 提示 / 2 一般 / 3 严重 / 4 紧急 → `Info/Minor/Major/Critical` 四个分项 | 只映射 3 级会漏掉「提示」类告警，导致 **四个分项之和不等于 total**，前端做校验就对不上 |
| **M4 能耗缺指标** | 契约只提供电耗 → `TotalWater` 用 **`*float64` 返回 `null`** | 用 `0` 冒充会显示「今日用水 0 吨」，把「没有该指标」说成「确实没用水」 |
| **M1 设备统计无类型分组** | 不臆造分类字段 | 编造分组会让大屏显示假数据 |

`AlarmProvider.Stat(ctx, tenantId)` 特意带 `tenantId`：漏传会把别的园区的告警显示到本园区大屏上。
