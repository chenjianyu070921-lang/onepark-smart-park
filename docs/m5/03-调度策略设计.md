# M5 调度策略设计（dispatch-service）

> 对应组长一周计划书：**周二 P0**「Kafka 消费 alarm-event + 自动建单 + 就近指派 + 幂等控制」、
> **周三 P0**「5 态 FSM + 状态流转 + 操作日志 + 乐观锁」。

## 1. 工单生命周期（5 态 FSM）

```
待指派(1) ──assign──► 已指派(2) ──start──► 处理中(3) ──finish──► 已完成(4)
    │                    │  ▲                                        │
    │                    │  └──assign(改派/超时重派)                  │
    │                    │                                           │
    │                 release(释放回池)                              │
    │                    ▼                                           │
    │◄───────────────────┘                                           │
    │                                                                │
    └────────────────────close────────────────────────────────────► 已关闭(5)
```

| 动作 | 转移 | 说明 |
|---|---|---|
| `create` | → 待指派 | 人工建单 / 告警自动建单 |
| `assign` | 待指派/已指派 → 已指派 | 含改派与**超时自动重派** |
| **`release`** | **已指派 → 待指派** | 超时且无人可接管 / 重派达上限 → 放回池交人工 |
| `start` | 已指派 → 处理中 | 处理人接单（**接单后不再被重派抢走**） |
| `finish` | 处理中 → 已完成 | |
| `close` | 任意非终态 → 已关闭 | 已完成为终态（仅可归档 close） |

**为什么需要 `release`**：若超时工单只能留在「已指派」，它会**永久卡住**且不出现在任何待办列表里 —— 这是数据正确性问题，不只是「少个功能」。

**审计与状态更新刻意不同事务**：状态变更是主流程，审计写失败只记日志不回滚 ——「改了但没留痕」比「留了痕但没改」危害小得多，也不会让整个定时任务失败。

## 2. 智能派单打分模型

```
score = 10000 × 技能匹配 + 100 × (3 − 拓扑距离) + (99 − min(负载, 99))
```

### 为什么权重是 `10000 / 100 / 99`

三者量级拉得足够开，保证**严格字典序：技能 > 距离 > 负载**：

- 技能项 10000 ≫ 距离项最大 300 → **有技能的一定赢过没技能的**（哪怕跨楼栋）；
- 距离项 100 ≫ 负载项最大 99 → **同技能时先看远近**，负载永远翻不过距离一档。

「就近指派」用 `zone_code` 前缀拓扑距离（`A-3F-301` → `A-3F` → `A` 逐段比对），不用经纬度 —— 园区是室内场景，同一栋楼里经纬度区分不出楼层。

### 两个兜底（保证不把工单卡死）

| 情况 | 行为 |
|---|---|
| 无人匹配所需技能 | **退化**为「就近 + 负载」，照常派人，而不是「无人可派」 |
| 工单未指定技能 | 技能项对所有人相同，自动退化为就近 + 负载 |

### 候选池双轨

优先 `dispatch_staff`（带技能标签、`on_duty=1` 硬过滤）→ 池为空时回退历史指派记录（无技能）。

> 为什么自持人员池：截至交付，`proto/user` / `proto/auth` 仍是 `rpc Ping` 骨架，团队没有人员主数据接口，而「技能标签」是明确要求。待 M6 提供后改为「同步 + 本地缓存」，**打分算法无需改动**。

### 决策必须可解释

`assign.Explain()` 返回打分明细并写入日志，排查时能回答「为什么派给了他」：

```
[dispatch] 自动指派: taskId=15, pool=staff, requiredSkill="fire" -> assignee=2002(Li-Far-Fire),
           技能命中=true, 距离=3, 负载=0, 得分=10099, 候选数=2
```

## 3. 指派超时重派

工单被指派后若在 **5 分钟**（`model.AssignExpireWindow`）内无人接单，由 cron 改派他人。

### 三层兜底：保证工单最终一定有人管

```
1. 未达重派上限且有人可派 → 改派给「排除原处理人」后的最优人选
2. 没有人可派             → 释放回「待指派」，交人工
3. 重派次数已达上限(3)    → 释放回「待指派」，交人工
```

**为什么上限必须有**：园区可能「全员不在岗」或技能池为空，无上限会每轮重试同几张单 —— 既刷爆日志，又掩盖了「真的没人可派」这个事实。

**为什么只处理 `status=已指派`**：`处理中` 说明人已经接单，重派等于把人正在干的活抢走。

### 四个不显眼但会出事的细节

| 细节 | 不这么做的后果 |
|---|---|
| **重派必须排除原处理人** | 会原样再派给刚超时的那位 → **每轮重派同一个人的死循环** |
| **本轮已派出的负载要累加回内存** | 一批积压工单会拿同一份陈旧负载**反复选中同一个人**，负载均衡当场失效 |
| **重派后重置超时窗口** | 新处理人同样需要一个接单时限 |
| **人工指派时 `reassign_count` 归零** | 否则「自动重派 3 次 → 释放 → 人工再指派 → 又超时」会**立刻被再次释放**，人刚指派的对象连一个接单窗口都拿不到 |

> 最后一条是在端到端验证中才发现的：释放后计数仍是 3，人工重新指派后一旦超时就立即被释放，不走任何重派。

### 并发防护三层（锁会丢，不能只靠锁）

1. Redis `SET NX` 锁 + **Lua 比对持有者释放**（直接 `DEL` 会删掉别人刚抢到的锁）
2. 更新条件带 `status AND version` —— **数据库层兜底**，锁失效也不会重复改派
3. 审计流水仅在 `RowsAffected > 0` 时写 —— 一张单一次改派只留一条流水

## 4. 告警自动建单（消费 `alarm-event`）

| 点 | 做法 | 理由 |
|---|---|---|
| **幂等** | `alarm_id = request_id`，靠 `uk_alarm_id` **唯一索引** | 数据库层保证；应用层「先查后插」有并发竞态 |
| **优先级映射** | fire/smoke → 紧急；intrusion/door_force → 高；fault/offline_alert → 普通 | 与 `dispatch_task.priority` 取值一致 |
| **未知告警类型** | **不丢弃**，按普通优先级建单 | 丢弃会漏掉真实告警，宁可多派一次 |
| **拿不到 `zone_code`** | `payload.zone_code` → `payload.location` → **留空** | **绝不臆造区域** —— 就近指派靠真实区域编码，编造会把保安派到错的地方；留空则落到「待指派」交人工 |
| **坏消息** | 记日志后**返回 `nil`** | 返回 error 则位移不提交，**一条毒消息会把整个分区永久卡死** |
