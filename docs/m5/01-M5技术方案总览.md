# M5 技术方案总览（运营招商 + 指挥调度）

> 模块负责人：乔宇翔（`qyx-module5`）｜ 最后更新：2026-09-17

## 1. 模块定位

M5 是团队的**上游聚合方 + 事件消费方**，本身不产生物联数据：

| 定位 | 说明 |
|---|---|
| 大屏聚合方 | 并发调用 M1/M2/M3/M4 的 gRPC，聚合成园区总览；单路失败只降级该卡片 |
| 事件消费方 | 消费 Kafka 告警/工单事件，驱动「自动建单」与大屏增量推送 |
| 业务自持方 | 招商租赁（合同/账单/入驻率）与指挥调度（工单/派单）的业务数据由 M5 自己的库承载 |
| gRPC 提供方 | `leasing-service` 对外提供 `GetContract` / `GetOccupancy`（见 §5） |

## 2. 三个服务

| 服务 | 目录 | HTTP | gRPC | 职责 |
|---|---|---|---|---|
| 招商租赁 | `app/leasing-service` | `8051`（`/api/lease`） | `9051` | 合同 FSM、入驻率、租金账单、到期提醒与自动续约 |
| 指挥大屏 | `app/dashboard-service` | `8052`（`/api/dashboard`） | — | 四路 gRPC 聚合、逐源降级、缓存、WebSocket 推送 |
| 指挥调度 | `app/dispatch-service` | `8053`（`/api`） | — | 调度工单 FSM、智能派单、超时重派、告警自动建单 |

> 端口取自《接口清单》口径。**README 的端口表已不可信**（M1 实际 8001、M2 实际 8091，其余多数仍是默认 8888）。

## 3. 依赖关系

```
        ┌─────────────── M5 dashboard-service ───────────────┐
        │  GetDeviceStat  GetWorkOrders  GetActiveAlarms     │
        │  GetDailyReport                                    │
        ▼        ▼             ▼              ▼              │
      M1 设备   M2 物业      M3 安防       M4 能源            │
   (9001 gRPC)(9091 gRPC)(9009 gRPC)  (9061 gRPC)            │
                                                             │
   Kafka alarm-event / workorder-event ──► dashboard(增量推送) │
   Kafka alarm-event ───────────────────► dispatch(自动建单)  │
        └────────────────────────────────────────────────────┘
```

**硬约束**：服务间一律走 gRPC，**禁止 HTTP 互调**（`docs/服务协议规范-HTTP与gRPC.md`）。因此大屏的四路数据源全部是 gRPC Client，`Endpoints` 直连（go-zero v1.10.3 的 zrpc 不支持 Nacos）。

## 4. 启动与部署

### 4.1 本地开发

```powershell
# 中间件（MySQL 3306 / Redis 6380；宿主机 6379 被原生 redis 占用，故用 6380）
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d mysql redis

# 建表（全量，幂等）
docker cp deploy/sql/m5_mysql_tables.sql onepark-mysql:/tmp/m5.sql
docker exec onepark-mysql sh -c "mysql -uroot -p<密码> < /tmp/m5.sql"

# 已建过库的环境补列（非幂等，仅需执行一次）
docker cp deploy/sql/m5_mysql_migrations.sql onepark-mysql:/tmp/m5m.sql
docker exec onepark-mysql sh -c "mysql --force -uroot -p<密码> < /tmp/m5m.sql"

# 启动（各服务一个进程）
go run .\app\leasing-service\leasing.go        -f .\app\leasing-service\etc\leasing-api.yaml
go run .\app\leasing-service\grpcserver         -f .\app\leasing-service\etc\leasing-grpc.yaml
go run .\app\dashboard-service\dashboard.go    -f .\app\dashboard-service\etc\dashboard-api.yaml
go run .\app\dispatch-service\dispatch.go      -f .\app\dispatch-service\etc\dispatch-api.yaml
```

### 4.2 配置要点

| 项 | 说明 |
|---|---|
| DB 索引 | `conf.UseEnv()` 可展开 `${VAR}`；本地 yaml 直接写数字字面量（DB 索引必须数字，写 `${REDIS_DB}` 会类型不匹配） |
| `Name` 字段 | gRPC 配置的 `Name` **必填**，缺失会报 `field "Name" is not set`（M1/M2 都踩过） |
| MySQL 库 | 每服务独立库，**禁止跨库 JOIN**：`leasing_db` / `dashboard_db` / `dispatch_db` |
| 共享 Kafka | 组长提供的 `115.191.16.159:9092`（PLAINTEXT、零认证、多项目共用）→ 消费者**默认关闭**，见 §6 |

### 4.3 MySQL 脚本约定（2026-09-17 起）

| 文件 | 内容 | 幂等 |
|---|---|---|
| `deploy/sql/m5_mysql_tables.sql` | **全量**建表，新列直接并入 `CREATE TABLE` | ✅ 可反复执行 |
| `deploy/sql/m5_mysql_migrations.sql` | **增量** `ALTER`，仅已建库的环境需要 | ❌ 非幂等，文件头已标注 + 给出 `--force` 用法 |

> ⚠️ `mysql < file.sql` **遇错即停**：多语句文件里若前段有已执行过的非幂等语句（如 `ALTER`），**后面的语句会被静默跳过**。所以增量改表请单独执行或只跑迁移文件。

## 5. 对外接口

### 5.1 gRPC（`proto/leasing/leasing.proto`，端口 9051）

| 方法 | 说明 |
|---|---|
| `Ping` | 探活（不依赖 DB） |
| `GetContract` | 按合同 ID 查合同主信息；带 `tenant_id` 时校验归属，跨租户返回 `NotFound` |
| `GetOccupancy` | 园区入驻率 = 已租面积 / 可租总面积 |

**契约口径**：金额（`monthly_rent` / `deposit`）用 **string** 承载 decimal —— protobuf 没有 decimal 类型，用 double 会重现项目内已明令禁止的「金额浮点精度丢失」；面积沿用 HTTP 契约的 `double`（它本就不是金额字段）。

> gRPC 层是**薄适配层**：直接复用 HTTP 的 logic（`ContractDetailLogic` / `OccupancyLogic`），不重写查询。否则同一份数据两套实现，返回值迟早不一致而调用方无从判断该信哪个。

## 6. ⚠️ 共享基础设施的默认关闭策略

本项目 Kafka 是**多项目共用的 broker**。M5 的两个消费者（dispatch 自动建单、dashboard 事件推送）均设为 **`Enabled: false` 默认关闭**，开启前必须确认：

```
☐ 0) 先经组长授权 —— 若 broker 开 auto.create.topics.enable, 消费不存在的 topic 会隐式建 topic
     (= 向共享基础设施写入)
☐ 1) 目标 topic 存在且属于 onepark 体系(共享 broker 上还有其它项目的 topic)
☐ 2) 消费组形如 m5-{service}-{env}-{owner}, 且与生产方(M2/M3)不重名
     —— Kafka 位移按 (group, topic) 提交, 重名会把它们该消费的消息吃掉
☐ 3) common/kafka.NewConsumer 固定 StartOffset=FirstOffset: 新消费组会从最早位移开始消费,
     broker 有积压时会一次性全处理
```

> 第 3 条是 `common/kafka` 的既有行为（非 M5 代码）。**建议 `common/kafka` 增加 `StartOffset` 参数**，供消费方按场景选择。

## 7. 验证口径

| 维度 | 口径 |
|---|---|
| 大屏降级 | 单路失败 → 该字段 `null` + `degraded` 列出，接口**整体始终 200**，绝不因单路失败抛 5xx |
| 大屏缓存 | 30s 租户维度（组长口径，非清单的 5s）；事件到达时主动失效，不靠 TTL 等 |
| 工单/合同状态 | 由 FSM 校验合法性，非法转移一律拒绝；并发用乐观锁 `version` |
| 幂等 | 告警自动建单靠 `uk_alarm_id` 唯一索引；账单靠 `uk_contract_period` 唯一索引 |
