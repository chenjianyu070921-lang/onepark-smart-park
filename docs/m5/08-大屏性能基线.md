## 一、聚合层净开销（benchmark，桩替代四路 gRPC）

```powershell
go test ./app/dashboard-service/internal/logic/dashboard/... -run '^$' -bench . -benchmem -benchtime 500x
```

| 基准 | ns/op | B/op | allocs/op | 说明 |
|---|---|---|---|---|
| `FourSourcesOK` | **7 924** | 2 687 | 44 | 四路全部正常 |
| `OneSourceDown` | 8 794 | 2 673 | 45 | 一路挂（+11%） |
| `AllSourcesDown` | 8 682 | 2 797 | 47 | 四路全挂（+10%，**仍正常返回**） |
| `Concurrent` | **543** | 305 | 4 | 32 路并发下每个 op |

**读法**：这是「并发编排 + 降级判定 + 缓存读写」这段代码的净开销，**不含**网络与上游耗时。
`AllSourcesDown` 与 `FourSourcesOK` 几乎持平，说明**降级处理本身不引入额外代价** ——
逐源降级不是"用性能换可用性"。

> ⚠️ 别把这些数字当成"接口响应时间"。接口的真实耗时见第三节。

## 二、缓存的真实收益（benchmark，含 Redis 往返）

```powershell
go test ./app/dashboard-service/internal/logic/dashboard/... -run '^$' -bench 'Cache'
```

| 基准 | ns/op | 场景 |
|---|---|---|
| `CacheHit` | 565 614 | 上游**零耗时桩** + 命中 |
| `CacheHitWithSlowUpstreams` | **602 789** | 上游各 5ms + 命中 |
| `CacheMissWithSlowUpstreams` | **6 783 281** | 上游各 5ms + 未命中 |
| `CacheMissThenAggregate` | 1 159 446 | 上游零耗时桩 + 未命中（只剩 Redis 两次往返） |

**两个结论**：

1. ⭐ **命中路径完全不随上游变慢**：565 µs → 603 µs（+7%），而未命中要 **6.78 ms** ——
   **缓存收益 = 11 倍**。而且上游越慢，收益越大（这正是缓存的意义）。
2. ⚠️ **反直觉的那个数字要小心解读**：拿"上游零耗时桩"比时，缓存命中（565 µs）
   反而**慢于**聚合本身（7.9 µs）。那不是"缓存是负优化"，而是**桩太快**：
   命中路径的成本是**一次 Redis 往返（≈0.5 ms）**，而零耗时桩的聚合不需要任何等待。
   真实上游是毫秒级网络调用，所以真实场景里缓存稳赚 —— 见上表第 2、3 行。

## 三、真实服务并发压测（对 `/api/dashboard/overview` 发真实 HTTP）

```powershell
# 起 dashboard（临时配置, 端口 18052; 四路上游未启动 -> 降级路径）
go run ./app/dashboard-service/tools/dashload `
  -url http://127.0.0.1:18052/api/dashboard/overview -c <并发> -d 10s -tenant 1
```

| 并发 | 路径 | QPS | p50 | p95 | p99 | max | 超 800ms |
|---|---|---|---|---|---|---|---|
| 100 | 缓存命中 | 4 426 | 22.4 ms | 24.9 ms | 26.4 ms | 103 ms | **0** |
| 500 | 缓存命中 | 4 752 | 96.0 ms | 103 ms | 189 ms | 3.68 s | 295（0.62%） |
| 1000 | 缓存命中 | 4 456 | 104.6 ms | 117 ms | 179 ms | 10.05 s | 312（0.70%） |
| 500 | **穿透**（每请求换租户） | 694 | **605 ms** | 1.11 s | 3.67 s | 4.84 s | **2 351（33.9%）** |

缓存命中率：命中路径 **100.0%**（39 539/39 539）；穿透路径 **0.0%**（构造如此）。

### 怎么读这张表

- ✅ **800ms 预算在命中路径守得住**：p99 ≤ 190 ms，稳态下 99.3% 的请求远在预算内。
- ⚠️ **但尾部有尖峰**：max 达 3.7~10 s（0.6~0.7% 的请求超预算）。
  均值/p50 都好看，**尾部才是演示现场"卡住"的来源** —— 建议后续用 pprof 定位（GC 还是连接抖动）。
- ⚠️ **吞吐在 ~4 500 QPS 就到平台**：100 → 1000 并发 QPS 几乎不变（4 426 → 4 456），
  而 p50 从 22 ms 涨到 105 ms —— 典型的**排队**特征：瓶颈不在并发数，而在某个共享资源
  （命中路径每请求一次 Redis GET，Redis 单线程 + 同机 CPU 竞争是最可能的候选）。
- 🔴 **穿透路径 33.9% 超预算**：缓存不可用（或全是不重复的租户）时，聚合层直接暴露在全部并发下。
  **这就是"缓存击穿防护"为什么必要** —— 而它已经实现了（见下节）。

## 四、缓存击穿防护：计划书判断已过时（已实现）

计划书 Day 4 加练 A 写「已核实：dashboard 没有用 singleflight」—— **该判断已过时**：

| 证据 | 位置 |
|---|---|
| 已使用 singleflight | `internal/logic/dashboard/overviewlogic.go`（`singleflight.Group`） |
| 专门的防击穿用例 | `internal/logic/dashboard/overview_stampede_test.go` |
| 实测 | `go test ... -run StampedeProtection -v` → **PASS (0.20s)** |

用例的核心断言：**桩阻塞 200 ms** 让并发都堵在门口，然后断言「上游只被调用 **1** 次」（而非 N 次）。
注释里写着这条为什么重要：没有它，「500 并发 = 2000 次上游调用」，缓存"减轻 gRPC 压力"的意义被抵消。

> 实现细节上的一个坑（代码里已处理）：`singleflight` 的返回值会被**所有并发调用方共享**，
> 因此 `Cached` / `ElapsedMs` 这类字段必须**拷贝一份再写**，否则数据竞争。

## 五、口径限制（引用上面的数字前必读）

| # | 限制 | 影响 |
|---|---|---|
| 1 | ⚠️ **压测程序与被压服务同机** | 1000 并发时**压测端**先耗尽本机端口/缓冲区：`bind: ... lacked sufficient buffer space or because a queue was full`，随后 41 384 次「连接被拒」是它的级联。**→ 表中的 QPS 是下限，不是服务上限**；p50/p99 取自成功请求，仍有效 |
| 2 | ⚠️ **被压的是降级路径** | M1~M4 未启动，四路快速失败。**"四路全绿 + 真实上游延迟"的端到端数据仍缺** |
| 3 | ⚠️ 单机回环 | 不含真实网络 RTT（内网通常 0.1~1 ms/跳） |

**要把数字做实，下一步**（按性价比）：

1. 压测端换到**另一台机器/容器**，或调大 Windows `MaxUserPort` 与 `TcpTimedWaitDelay`
2. 让 M1~M4 起来（或有桩服务）后重跑，补上"四路全绿"那一列
3. 用 `pprof` 定位第三节约 0.7% 的尾部尖峰

## 六、加练 B：WebSocket 推送压测

```powershell
go test ./app/dashboard-service/internal/wshub/... -run WSLoad -count=1 -v -timeout 300s
```

**为什么做成测试而不是外部压测工具**：这一层量的是「广播到 N 个在线连接」的成本，
与 HTTP、网关都无关；进程内起真实 WS 连接（`httptest` + 真升级）就能量准，
而且**可复跑、不依赖手工起服务** —— 外部工具换个环境就容易变成"跑不起来"，那还不如没有。

| 客户端 | 推送延迟 p50 | p95 | max | 收到帧 | 每连接堆占用 | 全断开后清理 |
|---|---|---|---|---|---|---|
| 50 | 1.51 ms | 1.81 ms | 2.32 ms | 250/250 ✅ | ≈21.6 KB | **2 ms** → 在线数归 0 |
| 200 | 3.02 ms | 3.13 ms | 4.27 ms | 1000/1000 ✅ | ≈21.5 KB | 19 ms → 归 0 |
| 500 | **6.50 ms** | 6.79 ms | 7.14 ms | 2500/2500 ✅ | ≈21.3 KB | 22 ms → 归 0 |

**四条结论**：

1. **推送延迟对客户端数近似线性**：50→200→500 为 1.5→3.0→6.5 ms（约 **13 µs/客户端**）。
   按此外推，5000 个在线客户端约 65 ms —— 相对 5 s 的推送周期，余量非常大。
2. **内存 ≈ 21.4 KB/连接**（含读/写泵两个 goroutine）→ 1 万客户端约 214 MB。这是容量估算的依据。
3. **零丢帧**：每连接发送缓冲只有 16 条（`sendBufferSize`），连续 5 轮广播仍全部收到。
4. ⭐ **慢客户端不拖累他人**：一个连上就不读的客户端在场时，20 个正常客户端仍 2 ms 内收齐 100/100 条 ——
   证明「每连接一个带缓冲 channel + 异步写泵」的设计确实隔离了慢连接（若广播同步写 socket，这里会全卡死）。

**连接泄漏检查（计划书要求的那一项）**：三种口径都验了 ——

| 检查 | 结果 |
|---|---|
| 500 客户端全部断开后 | 22 ms 内 `Count()==0`，堆回落 |
| 反复「连 100 → 全断开」3 轮 | 每轮在线数都回到 0（不是越攒越多） |
| 慢客户端被踢的场景 | 由既有 `TestBroadcast_StaleClientKicked` 覆盖 |

> ⚠️ 一处**未做**：服务端的 CPU 占用没取到 —— 需要真实起服务后读进程指标，
> 而当时本地服务类命令的审批通道超时。改用「推送延迟 + 堆增量」间接反映成本。

## 七、加练 C：列表与扫描查询的执行计划

```powershell
go run ./app/dispatch-service/tools/dbexplain `
  -dsn "root:***@tcp(127.0.0.1:3306)/dispatch_db" -rows 5000
```

**方法**：`CREATE TABLE <真实表>__x<随机> LIKE <真实表>` 造**影子表**（完整复制列与索引），
灌 5000 行后 `ANALYZE TABLE` 再 `EXPLAIN`，跑完即 `DROP`。

- 为什么**不往真表灌数据**：库里是答辩/演示用的真实数据，灌 5000 条会改掉列表展示内容；
  而 EXPLAIN 关心的只是**数据分布**，影子表量出的计划与真表等价。
- 为什么**必须造数据**：几十行的表上优化器必然全表扫描（反正全表，走索引更贵）——
  小表上的 EXPLAIN 结论**没有意义**。
- 每张影子表里 `status/priority/tenant_id/zone_code/日期` 等列按行号做了**低基数分布**，
  否则"全表同值"会让优化器选出失真计划。

| 查询 | 出处 | type | key | rows | 判读 |
|---|---|---|---|---|---|
| 工单列表·状态+优先级 | `tasklistlogic.go:52,55` | ref | **idx_status_priority** | 333 | ✅ 设计目标达成 |
| 工单列表·仅状态 | `tasklistlogic.go:52` | index | PRIMARY | 99 | ✅ 合理：`ORDER BY id DESC LIMIT 20` 下倒序扫主键更省 |
| 工单列表·园区+状态 | 索引设计目标 | ref | **idx_zone_status** | 250 | ✅ |
| **重派扫描·到期工单** | `cron/reassign.go:106` | ref | idx_status_priority | **1000** | ⚠️ **见下** |
| 乐观锁条件 | `cron/reassign.go:174,204` | const | PRIMARY | 1 | ✅ 最优 |
| 合同列表·状态 | `contractlistlogic.go:55` | index | PRIMARY | 99 | ✅ 同上（合理） |
| 即将到期合同 | `contractexpiringlogic.go:66` | ref | **idx_status_end_date** | 1000 | ✅ |
| 每日到期扫描 | `cron/daily.go:96,147` | **range** | **idx_status_end_date** | 1000 | ✅ `end_date < ?` 用上了范围扫描 |
| 账单列表·租户+状态 | `billlistlogic.go:62,67` | index | PRIMARY | 20 | ⚠️ 见下 |
| 账单列表·周期+状态 | `billlistlogic.go:59` | ref | **idx_period_status** | 84 | ✅ |

**结论：10/10 都走了索引**，设计的组合索引（`idx_status_priority` / `idx_zone_status` /
`idx_status_end_date` / `idx_period_status`）都被优化器选中。但有两处**值得记一笔**：

### ⚠️ 待改进 1：重派扫描在 `assign_expire_at` 上没有索引

```
SQL: SELECT * FROM dispatch_task
     WHERE status = 2 AND assign_expire_at IS NOT NULL AND assign_expire_at < NOW() LIMIT 100
计划: type=ref key=idx_status_priority rows=1000 Extra=Using where
```

它只能借 `status` 的前缀进索引，再**回表逐行过滤** `assign_expire_at` ——
5000 行里要扫 1000 行才凑够 100 条结果。**这条 SQL 由定时任务每轮都执行**，
工单量上量后成本随 `status=已指派` 的行数线性增长。

> 建议：加 `idx_status_expire(status, assign_expire_at)`。
> **本次未改**（表结构改动要走迁移流程、且当前数据量下不是瓶颈），只记录为结论。

### ⚠️ 待改进 2：`lease_bill` 没有 `tenant_id` 索引

```
SQL: SELECT * FROM lease_bill WHERE tenant_id = 1 AND status = 1 ORDER BY id DESC LIMIT 20
计划: type=index key=PRIMARY rows=20 Extra=Using where
```

`lease_bill` 现有索引是 `idx_period_status(billing_period,status)` 与 `uk_contract_period`，
**租户维度只能回表过滤**。当前 LIMIT 小（20）所以代价可接受，
但"按租户查全部账单 + 大偏移分页"会退化成扫全表。

> 建议：若账单需要按租户维度查（前端已这么查），补 `idx_tenant_status(tenant_id,status)`。
