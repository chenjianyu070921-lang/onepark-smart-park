## 二、阻塞项与根因

### B1. 宿主机 3306 / 6379 被既有容器占用（端口冲突）

```
Error response from daemon: ... Bind for 0.0.0.0:6379 failed: port is already allocated
```

占用者（**非本 compose 栈容器**，属其它环境，本次未触碰）：

| 容器 | 镜像 | 端口映射 |
| --- | --- | --- |
| `mysql80` | mysql:8.0 | `0.0.0.0:3306->3306` |
| `redis` | redis:latest | `0.0.0.0:6379->6379` |

影响：compose 默认 `${MYSQL_PORT}`/`${REDIS_PORT}` 无法绑定 → 栈无法正常拉起。
（`.env.example` 中 `REDIS_PORT=6379`；各 `*-api.yaml` 注释亦记录"宿主机 6379 被占用，容器用 6380"。）

### B2. MySQL 容器初始化失败（宿主资源受限，**非 SQL 脚本问题**）

证据 A（首次，卷内有残留）：
```
[ERROR] [MY-010457] [Server] --initialize specified but the data directory has files in it. Aborting.
[ERROR] [MY-013236] [Server] The designated data directory /var/lib/mysql/ is unusable.
```

证据 B（**彻底删除脏卷后仍复现**，排除脏卷因素）：
```
[Warning] [MY-010001] [Server] Can't create thread to handle bootstrap (errno: 1)
[ERROR]   [MY-010020] [Server] Data Dictionary initialization failed.
```
容器 `ExitCode=1`、`OOMKilled=false`、`RestartCount=11`。

资源证据：
- 容器内 `ulimit -u = unlimited`，`/proc/sys/kernel/threads-max = 62900`（WSL2 内核线程上限偏低）
- 宿主机：16 GB 总量，**仅 2.45 GB 空闲**

判定：mysqld 在 bootstrap（数据字典初始化）阶段创建线程失败 → 崩溃 → 重启后撞上残留文件 → 崩溃循环。
根因是 **WSL2/Docker Desktop 的内核线程上限 + 宿主内存压力**，与 `init.sql`/`sys.sql` 无关（两脚本已在独立容器中挂载，未执行到 SQL 阶段即崩溃）。

### B3. Kafka / EMQX / TDengine / Nacos 镜像拉取失败（registry 网络超时）

```
docker compose pull kafka emqx tdengine nacos
→ Error response from daemon: Get "https://registry-1.docker.io/v2/":
  net/http: request canceled ... (Client.Timeout exceeded while awaiting headers)
```
连续重试 2 次均失败。对照：小镜像 `redis:7-alpine` 可成功拉取 → **大层/多镜像并发时 registry 连接不稳定**。

## 六、2026-09-20 复查（dev-expert 收尾）

> 环境：本机 Docker 守护进程仍未运行（`docker ps` 连接失败），故 **live `healthy` 仍无法实跑**，与 09-18 的 B2/B3 阻塞一致。以下为静态核查结论。

### 1. 全量编译（P0）
- 遍历 22 个 `go.mod` 模块逐一 `go build ./...`，**全部通过，0 失败**（含本次 parking-service 重构）。无回退。

### 2. .env.example ↔ 各服务 yaml 对齐（P0，含 tokenblk）
- 脚本提取所有服务 `etc/*.yaml` 的 `${VAR}` 并与 `.env.example` 比对：**全部已定义**（`ALL_YAML_VARS_DEFINED_IN_ENVEXAMPLE`）。
- `docker compose config -q`（以 `.env.example` 为 env-file）返回 0 ⇒ compose 层变量亦完整。
- tokenblk 相关：`REDIS_ADDR/REDIS_PASS`（网关）、`AUTH_REDIS_ADDR/PASS`（auth-service）均已对齐且注入 compose。

### 3. init.sql 建表状态（P0，**发现部署就绪致命缺口 + 架构矛盾**）
- **现状**：`init.sql` 仅 `CREATE DATABASE × 20`，**不含任何建表语句**（09-18 记录已载，仍未修）。
- compose 的 mysql 仅挂载 `init.sql` + `sys.sql` 到 `initdb.d` ⇒ **模块建表脚本与迁移脚本均未自动执行** → 全新 `up` 后业务表（work_order/parking_record/alarm/...）全部缺失，服务首访即 `Table doesn't exist`。
- **架构矛盾（修复前必须先定夺）**：`deploy/sql/m2_mysql_tables.sql` 第 12–13 行明确写道"目标库：当前部署为单一共享库 `onepark-smart-park`，脚本内不含 CREATE DATABASE / USE"。但：
  - `init.sql` 建的是**每服务独立库**（`workorder_db`/`parking_db`/`notice_db`/...），且**根本没建 `onepark-smart-park`**；
  - 各服务 DSN（如 `PARKING_MYSQL_DSN→parking_db`）也连独立库。
  - 三者自相矛盾：即便把 M2 SQL 挂上，表也会落到错误/不存在的库。m3/m5/billing 的建表脚本则各自 `USE` 独立库（如 `alarm_db`/`leasing_db`/`billing_db`），与"每服务独立库"模型一致；仅 **M2 是"共享库"异类**。
- **其他约束**：
  - `m1_tdengine_tables.sql` 是 **TDengine** SQL，绝不能进 MySQL `initdb.d`（会直接报错）。
  - 迁移脚本 `m1_device_add_*` / `m5_mysql_migrations` / `l2_tenant_id_migration` / `rbac_data_scope` 注释均声明"全新环境无需执行 / 重复执行会报错"，**不可自动跑**，仅用于存量库。
- **修复方向（待用户确认数据库模型后再实施）**：
  - 方案 A（推荐，贴合 m3/m5/billing 现状）：统一"每服务独立库"。把 `m2_mysql_tables.sql` 拆为按域 `USE workorder_db/parking_db/notice_db/visitor_db/billing_db`，或改为按服务分文件；并确保 `init.sql` 已建这些库（已建）。
  - 方案 B（贴合 M2 注释原文）：统一"共享 `onepark-smart-park` 库"。改各服务 DSN 指向 `onepark-smart-park`，并在 `init.sql` 补建该库；m3/m5/billing 的 `USE` 独立库需同步改。
  - 无论哪种：把 `init.sql` 改为**编排器**（建全库 + 按序 `SOURCE` 仅"建表脚本"，排除 TDengine 与迁移脚本），并把 `./sql` 以只读挂载供 `SOURCE` 引用。
