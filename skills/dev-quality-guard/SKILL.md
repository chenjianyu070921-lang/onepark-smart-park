# 项目开发质量约束（dev-quality-guard）

## 目的

面向 Go 微服务实训项目（go-zero / Kratos 技术栈），约束从需求到交付的全过程：所有代码产出必须架构合规、可讲解、可测试、可部署。任何"直接让 AI 生成代码再粘贴进项目"的做法都被本流程拦截。

## 硬性工作流（四阶段，禁止跳过任何阶段）

### 阶段一：需求梳理（写任何代码之前必须完成）

1. 以头脑风暴方式与开发者澄清：业务目标、模块边界、上下游依赖、数据流向。
2. 明确回答：这个模块解决什么问题？成功标准是什么？不做什么？
3. 将结论写入 `docs/specs/<模块名>.md`（需求规格），经确认后才可进入阶段二。

### 阶段二：规格化输出（规格未确认，禁止生成业务代码）

1. 接口契约：method + path + 请求/响应字段 + 错误码表。
2. 数据设计：表结构、索引依据、迁移脚本。
3. 依赖清单：Redis / Kafka / etcd / 第三方服务，以及各自的降级方案。
4. 验收标准：可测试的功能点清单 + 性能要求。

### 阶段三：约束编码

1. 先读取 `references/conventions.md`，逐条对照执行（分层、命名、错误码、安全红线、缓存与并发五问、测试规约）。
2. 每完成一个功能点立即补对应测试，禁止"先堆代码后补测试"。
3. 使用 AI 辅助时遵守下方「AI 生成代码三道关」。

### 阶段四：质量自检（交付前必须全部通过）

1. 逐项执行 `references/checklist.md` 的全部检查项。
2. 输出《变更说明》：改了什么 / 为什么 / AI 参与了哪些部分 / 如何验证。
3. 任一项不通过：修复后重新自检，禁止带病交付。

## AI 生成代码四道关

1. **需求先行**：未完成阶段一、二，禁止让 AI 直接生成业务代码。先有规格，再谈实现。
2. **可讲解性**：AI 生成的每段代码必须能回答"为什么这样写、边界条件在哪"。讲不清视为未完成，必须重写或学习至能讲清为止。
3. **入仓评审**：提交前按清单自查边界条件、并发安全、命名规范；先改再提，禁止把明显问题留给 review 发现。
4. **出口闸门**：拦截范围内（并发/事务一致性/鉴权安全/缓存/消息队列/核心 SQL/状态机/跨服务调用）的代码产出，以及测试、优化阶段的代码产出，写入项目前必须通过 **code-explain-gate** 理解闸门（答题通过 + 生成讲解卡）。无论代码经由哪个技能流程或何种方式产生，出口唯一；无闸门讲解卡的拦截范围改动视为未验证交付。

## 完成定义（Definition of Done）

- `go build ./...`、`go vet ./...`、`go test ./...` 全部通过且零警告。
- 新增模块包含 ≥10 个带断言的单元测试（表驱动优先）。
- 核心接口有 P50/P99 压测数据记录（工具、并发数、错误率齐全）。
- 接口文档与 README 同步更新，可一键运行/部署。

## 禁止行为（红线，触犯即打回）

- 跳过需求与规格，直接生成业务代码。
- 提交自己讲不清的代码（含 AI 生成代码）。
- user_id 等身份字段取自前端参数（必须取登录态 Claims）。
- 硬编码数据库连接串、密码、密钥（必须配置文件或环境变量注入）。
- 吞错误：err 不处理、空 catch、魔法字符串比对错误。
- 无索引字段全表扫描、循环内单条查询。
- 修改他人服务接口却不更新契约文档。

## 参考文件

- `references/checklist.md` —— 提交前自检清单（DoD）与《变更说明》模板。
