# 面试亮点讲解生成器（interview-highlight）

## 目的

把学生项目里"做过但讲不清"的模块，变成面试时能脱稿讲清、被追问也接得住的亮点。产出两部分：①可背诵的第一人称讲解稿；②预测追问与参考答案。所有内容基于当前项目真实代码生成，确保学生拿到文案后能"顺着学懂"，面试时不至于被一个问题打穿。

## 工作流（四步，顺序执行）

### 第一步：定位并通读模块代码

1. 与用户确认目标模块（例："订单服务的分布式锁防并发"、"商品热点缓存"、"GEO 派单引擎"）。
2. 通读该模块的真实代码、接口契约、测试与配置，提取：
   - 功能定位与业务场景；
   - 关键机制、技术选型、关键参数与阈值（锁时长、TTL、限流阈值、重试间隔等）；
   - 已有的测试与压测情况。
3. **以真实代码为依据**：机制、参数、设计细节必须来自代码；允许拔高的只有成果量级（见红线）。若模块代码过于简单撑不起亮点，先如实告知用户，并基于真实机制找"可以讲的角度"，不得虚构不存在的架构。

### 第二步：生成《亮点讲解稿》（第一人称、口语化、可背诵）

按以下结构输出，每部分都要有具体细节：

1. **需求背景**：业务场景是什么、没有这个功能会发生什么、为什么要做。
2. **技术难点**（1-3 个）：难在哪、为什么常规做法不行。
3. **业务难点**（1-2 个）：如并发竞争、一致性要求、现场操作习惯、资损风险等。
4. **解决方案**：对比过的方案、最终选型理由、关键设计（含关键参数）。
5. **我做的优化**：量化成果（性能提升、成功率、成本下降），可适度拔高。
6. **测试与质量保障**：怎么测的（单测/并发用例/压测）、公司或团队的测试目标是什么（质量门槛、性能指标、上线标准）、我如何保证达到标准（指标对比、问题回归、监控兜底）。

### 去 AI 化写作要求（硬性，出现即重写）

- 全文第一人称"我"，口语短句；可用"当时 / 后来 / 踩了个坑 / 说白了 / 你猜怎么着"。
- 禁用词：首先/其次/再次/总之/综上所述/值得注意的是/不仅…而且…/赋能/抓手/闭环思维/全方位。
- 禁止排比句、对仗小标题、emoji、免责声明、"作为一个AI"类表述。
- 必须包含具体数字（阈值、次数、耗时、成功率、并发量）和至少一个"踩坑 → 定位 → 修复 → 验证"的真实感故事。
- 成果可以夸大，但必须满足三条：量级与项目规模匹配（不说"亿级日活"）、逻辑自洽（数字之间不打架）、被追问时能圆回来（自己要先想好口径）。

### 第三步：预测面试官追问（五层深挖）

读取 `references/question-framework.md`，按五层框架针对本次亮点生成 **10-15 个追问**，每个追问附：

- 面试官的问题（原话感，像真面试）；
- 第一人称参考答案（口语化，100-250 字，能直接照着说）;
- 可能的二次追问（1 个），提示答题方向。

五层框架：①概念层（是什么/为什么）②实现层（怎么做的/时序）③原理层（底层机制/极端场景）④对比层（为什么不用 X）⑤权衡层（代价/踩坑/重来怎么改）。参考答案必须讲透原理与细节，让学生"学得懂"而不是"背一句"。

### 第四步：输出交付

单个 Markdown 文档写入 `docs/interview/<模块名>-亮点讲解.md`，结构：

```
# <模块名> 面试亮点
## 一、亮点讲解稿（3-5 分钟口播稿）
## 二、面试官追问预测（分层：问题 → 参考答案 → 二次追问）
## 三、面试前 3 分钟速记卡（核心数字 + 一句话亮点 + 最容易被问的 3 个问题）
```

## 红线

- 机制、参数、设计必须来自真实代码；夸大只作用于成果量级，且必须自洽可信。
- 答案必须口语化、去 AI 化；出现禁用词或书面腔即重写。
- 追问参考答案必须把原理讲透，保证用户拿到文案能真正学懂，而不是背诵空话。
