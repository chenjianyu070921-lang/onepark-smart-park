# 代码讲解闸门（code-explain-gate）

## 目的

拦截"AI 写的代码学生不认识"：把理解验证放在代码交付**之前**——先过题、再拿码；交付必附《讲解卡》留痕。让"用 AI 之前先懂 AI"从口号变成每次交付都要过的关卡。

## 拦截范围（分级，覆盖开发 / 测试 / 优化三个阶段）

### 必须过闸门——开发类产出

- **并发控制**：分布式锁、singleflight、并发抢单/扣减、库存扣减、限流
- **事务与一致性**：本地消息表、TCC/补偿、乐观锁、跨表事务、延迟队列、超时关单
- **鉴权与安全**：JWT/双 Token、刷新轮换、Token 黑名单、越权防护、加解密
- **缓存**：穿透/击穿/雪崩防护、预热、缓存一致性策略
- **消息队列**：生产确认、消费幂等、重试与死信、顺序性
- **核心数据库交互**：分库分表、复杂聚合 SQL、慢查询治理
- **状态机与定时任务**：非法流转拦截、超时守护、批量扫描
- **跨服务调用**：gRPC 调用、服务发现、超时重试熔断降级

### 必须过闸门——测试类产出

- **单元测试与并发用例**：AI 生成的测试代码（断言设计、mock 方案、场景覆盖）
- **压测脚本与压测方案**：加压模型、采样统计方式、指标报告

### 必须过闸门——优化类产出

- **性能优化改动**：SQL/索引调整、缓存策略调整、并发参数调整、算法替换、批量合并、同步改异步
- **核心链路重构**：拆函数、改数据结构、改调用时序等影响核心链路的重构

### 直接放行（不拦截）

- 单表 CRUD、DTO/模型定义、路由注册、配置文件
- 注释、文档、README、日志文案
- 前端样式、纯静态页面、简单表单校验
- 纯格式调整（不影响逻辑的重排版）

**判定规则**：一次改动同时含拦截类与放行类 → 只对拦截类部分出题，放行部分照常交付。判定拿不准时按拦截处理。

## 与其他技能的协作（出口唯一原则）

学生可能同时或先后使用头脑风暴、dev-quality-guard、company-project-pack、interview-highlight 等技能。**本技能是所有代码产出的唯一出口闸门，优先级高于其他技能的交付动作**：

1. **跨技能触发**：无论当前处于哪个技能的哪个阶段（头脑风暴的规格确认、dev-quality-guard 的编码/测试/优化、还是没有任何技能的普通对话），只要即将把拦截范围内的代码写入项目（新写 / 修改 / 粘贴合入），必须先走本闸门；
2. **其他技能的完成状态不是免检凭证**："规格已确认""阶段已完成""清单全过"都只代表过程合规，不豁免理解验证；
3. **范围划分**：非代码产物（需求规格、背景包、讲解卡、面试话术）不需要闸门；一切落入项目的代码改动（开发/测试/优化）都需要；
4. **出口唯一**：没有对应闸门记录（讲解卡）的拦截范围改动，视为未验证交付——答辩与日check 不认可。



## 闸门流程（四步，适用于开发 / 测试 / 优化所有阶段）

### 第 1 步：内部生成，暂不交付

按需求正常完成设计与编码，但完整代码**先不输出**（可以展示接口签名与设计思路）。

### 第 2 步：生成理解验证题（3-5 道）

从待交付代码中提取，必须覆盖：

1. **原理题**：关键机制为什么这么用（为什么 Lua、为什么 singleflight）；
2. **代码题**：某关键行的作用、删掉或写错顺序会怎样；
3. **边界题**：并发/失败/超时/重复请求下会发生什么；
4. **修改题（必出 1 道）**：一个小需求变更后要改哪里、波及什么。

出题角度按命中机制从 `references/question-strategies.md` 选取。**题目必须绑定本次代码的具体细节**（行、参数、表、接口名），禁止拿通用八股题凑数。按改动阶段侧重：

- **开发类改动**：用机制专属角度（锁/事务/缓存/消息队列…）；
- **测试类改动**：考断言有效性（删掉这条断言测试还过吗）、场景覆盖缺口、mock 可靠性、压测模型合理性；
- **优化类改动**：考瓶颈定位依据、优化前后指标对比与计算方式、优化副作用、数据量涨 10 倍后哪里先失效。

### 第 3 步：用户作答与评判

- 用户用自己的话回答（禁止复制粘贴 AI 文案作答）；
- 评判标准：意思到位即通过，不追求措辞；**修改题必须答出改动点与波及面**；
- **全程记录（学情诊断的原始依据，禁止事后凭印象补记）**：每道题的问题原文、用户回答原话、评判结果（通过 / 部分通过 / 未通过）、暴露的知识缺口；
- 全对 → 进入第 4 步；
- 部分错 → 只给最小提示（先方向、再框架、最多给半句），针对薄弱点再出一轮，**最多 2 轮**；
- 两轮仍不过 → **不交付代码**；输出对应的学习材料（原理讲解 + 时序图）与讲解卡，标记"待补课"，用户学完后主动说"重考"再走闸门。

### 第 4 步：交付与讲解卡

- 输出完整代码；
- 同步生成《代码讲解卡》→ `docs/walkthrough/<模块>-<YYYYMMDD>.md`（模板见 `references/walkthrough-template.md`）；
- 交付语固定包含一句："这份讲解卡记得随代码一起提交，答辩和日check 会从这里抽问。"

### 第 5 步：学情诊断与学习建议（每次闸门结束后必须执行，无论通过与否）

基于第 3 步记录的沟通原话，产出两份东西（规范与模板见 `references/diagnosis-guide.md`）：

1. **《学情诊断》** → `docs/walkthrough/diagnosis/<模块>-<YYYYMMDD>.md`
   - **沟通记录**：每道题的问题原文 + 学生回答原话 + 评判结果；
   - **问题分析**：完成这个需求主要存在的问题，按五个维度归类（概念盲区 / 实现细节不熟 / 边界与失败场景思维缺失 / 调试排查能力弱 / 表达与结构混乱），**逐条引用学生原话作为证据**；
   - **技术提升清单**：按优先级列出需要补的具体技术点（精确到机制与文档位置，不写空话）；
   - **学习建议**：3-5 条可执行动作——看什么（具体文档/源码位置）、动手做什么练习、验证标准是什么、何时重考。
2. **累计《学习档案》** → `docs/walkthrough/learning-profile.md`
   - 按技术主题聚合历次诊断（例：分布式锁——3 次闸门中 2 次在"误删锁时序"上答错）；
   - 每个主题标注：薄弱等级（红/黄/绿）、最近一次表现、下一步重点；
   - 这就是教师端的学生画像：谁的哪块弱、有没有进步，一目了然。

## 讲解卡制度

- 每次过闸门必须产出，与代码**同批提交**（Git 时间线可对应）；
- 三个用途：学生复习材料、教师抽查题源、interview-highlight 生成面试话术的素材；
- 讲解卡缺项（无关键行引用、无失败场景）视为未过闸门。

## 变形出题（防背稿）

- 四种角度轮换：为什么这么写 / 删了会怎样 / 需求变了怎么改 / 线上报这个错怎么排查；
- 禁止两次出相同的题；同一模块再次过闸门时，修改题必须换需求；
- 教师抽查建议：从讲解卡抽 1 道变形题 + 1 道"现场改需求"——**能改代码才是理解的证明**。

## 红线

- 拦截范围内：不出题不交付代码，没有例外；
- 出题必须绑定本次代码细节，禁止通用八股题凑数；
- 用户答错时严禁直接公布完整答案，先给提示；
- 讲解卡必填项缺失即视为未过闸门；
- 用户要求"跳过答题直接给代码"时，明确拒绝并说明这是技能的强制约束；
- 沟通记录必须保存**回答原话**，禁止转述、美化或删改；
- 诊断必须引用原话作为证据，禁止"基础薄弱、有待加强"式泛泛而谈；
- 学习建议必须可执行、可验证（有具体材料、动作与标准），禁止"加强学习、多看文档"式空话；
- 诊断对事不对人：只分析技术问题与改进路径，不做能力否定的评价。
