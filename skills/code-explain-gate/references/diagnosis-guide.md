# 学情诊断指南与模板

第 5 步的执行依据。每次闸门结束（通过、待补课均包含）必须产出《学情诊断》，并同步更新累计《学习档案》。

## 一、问题分析五维度

分析学生"完成这个需求主要存在的问题"时，从以下五个维度归类，每个结论必须引用学生回答原话作为证据：

| 维度 | 典型表现（判断信号） |
|---|---|
| 概念盲区 | 说不清机制是什么、为什么用它（例：不知道 Lua 为什么能保证原子） |
| 实现细节不熟 | 知道大概思路，说不出关键参数、行级逻辑、调用顺序 |
| 边界与失败场景思维缺失 | 只讲正常链路，问超时/重复/并发就卡住，兜底手段说不出来 |
| 调试与排查能力弱 | 修改题/排错题答不出改动点，没有定位问题的方法路径 |
| 表达与结构混乱 | 知道但说不清：跳跃、绕圈、抓不住重点（单独标注，与技术问题区分） |

补充维度（出现才写）：工程习惯（不写注释、命名随意、无自测就交付）、态度问题（明显没看代码就作答）。

## 三、学习建议写法规范

每条建议必须满足"**动作 + 材料 + 验证标准 + 时限**"四要素，反例与正例：

- ❌ "加强对分布式锁的学习，多看相关文档。"（空话，不可验证）
- ✅ "动手复现锁误删：写两个 goroutine 模拟 A 超时后 B 抢锁、A 回来释放的场景，打印锁持有者变化；完成标准是能画出误删发生的时序图并说清 token 如何避免；预计 2 小时，3 天内完成，重考时第 1 题就考这个。"

建议来源优先级：本次闸门暴露的具体缺口 > 该主题历史薄弱点 > 通用工程能力（测试、调试习惯）。

## 四、累计《学习档案》模板

文件：`docs/walkthrough/learning-profile.md`（每生一份，持续追加更新）

```markdown

> 由 code-explain-gate 闸门自动维护；教师查看学生画像用。

## 一、主题掌握度总览（红=薄弱 黄=不稳定 绿=掌握）

| 技术主题 | 等级 | 闸门次数 | 错误集中点 | 最近表现 | 下一步重点 |
|---|---|---|---|---|---|
| 分布式锁 | 🔴 | 3 | 误删时序、看门狗原理 | 2 轮通过 | 重考变体：主从切换丢锁 |
| 缓存三重防护 | 🟡 | 2 | 击穿与雪崩概念混淆 | 1 轮通过 | 讲清 singleflight 原理 |
| JWT 双 Token | 🟢 | 2 | — | 1 轮通过 | 无 |

## 二、历次诊断索引
| 日期 | 模块 | 结果 | 诊断报告 |
|---|---|---|---|
| 2026-09-19 | 订单超时关单 | 待补课 | diagnosis/order-20260919.md |

## 三、阶段性结论（每 2 次闸门更新一次）
<进步点 + 仍需关注点 + 对教师的建议（是否需要一对一）>
```

## 五、教师用法

1. **日常**：抽看 learning-profile.md 的红/黄项，直接获得"谁、哪块弱、错在哪"；
2. **一对一辅导**：用诊断报告里的原话证据开场（"你当时说……，实际上……"），比空泛批评有效；
3. **答辩抽查**：从红/黄主题出变形题；
4. **月度复盘**：对比学习档案的阶段结论，评估学生进步曲线并调整分层。
