# 《代码讲解卡》模板

第 4 步的执行依据。每次过闸门生成一份，保存到 `docs/walkthrough/<模块>-<YYYYMMDD>.md`，与代码**同批提交**。必填项缺失视为未过闸门。

```markdown
# 讲解卡：<功能名>

- 日期：<YYYY-MM-DD>
- 涉及文件与关键行：<path/file.go:L12-L48>
- 闸门结果：1 轮通过 / 2 轮通过 / 待补课
- 关联需求：<需求规格或任务描述的一句话>

## 一、这段代码做什么（3 句话说清）
<业务场景 + 解决什么问题 + 在整个链路里的位置>

## 二、为什么这么设计
<对比过的方案一句话 + 选型理由；不废话>

## 三、流程 / 时序
<文字时序或 mermaid，6-10 步；标注并发与失败分支>
1. ...
2. ...

## 四、关键代码点（2-4 处，必填）

| 位置 | 作用 | 删掉/改错会怎样 |
|---|---|---|
| handler.go:L31 | ... | ... |
| lock.go:L18 | ... | ... |

## 五、参数与阈值（必填）

| 参数 | 值 | 为什么是这个值 |
|---|---|---|
| 锁 TTL | 10s | ... |
| 重试次数 | 3 | ... |

## 六、失败与边界场景（至少 3 条，必填）

| 场景 | 系统行为 | 兜底手段 |
|---|---|---|
| 并发 100 个同 id 请求 | ... | ... |
| Redis 超时 | ... | ... |
| 重复请求 | ... | ... |

## 七、闸门问答摘录
<本次出的问题 + 我的回答（原话精简）+ 哪题第一次答错了、错在哪>

## 八、可能的追问（3 个 + 一句话答题方向）
1. <追问> → <方向>
2. ...
3. ...
```

## 使用规则

- 学生：复习用——面试/答辩前只看讲解卡就能快速回忆全部细节；
- 教师：抽查用——从"关键代码点/参数阈值/失败场景"任选一项变形提问；重考"待补课"模块；
- 联动：interview-highlight 生成面试话术时，优先读取讲解卡作为素材（真实、可追溯）。
